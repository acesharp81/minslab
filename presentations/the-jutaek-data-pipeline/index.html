01

결과뿐 아니라, 왜 이렇게 만들었는가

처음의 목표와 원천자료의 제약을 연결해 구현 선택을 설명합니다. 기록으로 확인한 이유와 분석에 따른 해석을 구분했습니다.

SOURCE DISCOVERY

법정 절차에서 출처로

정책 발표·지구 지정·인허가·착공·모집·입주의 절차를 따라 소관기관과 공고부서를 찾고, 고시·API·기관 원장으로 수집 경로를 구조화한 방법.

TYPE-SPECIFIC PIPELINES

자료마다 다른 처리 방식

JSON/XML, HTML, CSV, PDF, DOCX, HWPX, 이미지와 GIS의 수집·파싱·변경 감지. 자동 순회·백필과 추출 대기 상태의 차이.

PREPROCESSING

같은 사업, 다른 물량

명칭·주소·블록 정규화, 대표 사업 연결, 전체와 부분의 구분, 정정·추가 모집과 중복 처리. 0·자료 없음·미측정을 구분하는 원칙.

OPERATIONS

실패하고 복구한 기록

API 429, 누락된 지역·유형, 문서 구조 변경, 잘못 합쳐진 블록, 과도한 응답 크기와 복원 검증 등 실제 장애와 보완 사례.

AI & ACCOUNTABILITY

AI가 한 일과 검수 책임

탐색·문서 대조·이미지 검토·코드와 수정 제안에 기여한 AI. 규칙 기반 운영 파이프라인 및 실제 담당자의 승인과 구분해야 할 부분.

DATA GOVERNANCE

원천에서부터 식별하기

정책·프로그램·사업의 공통 ID, 공급 범위와 사건의 연결, 표준 API, 정정·취소 이력, 승인 책임과 단계별 이행 방안.

02

수집 성공은 검증 완료의 출발점입니다

파일을 내려받았어도 문자를 읽지 못할 수 있고, 숫자를 읽었어도 어느 사업의 실적인지 판단이 남을 수 있습니다.

STEP 01공식 출처 선택

법정 절차·책임기관
공개 범위와 갱신 조건

STEP 02원문 수집·보존

자동 순회·재시도
원문 해시와 판본

STEP 03유형별 추출

표·본문·좌표 정형화
그림·미추출 상태 보존

STEP 04사업·근거 연결

동일성·범위·시점 판단
중복·모순·귀속 검토

STEP 05집계·설명·운영

기준본·산식·기여 원천
화면·CSV·감사·복구

현재 파이프라인은 기관별 규칙 파서를 중심으로 운영됩니다. 통합 자동 OCR은 미구현이며, 일부 이미지 표는 별도 시각 검토로 보완했습니다.

03

숫자가 달라진 이유를 실제 사례로

오류의 이름만 나열하지 않고, 발견한 현상·원인·조치·남은 한계를 함께 설명합니다.

1,030호 안의 344호

주암 C2 · 전체와 임대 부분

전체 사업 1,030호와 행복주택 344호는 서로 다른 범위입니다. 같은 이름이라는 이유로 더하거나, 서로 모순되는 값으로 처리하면 안 되는 사례입니다.

AA13-1 ≠ AA13-2

검단 · 분할 블록의 정체성

분할 블록을 보존하도록 파서를 보완했습니다. 추출이 고쳐졌어도 복수현장 계약의 포함관계와 정책 귀속 검토는 별도로 남습니다.

700 → 350호

부평 · 같은 현장의 중복 표시

지도에서 같은 현장의 중복 물량을 바로잡았습니다. 원천 파일이 바뀐 것인지, 연결·표시 방식이 바뀐 것인지와 정책 집계 영향을 구분합니다.

82,968 / 99,885호

누적 착공 도달량과 연말 전망

10월 22일 정책 관리 기준본의 서로 다른 지표입니다. 과거 착공·관리 채택·추정이 포함되어, 올해 정부 전체 실착공 통계와 직접 비교할 수 없습니다.

오래된 미완료 기록은 최신 조치와 대조했습니다. 일반 인허가 2,907/2,907 조회 완료와 원천의 완전성·사건 연결 검증은 서로 다른 상태입니다.

04

AI의 기여는 구체적으로, 승인은 명확하게

어떤 판단이 AI·규칙 엔진·업무 책임자의 것인지 구분해야 기록을 신뢰할 수 있습니다.

기록에서 확인한 AI의 역할

  • 공식 자료 조사와 후속 근거 찾기, 다른 조사 결과의 교차 확인
  • 문서·이미지 표의 검토, 동일 사업·블록·수량 후보 대조
  • 오류 원인 분석, 파서·매칭·집계 코드 수정과 검증 보조
  • 위임된 검토·반영 및 근거 문서 작성

별도로 확인해야 할 책임과 한계

  • 상시 수집의 중심은 API 호출과 규칙 파서이며, 모든 문서를 LLM이 읽는 구조로 확인되지 않음
  • 자동연결이나 에이전트 대행 기록만으로 인간의 독립 승인을 입증할 수 없음
  • 모델·프롬프트·호출별 평가 로그가 전부 확보된 것은 아님
  • 앞으로 수행자 유형·제안·검토·공식 승인 상태를 각각 기록해야 함
강점과 공백을 함께 봅니다. 원문·판본·근거를 남기고 모순을 설명하는 기반은 갖췄습니다. 기관 간 공통 ID, 실계약·실입주 전량 연계, OCR, 문서별 처리 완결률과 승인 통제는 더 보완해야 합니다.
05

다음 단계는 원천 업무시스템의 개선입니다

the주택 내부 ID는 이미 있습니다. 개선의 핵심은 기관들이 같은 대상을 식별하고, 그 관계와 변경을 함께 전달하는 체계입니다.

공통 ID + 관계 + 변경 이력 + 책임

정책·프로그램·사업에 공통 식별자를 부여하고, 고시·공고·공개 파일·표준 API에 명시해야 합니다. 공급 범위와 행정 사건까지 연결해야 전체·부분 물량과 정책 중복을 설명할 수 있습니다.

정책 ID프로그램 ID사업 ID공급 범위 ID사건 ID문서·판본 ID
업무 등록 단계

기존 ID 조회·발급, 기관 키 대응, 분할·통합·승계 관계, 책임부서와 승인권한.

API 제공 단계

수량·단위·기간·범위, 정정·취소와 이전 판본, 변경 피드·누락 상태·재개 지점.

검수·공표 단계

인간·AI·서비스 계정 구분, 제안과 승인 분리, 기준본·산식·근거와 정정 공표.

이 부분은 개선 제안입니다. 해당 거버넌스 기능이 이미 모두 도입되었다는 의미는 아닙니다. 학습서 마지막 장에 업무별 개선 표, API 예시, 이행 단계와 평가 지표를 담았습니다.
