# ㅁㅁㅈ(뭐먹지?) — 대화형 매장 주문 PoC

**누구나, 자기 말로 주문할 수 있게.** 손님은 **먹고 가기/가져가기**를 고른 뒤 일행과 취향을 평소 말처럼 입력하고, 여러 차례 대화하며 메뉴를 함께 골라 모의 결제로 주문합니다. 전체 메뉴판은 참고용입니다. 사장님은 별도 화면에서 메뉴·알레르기·옵션을 관리하고 주문과 직원 호출을 접수합니다. 이 문서만으로 현재 서비스를 사용하고 재현할 수 있도록 실제 동작 기준으로 작성했습니다. 팀의 목표·진척·담당 인수인계는 [단일 공유 계획](docs/PLAN.md)에 있습니다.

> **현재 상태 (2026-10-02): Groq 무료 모델로 문맥 해석·일행별 상태 변경 구현, 내부 최종 수용은 보류.** 메뉴·주문·점주 관리가 공개 HTTPS 주소에서 동작합니다. 데모 매장과 모든 음식·알레르기 표시는 가상 테스트 데이터입니다. 실제 음식을 주문하거나 안전 판단에 사용하지 마세요. 실제 돈은 결제되지 않습니다.

## 바로 사용하기

| 사용자 | 주소 | 하는 일 |
| --- | --- | --- |
| 손님 | <https://www.minslab.kr/mmj> → **손님으로 주문하기** | 방문 방식 선택·대화형 그룹 추천·장바구니·모의 결제·주문 내역·직원 호출 |
| 테이블 손님 | `/poc/mwomeokji/s/orange-table/?table=A1` | 미래 QR 진입 호환용 A1 테이블 힌트. 현재 화면에서 테이블 선택은 요구하지 않음 |
| 사장님 | `/poc/mwomeokji/merchant/` | 주문·직원 호출·메뉴·옵션·메뉴판 초안 관리 |
| 운영 점검 | `/poc/mwomeokji/api/health/` | DB 연결을 포함한 앱 상태 |

사장님 로그인 화면에는 공개 내부 테스트 계정 `demo@mmj.local` / `demo1234`가 자동 입력되어 있습니다. **로그인**만 누르면 됩니다. 별도 비공개 점주 계정은 루트 `.env`의 `POC09_MERCHANT_EMAIL`, `POC09_MERCHANT_PASSWORD`로 설정할 수 있습니다. 공개 데모 계정은 가상 매장 전용입니다. 현재 매장은 `오렌지 테이블`, 가상 메뉴 **84개**, 테이블 5개입니다. 메뉴 구성은 식사 39개·국물 9개·사이드 12개·디저트 10개·음료 14개입니다. 기존 28개에 `prisma/scenario-recipes.ts`의 56개를 추가했으며, 다시 seed를 실행해도 이미 수정된 메뉴 값은 덮어쓰지 않습니다.

### 가상 메뉴로 시험할 수 있는 상황

| 종류 | 예시 | 시험할 조건 |
| --- | --- | --- |
| 식사 39개 | 키즈 덮밥, 매운 참치 볶음밥, 비건 두부 덮밥, 연어 덮밥, 베이글·파니니, 파스타 | 인원별 맛, 맵기 0–4, 채식·해산물 제한, 밥/빵/브런치, 가격대 |
| 국물 9개 | 순한 닭고기 수프, 매운 김치 두부찌개, 조개 맑은탕, 단호박 수프 | 맵기 변경, 알레르기 후 다른 국물 찾기, 유제품·해산물 구분 |
| 사이드 12개 | 감자튀김, 새우튀김, 오이 피클, 견과 에너지볼 | 작은 예산, 땅콩·견과·밀·갑각류, 추가 주문 |
| 디저트 10개 | 치즈케이크, 망고 코코넛 푸딩, 레몬 셔벗, 티라미수 | 달콤/새콤 전환, 비건·우유·참깨·커피 재료 확인 |
| 음료 14개 | 에이드, 달콤 사과 주스, 딸기 우유, 보리차, 디카페인 커피 | 카페인 없음과 디카페인 구분, 수량·합계 예산, 신맛 제외 |

이 메뉴는 대화와 주문 안전 검증을 위한 **가상 레시피**입니다. `merchant_verified`도 가상 재료에 대한 테스트 표시이며 실매장 성분 보증이 아닙니다. 전체 메뉴판은 손님 화면의 참고 영역과 사장님 메뉴 관리에서 볼 수 있습니다.

### 손님 흐름 — Tap · Talk · Together

1. **손님으로 주문하기**를 누르고 **먹고 가기** 또는 **가져가기**를 탭합니다. 테이블 번호나 회원가입은 필요하지 않습니다.
2. 대화창에 “2살 딸이랑 와이프랑 나랑 밥 먹을게. 나는 매운 걸로, 아이는 키즈 메뉴 중 달달하고 맵지 않은 걸로, 와이프는 국물 있는 걸로 주문해줘”라고 입력합니다. 세 사람의 조건을 따로 기억하고 실제 메뉴와 가격을 추천합니다. 이때 “주문해줘”는 메뉴를 골라 달라는 뜻으로 처리하며 곧바로 주문을 접수하지 않습니다. 데모 매장에는 순하고 달콤한 키즈 덮밥이 있습니다. 2살 아이에게 맞는 재료와 식감인지 보호자가 확인해야 합니다.
3. “와이프꺼는 더 얼큰한걸로 보여줘”라고 이어 말하면 와이프의 순한 국물 메뉴를 얼큰한 국물 메뉴로 바꿔 추천합니다. 이어 “아니면 덮밥류로 추천해줘”라고 하면 같은 사람의 국물 조건을 덮밥 조건으로 교체하고 얼큰한 맛은 유지합니다. 데모에는 해물 없이 고를 수 있는 가상 얼큰 닭고기 수프·덮밥이 있습니다. “알러지는 없고 얼큰한걸로”라고 명시하면 현재 손님/테이블의 알레르기 설정을 정정하고 직전 사람의 추천을 이어갑니다. 이름이 붙은 일행의 알레르기 제한은 그대로 남습니다. “추천한 거 전부 담아줘”, “좋아 담아줘” 또는 “담아줘”로 직전의 완성된 일행별 제안을 장바구니에 담습니다. “첫 번째 담아줘”, “다른 거”, “4만원 안에서 다시 추천해줘”처럼 이어 말해도 앞서 파악한 일행을 기억합니다. “많이” 등 옵션명을 함께 말하면 해당 옵션을 우선 확인합니다. 카드의 **자세히**는 재료와 옵션을 직접 확인하는 보조 조작입니다.
4. “내꺼에 오이가 들어갔는지 확인해봐”처럼 물으면 직전 추천이나 장바구니에서 본인 메뉴를 찾아 등록 재료와 선택한 옵션을 확인합니다. 재료 목록에 없다는 결과는 미포함 확인이 아니므로 실제 조리 재료는 점주에게 확인해야 합니다. 그룹 메뉴를 추천받은 뒤 “주문해줘”라고 하면 일행별 추천을 장바구니에 담고 합계를 읽은 다음 **최종 확인**을 받습니다. 혼자 여러 후보를 추천받았다면 주문할 메뉴를 먼저 지정해야 합니다. **장바구니**에서 금액·일행별 메뉴·수량을 확인합니다. 대화에서 “주문할게” 또는 “주문할께”라고 말해 장바구니 합계를 듣고 “응”으로 확인하거나 장바구니의 **모의 카드/현장 결제** 버튼을 누릅니다. 실제 돈은 결제되지 않습니다. **주문 내역**에서 상태를 확인합니다.
5. “카페인 없는 커피 음료 2잔, 1만원 이하”처럼 메뉴 종류·제외 성분·수량·전체 예산을 함께 말해도 됩니다. 현재 가상 매장에는 **카페인 없음이 확인된 커피 메뉴가 없어** 다른 음식으로 바꾸지 않고 메뉴가 없다고 안내합니다. `2잔`은 `2명`으로 취급하지 않으며, 해당 메뉴가 점주 확인 후 등록되면 2잔 합계를 검증합니다. 이어 “카페인 없는 음료 2잔으로”라고 말하면 커피 조건만 풀고, 가상 데이터에 `caffeine_free`로 표시된 판매 가능한 음료 중에서 고릅니다(예: 오렌지 에이드 2잔 9,000원). 이어 “신거 말고 달달한거로”라고 하면 카페인 없음·2잔·1만원 조건을 유지하고, 가상 단맛 음료 중에서 고릅니다(예: `달콤 사과 주스` 2잔 9,000원). “첫 번째 담아줘”로 2잔이 장바구니에 담깁니다. 디카페인은 별도 종류이므로 원하면 명시적으로 말씀해 주세요.
6. “친구 3명이 브런치로 먹을 메뉴”, “빵으로 간단히”, “점심에 밥”, “저녁엔 든든하게”, “대표메뉴”, “추천이 많은 식사”, “애기용으로 맵지 않게”, “데이트로 둘이”, “직장동료와 점심”처럼 상황을 말할 수 있습니다. 브런치·밥·빵·대표메뉴·든든·데이트·직장동료는 사장님이 메뉴에 적은 **추천 키워드**에 맞춰 고릅니다. 디저트와 음료는 각 카테고리에서 고릅니다. 여러 명에게 추천할 때는 가능한 한 서로 다른 메뉴를 고르며, “겹치지 않게”라고 말하면 중복 없는 조합만 제안합니다. 현재 조건으로 불가능하면 같은 메뉴를 몰래 반복하지 않고 조건 변경을 요청합니다. “매콤한” 요청은 실제 맵기 정보를 확인합니다. “추천이 많은”은 현재 데모의 상대적 인기 점수를 참고하며 실제 추천 횟수를 뜻하지 않습니다. 점심·저녁은 식사 맥락으로 이해하지만, 현재 메뉴별 판매 시간 정보는 없으므로 시간 한정 메뉴 여부는 판단하지 않습니다. 아이 음식은 보호자가 나이·재료·식감을 확인해 주세요. “이전에 주문했던 메뉴”는 **같은 브라우저의 현재 익명 세션에서 완료한 주문**만 찾아 현재 판매·안전 조건으로 다시 확인합니다. 다른 기기나 만료된 세션의 주문은 찾지 않습니다.
7. 알레르기·못 먹는 재료는 대화로 알려 주세요. **내 취향** 패널에서 지속 취향·큰 글씨를 설정할 수도 있습니다. **전체 메뉴 참고**는 대화가 어려울 때만 열면 됩니다. 필요하면 “직원 불러줘”라고 말합니다.

조별 식사 예시: “4명이서 식사할 건데 여자 두 분은 매운 걸 잘 못 드셔. 메뉴 추천해줘”라고 말하면 **네 분 모두 식사 메뉴**에서 고르고, 여자 두 분에게만 맵기 0 메뉴를 배정합니다. 이어 “음료나 사이드 말고 식사류로 선택해줘”라고 정정해도 네 분의 식사 종류와 사람별 맵기 조건을 유지합니다. 성인 일행에게 키즈 메뉴를 기본 배정하지 않습니다. 이전 버전에서 음료가 남은 대화도 같은 정정 문장으로 식사 추천을 다시 받을 수 있습니다.

가족 주문 예시: “4식구 외식을 왔어. 아이 둘은 키즈 메뉴로, 나와 와이프는 든든한 메뉴로. 와이프는 맵지 않게 추천해줘”라고 말하면 아이 둘과 어른 둘의 조건을 각각 적용합니다. 아이 둘에게 맞는 키즈 메뉴 조합을 검증할 수 없을 때만 “아이들에게 맵지 않은 일반 메뉴를 골라볼까요?”라고 묻습니다. 이어 “그래 그러게 해줘” 또는 “그렇게 해달라고”라고 답하면 **아이 둘의 메뉴 조건만** 바꿔 다시 제안하고, 어른 메뉴와 채식·알레르기 같은 안전 조건은 유지합니다. 제안된 네 메뉴가 마음에 들면 “좋아 담아줘”로 함께 담을 수 있습니다.

문자 입력과 스마트폰 **음성 키보드** 입력은 같은 대화 API를 사용합니다. 앱 자체 마이크·STT·음성 출력은 아직 제공하지 않습니다. 브라우저를 새로고침할 때 장바구니가 비어 있으면 채팅 문장과 일회성 인원·메뉴 조건을 함께 새로 시작합니다. 장바구니에 메뉴가 있으면 일행별 안전 검증을 위해 그 조건과 담은 메뉴를 유지하며, 대화로 주문을 이어갈 수 있습니다. 주문을 완료하면 일회성 대화 조건과 추천은 지우고, 내 취향 설정과 주문 내역은 유지합니다. 재방문 후 “남자 4명인데 든든히 먹을 메뉴를 추천해줘”처럼 일행과 식사를 처음부터 다시 설명하면 이전 대화의 예산·메뉴 취향·수량을 지웁니다. 새 문장에 예산을 말한 경우에만 그 예산을 적용합니다. “그럼 다른 메뉴로”처럼 이어 말하면 이전 조건을 유지합니다. 같은 사람에게 기록된 알레르기·엄격한 식사 조건과 **내 취향 설정**은 유지됩니다. 이전 일행의 알레르기 대상을 새 설명만으로 확인할 수 없으면 이번 주문의 공통 제한으로 유지합니다. 조건 때문에 메뉴가 없으면 화면에 저장된 제한 종류를 알려 줍니다. 잘못 저장된 공통 알레르기는 “알러지는 없어”처럼 명시적으로 정정하거나 **내 취향**에서 수정할 수 있습니다.

### 사장님 흐름

1. 입력된 데모 계정으로 **로그인**만 누릅니다. 새 주문에 먹고 가기/가져가기 방식이 표시됩니다. 주문·직원 호출 화면은 약 12초마다 새로고침되고 수동 새로고침도 가능합니다.
2. 주문의 상태를 **새 주문 → 접수 → 조리 중 → 준비 완료 → 전달 완료** 등으로 변경합니다. 손님 주문 내역에 반영됩니다. 직원 호출은 **처리 완료**로 닫습니다.
3. **메뉴 관리**에서 새 메뉴를 만들거나 기존 메뉴를 수정하고 공개·판매 상태를 바꿉니다. 추천 키워드에는 실제 매장 메뉴의 용도나 상황(예: 브런치, 대표메뉴, 데이트)을 쉼표로 구분해 입력합니다. 음료 메뉴에는 커피 여부, 디카페인/카페인 없음, 달콤함/새콤함을 실제 메뉴 정보에 맞춰 선택합니다. 디카페인을 카페인 없음으로 표시하지 않습니다. 재료와 10개 알레르기 항목은 실제 확인 결과에 따라 `포함 / 확인: 미포함 / 미확인`으로 입력합니다. 공개 전 재료와 모든 항목의 점주 확인이 필요합니다.
4. 메뉴 편집기의 **메뉴 옵션**에서 그룹(예: 밥 양), 필수·최대 선택 수, 각 선택지의 추가 금액·재료·알레르기 정보를 등록하거나 삭제합니다. 옵션을 바꾸면 손님의 기존 장바구니는 주문 전에 재검증됩니다.
5. **메뉴판 가져오기**에는 `메뉴명 | 가격 | 설명`을 한 줄씩 입력합니다. 초안으로만 저장되며 재료·알레르기 확인 뒤 공개합니다. 루트 `.env`에서 별도 이미지 AI 스위치인 `POC09_AI_PROVIDER=openrouter`를 켜면 JPG/PNG/WEBP 이미지 인식도 사용할 수 있습니다. AI 결과는 안전 정보로 확정하지 않습니다.

### 실행·재현

저장소 루트에서 PoC9 폴더로 이동합니다. 호스트에 Node 24가 없으면 Docker의 `node:24-bookworm` 이미지에서 **Node 바이너리만 이 폴더 `.runtime/`에 준비**합니다. 기존 호스트 Node 버전은 바꾸지 않습니다.

```bash
cd PoC/09-mwomeokji
./scripts/prepare-node24.sh
PATH="$PWD/.runtime/bin:$PATH" npx -y npm@11 ci
```

PostgreSQL 16을 독립 실행합니다. 이 서버에는 Compose 플러그인이 없어 아래 `docker run`을 사용했습니다. Compose가 있는 개발 환경은 `docker compose up -d db`를 사용할 수 있습니다.

```bash
sudo docker run -d --name poc09-mwomeokji-db --restart unless-stopped \
  -e POSTGRES_USER=poc09 -e POSTGRES_PASSWORD=poc09_local_only -e POSTGRES_DB=poc09 \
  -p 127.0.0.1:18091:5432 -v poc09_pgdata:/var/lib/postgresql/data postgres:16-alpine
PATH="$PWD/.runtime/bin:$PATH" npm run db:generate
PATH="$PWD/.runtime/bin:$PATH" npm run db:migrate
PATH="$PWD/.runtime/bin:$PATH" npm run db:seed
PATH="$PWD/.runtime/bin:$PATH" npm run build
PATH="$PWD/.runtime/bin:$PATH" npm run start
```

이미 같은 이름의 DB 컨테이너가 있다면 새로 만들지 말고 `sudo docker start poc09-mwomeokji-db`로 시작합니다. Seed는 재실행할 수 있습니다. 개발 중에는 `npm run dev`를 사용합니다. 위 npm 명령은 모두 `PATH`의 Node 24가 필요합니다. `prisma/migrations/202609240001_init`가 초기 스키마이고 `202609240002_visit_mode`가 식사 방식 필드를 추가합니다. 새 스키마 변경은 `db:dev-migrate`로 별도 마이그레이션을 만들고 운영에는 `db:migrate`를 적용합니다.

운영 서버에는 [PoC9 systemd 유닛](deploy/poc09.service)과 [만료 세션 정리 타이머](deploy/poc09-cleanup.timer)를 설치했습니다. `sudo systemctl status poc09.service`, `sudo journalctl -u poc09.service -n 100 --no-pager`, `sudo systemctl restart poc09.service`로 확인·재시작합니다. DB는 `sudo docker ps --filter name=poc09-mwomeokji-db`로 확인합니다. 변경 배포 순서는 `npm ci → db:generate → db:migrate → build → poc09.service 재시작 → smoke`입니다. Python 프록시 코드가 바뀐 경우에만 `myservice.service`도 재시작합니다. DB 백업은 `sudo docker exec poc09-mwomeokji-db pg_dump -U poc09 poc09 > poc09-backup.sql`처럼 별도 안전한 경로에 저장하고, 복구는 새 DB에 검증 후 수행합니다.

### 설정

설정과 API 키는 **루트 `.env`**에만 둡니다. `scripts/with-root-env.mjs`가 허용된 변수만 자식 프로세스에 전달합니다. 전체 루트 `.env`를 컨테이너에 주입하지 않으며 `NEXT_PUBLIC_*`에 비밀값을 두지 않습니다. 비밀값 없이 추천을 시험하려면 AI/판단 제공자를 Mock/Rules로 둡니다.

| 변수 | 기본/역할 |
| --- | --- |
| `POC09_DATABASE_URL` | 전용 PostgreSQL 접속. 미설정 시 위 로컬 DB URL |
| `POC09_MERCHANT_EMAIL`, `POC09_MERCHANT_PASSWORD` | 별도 비공개 점주 로그인, 루트 `.env`에서 설정 |
| `POC09_SESSION_SECRET` | 방문자·점주 세션 토큰의 HMAC 키 |
| `POC09_CONVERSATION_PROVIDER` | 운영 `groq`; 현재 발화와 필요한 익명 일행·직전 추천 요약을 무료 Groq 모델이 해석. `rules`는 외부 호출 없는 회귀 시험 |
| `POC09_AI_PROVIDER` | 메뉴판 이미지 인식용 별도 스위치. 현재 공개 서비스는 `mock` |
| `POC09_METER_TOKEN`, `POC09_METER_URL` | 공용 AI 장부 인증 토큰과 내부 URL. 요청 내용은 기록하지 않음 |
| `POC09_LLM_MODEL`, `POC09_VISION_MODEL` | 대화 모델은 `openai/gpt-oss-20b`(Groq 무료 경로), 이미지 실험 모델은 별도 서버 전용 설정 |
| `POC09_DECISION_PROVIDER` | 기본 `rules`; `jev-openrouter`면 검증된 후보의 순위만 선택적으로 조정 |
| `POC09_JEV_MODEL` | 선택 실험 모델 ID. 실패·낮은 신뢰도·형식 오류면 룰 순위를 유지 |
| `POC09_MENU_SELECTOR_PROVIDER`, `POC09_MENU_SELECTOR_MODEL` | 운영 `rules`: DB에서 검증한 실제 메뉴로 일행별 조합. 기존 OpenRouter 메뉴 선택 실험은 운영 대화 경로에서 사용하지 않음 |
| `POC09_UPSTREAM` | Python 프록시의 PoC9 서비스 주소, 기본 `http://127.0.0.1:18090` |

사용자가 현재 발화와 필요한 일행·추천 요약을 Groq 무료 모델로 보내는 범위를 승인했습니다. 운영 대화 모델은 `openai/gpt-oss-20b`로 고정하고, 메뉴 조합과 주문 검증은 서버가 합니다. Groq 장애·응답 형식 오류·무료 한도 소진 때는 **기존 대화와 장바구니를 보존**합니다. 한도 응답에 재시도 시간이 있으면 대략 몇 분 뒤 다시 말하면 되는지도 안내합니다. 유료 OpenRouter 모델로 자동 전환하지 않습니다. 메뉴판 이미지 인식은 별도 `POC09_AI_PROVIDER` 스위치이며 기본 `mock`, 실험 판단은 `rules`입니다. `--live-groq` 평가 명령은 합성 문장을 실제 Groq에 보내므로 공용 무료 한도를 사용합니다.

### 대화형 LLM 연결과 개인정보 범위

서버의 `lib/ai.ts`는 Groq의 무료 `openai/gpt-oss-20b`로 **현재 발화와 압축된 대화 상태**를 해석합니다. 전송 상태에는 익명 `seat_N` 일행, 열린 취향·공개 메뉴 태그, 직전 추천의 공개 메뉴명·ID·담당 자리, 전체 예산·종류, 직전 대체 제안이 필요한 경우 그 요약만 담습니다. 저장된 일행 이름은 외부 전송 전에 번호로 치환하고, 돌아온 번호는 서버 안에서 원래 사람에게 다시 연결합니다. 원문 대화 이력, 세션 ID, 장바구니 상세, 알레르기·엄격 식이 조건, API 비밀값은 보내지 않습니다.

모델은 발화가 일행별로 **누구의 어떤 조건을 바꾸는지**, 직전 제안을 수락했는지, 현재 추천의 몇 번째 자리를 바꾸는지를 구조화해서 제안합니다. 서버는 대상 자리와 메뉴 태그가 현재 발화·상태에 근거하는지 확인합니다. 실제 판매 메뉴·옵션·가격·예산·알레르기·채식·맵기·최종 주문 가능 여부는 DB와 서버 검증 코드만 결정합니다. “담아줘”와 “주문할게” 같은 명확한 장바구니 명령은 서버가 직전 제안·장바구니를 기준으로 처리합니다. 모델 JSON이 실패하면 제한된 재시도 후 그 턴을 중단하며 기존 상태를 보존합니다.

Groq는 [공식 데이터 문서](https://console.groq.com/docs/your-data)에서 일반 추론 입력·출력을 기본적으로 보관하지 않지만 장애 조사·남용 감시 상황에서는 최대 30일 보관될 수 있다고 설명합니다. Zero Data Retention은 계정의 Data Controls에서 별도로 켜야 하며, **이 계정에서 활성화됐는지는 API만으로 확인하지 못했습니다.** 데모는 가상 매장 데이터로 시험하고 실제 손님 데이터 사용 전 계정 설정을 운영자가 확인해야 합니다.

**배포 상태:** PoC9 대화는 Groq 무료 모델을 사용하고 OpenRouter 유료 대화·메뉴 선택을 활성 경로에서 호출하지 않습니다. PoC7 공용 계량 장부에는 공급자·모델·작업·성공 여부·HTTP 코드·토큰 수만 기록하며, 발화·모델 응답·세션 ID는 보내지 않습니다. `PATH="$PWD/.runtime/bin:$PATH" npm run ai:usage`는 OpenRouter 계정 정보와 함께 공용 장부의 Groq 직접 호출 메타데이터를 보여 줍니다. PoC4와 Groq 키를 공유하므로 [Groq 계정 한도](https://console.groq.com/docs/rate-limits)가 여러 PoC 호출의 합계에 적용됩니다.

`smoke`는 실제 HTTP 경로에서 방문자·점주 흐름과 중복 주문·메뉴판 초안 승인을 확인하고 테스트 주문·초안을 정리합니다. 자동 Firefox에서는 500px·768px·1280px의 가로 넘침 없음과 기본 점주 로그인을 확인했습니다. 360–430px 실제 스마트폰과 팀원의 새로운 발화에 대한 블라인드 UAT는 남아 있습니다.

2026-09-28 현재 **Groq 무료 모델 경로의 32개 독립 대화·74턴**을 1번부터 연속 통과했습니다. 여기에 4인 가족의 아이 둘·어른 둘 배정, 키즈 메뉴 대체 질문에 대한 짧은 동의, “첫 번째 거 더 맵게” 번호 지목, 대화로 장바구니·주문 확정이 포함됩니다. 외부 모델을 끈 규칙 경로는 기존 27개·67턴과 **200개 독립 세션·1,000턴을 새 세션으로 3회** 통과했습니다. 이 3,000턴은 서버 상태·DB 메뉴·주문 안전의 회귀 검사이며 Groq 자유 발화 3,000턴을 의미하지 않습니다. 단위·데이터 테스트 70개, TypeScript, ESLint, 운영 빌드도 통과했습니다. 추가 Groq 그룹 주제 32개 평가에서는 앞의 7개·35턴만 통과했고, 8번째 대화에서 공유 조직의 200,000 TPD 소진으로 HTTP 429가 발생해 전체 시험은 미완료입니다. 한도가 회복되면 첫 사례부터 다시 실행해야 합니다.

2026-10-02에는 4인 조별 식사 요청에서 음료·사이드가 섞이던 오류를 수정했습니다. 현재 빌드에서 보고된 발화 2턴, 기존 가족 키즈 주문 2턴, 키즈 메뉴 대체 동의 2턴과 **Groq 핵심 10개 대화·28턴을 1번부터 다시** 통과했습니다. 규칙 경로는 27개·67턴 및 200개·1,000턴 × 3회를 다시 통과했고, 단위 테스트 73개와 운영 빌드·HTTP 스모크도 통과했습니다. 배포 뒤에도 홈페이지 프록시를 통해 같은 조별 식사 2턴을 다시 확인했습니다. 이전 음료 추천이 저장된 세션에서 정정 한 턴으로 식사 4개가 복구되는 것도 공개 경로에서 확인했습니다. 2026-09-28의 Groq 32개·74턴 수치는 그 당시 빌드의 이력이며 현재 빌드 전체 34개를 재검증했다는 뜻은 아닙니다.

평가용 로컬 서버는 `POC09_CONVERSATION_PROVIDER=rules` 또는 `groq`를 명시해 띄웁니다. 규칙 서버에서 `npm run multi:evaluate`, `npm run multi:stress -- --run=1`을 실행하고, Groq 서버에서 `npm run multi:evaluate -- --live-groq`를 실행합니다. 두 명령의 평가 헤더가 공급자 불일치를 감지하면 409로 중단합니다. `multi:stress -- --live-groq --group-only`는 실제 무료 호출을 하므로 계정의 일일 요청·토큰 한도에 맞춰 `--topic-start`와 `--topic-count`로 나눠 실행합니다. 테스트 세션·장바구니는 정상 종료 시 정리합니다. 실패와 수정 내역, 아직 남은 원자적 대화 상태·공용 키 예약·무료 모델 대량 평가 계획은 [공유 계획 11절](docs/PLAN.md)에 기록했습니다. 운영 장애는 `/api/health/` → PoC9 systemd → DB → 루트 프록시 순서로 확인합니다.

알레르기는 메뉴와 선택 옵션 **둘 다** `merchant_verified + excludes`일 때만 해당 알레르기 조건으로 추천·주문을 허용합니다. `contains`, `unknown`, AI 추정은 통과하지 않습니다. 엄격한 식사 조건과 맵기 상한도 자동으로 완화하지 않습니다. 최종 추천 카드는 메뉴 종류·커피/카페인 표시·수량·합계 예산을 서버에서 다시 검사하며, 맞는 메뉴가 없으면 다른 종류로 대체하지 않습니다. 주문 가격은 클라이언트 값을 받지 않고 DB 메뉴·옵션에서 계산하며, 확정 트랜잭션에서 재계산합니다. 중복 요청은 idempotency key로 같은 주문을 반환합니다. 로그인 없는 점주 API는 401, 출처가 다른 변경 요청은 403, 로그인 반복은 일시 제한합니다.
