# PoC 09 공유·실행 단일 계획 — ㅁㅁㅈ(뭐먹지?)

**상태 기준: 2026-09-27 · 구현 완료, 팀 기기 UAT 대기.** 이 문서 하나로 새 팀원이 최종 제품의 방향, 이번 PoC의 범위, 실제 구현·배포 위치, 검증 근거, 남은 팀 결정과 다음 작업을 파악할 수 있도록 유지한다. 제품 사용·설치·운영의 상세 절차는 루트 [README](../README.md)에 있다. 원 설계 입력은 사용자 제공 「ㅁㅁㅈ — AI 대화형 주문 플랫폼 Architecture & Codex Implementation Specification」이며, 이후 사용자가 **QR·RF/NFC·STT는 이번 개발에서 제외**하도록 범위를 조정했다.

## 1. 최종 목적과 이번 단계

**최종 목적:** **Tap · Talk · Together**. 매장에 온 손님이 먹고 가기/가져가기를 탭으로 정하고, 평소 말로 일행·취향·제약을 설명하며, 여러 차례 대화로 음식을 함께 골라 주문한다. 메뉴 목록은 참고용 보조 기능이다. 실제 매장의 검증된 메뉴와 옵션·가격·안전 정보를 확인해 주문한다. 사장님은 메뉴 정보를 책임지고 주문을 접수한다. 장기적으로는 QR/NFC 진입, 음성 입출력, 운영 시스템 연동까지 확장한다. 핵심 원칙은 **“말은 자유롭게, 거래는 엄격하게.”** AI는 사용자의 말을 구조화하고 검증된 결과를 설명할 수 있지만, 메뉴·가격·알레르기·총액·주문 확정은 DB와 서버 코드가 결정한다.

**이번 PoC의 검증 질문:** 텍스트 대화와 간단한 터치 화면만으로도 손님이 취향·일행 조건을 반영해 안전 규칙을 깨지 않고 주문을 완료하고, 사장님이 즉시 처리할 수 있는가. 따라서 이번 단계는 **한 개 가상 매장, 대화에서 파악하는 한 기기 그룹 주문, 서버 내부 다중 턴 기억, 구조화 LLM 해석과 실제 메뉴 후보 중 LLM 선택, 안전 규칙 fallback, 선택적 Jev, 메뉴판 초안, 모의 결제**까지 제공한다. QR 발행·태그, RF/NFC, STT·마이크, 실제 결제·POS, 계정 기반 고객 프로필은 포함하지 않는다. 일반 `?table=` URL은 후속 QR/NFC에서 그대로 쓸 수 있도록 이미 제공한다.

**현재 사용 가능한 공개 진입:** `https://www.minslab.kr/mmj` → `/poc/mwomeokji/`. 손님 화면 `/poc/mwomeokji/s/orange-table/`, 사장님 화면 `/poc/mwomeokji/merchant/`. README의 데모 계정 위치를 참고한다. 메뉴·알레르기 정보와 자동 입력된 사장님 계정은 **공개 가상 테스트 데이터**로, 실제 음식 안전성 주장이 아니다.

## 3. MinsLab 홈페이지에 맞춘 구조와 버전 판단

```text
minslab.kr/mmj
  → 기존 Python ASGI 홈페이지의 307 단축 주소
  → /poc/mwomeokji/*만 PoC9 전용 프록시
  → 127.0.0.1:18090 Next.js (basePath=/poc/mwomeokji)
      ├─ 손님 화면 /s/[storeSlug]
      ├─ 사장님 화면 /merchant
      ├─ Route Handler /api/*
      ├─ 추천·안전·주문 코드
      └─ Prisma → 127.0.0.1:18091 PostgreSQL 16
```

같은 도메인에서 동작한다는 이유로 구형 Node/Prisma에 맞추지 않는다. 홈페이지는 **경로 프록시**이며 PoC9 프로세스만 Node 24와 Next 16/Prisma 7을 사용한다. 이는 루트 Python 서비스와 PoC7/8의 의존성 충돌을 피하고, `/mmj`·PoC 카드·쿠키 경로·정적 파일을 같은 출처에서 유지한다. 현재 서버 기본 Node 18은 그대로다. `.runtime/bin/node`는 배포 호스트에서 `scripts/prepare-node24.sh`로 준비하며 커밋하지 않는다. PostgreSQL도 PoC9 전용 컨테이너/볼륨이고 다른 DB를 수정하지 않는다.

프록시는 손님·점주 쿠키 중 `poc09_*`만 전달하고, 변경 메서드와 최대 6 MB 이미지 업로드를 허용한다. Root `.env` 값 중 PoC9에 필요한 변수만 `scripts/with-root-env.mjs`가 전달한다. 쿠키와 API 키는 클라이언트 번들에 넣지 않는다. 부모 홈페이지가 PoC9에 연결할 수 없으면 해당 경로만 503으로 실패한다. 운영 유닛·포트·백업·재시작 명령은 README에 있다.

## 4. 서비스 사용자 여정과 계약

### 손님 — 제품의 기본 경로

매장 방문 → **먹고 가기 / 가져가기** 중 하나 탭 → “우리 3명인데 한 명은 채식, 한 명은 매운 걸 못 먹어”처럼 입력 → 서버가 인원과 일행별 조건을 대화 맥락으로 저장하고 부족한 정보는 다시 질문 → 검증된 실메뉴를 사람별로 추천 → “추천한 거 전부 담아줘”, “첫 번째 담아줘”, “다른 거” 같은 후속 발화 → 옵션이 필요하면 검증된 기본 옵션을 선택하고 주문 전 재검증 → “주문할게”와 확인 대화 또는 장바구니 버튼 → 모의 결제 → 식사 방식이 적힌 주문을 사장님 화면에서 처리. 화면에서 멤버를 일일이 추가하는 입력란은 없다. 스마트폰 음성 키보드로 입력한 문자도 같은 대화 API로 들어간다. 앱 자체 STT/음성 출력은 이번 범위에서 제외한다.

알레르기·식이·큰 글씨 설정 패널, 추천 카드 상세, 장바구니, 내역, 직원 호출은 필요한 순간의 보조 조작이다. **전체 메뉴 참고**는 후순위 링크로만 제공한다. 인식되지 않는 말이나 후보가 없는 조건은 임의로 확정하지 않고 재질문·직원 호출로 연결한다. `?table=A1`은 미래 QR 진입 호환용이며 손님 화면에서 테이블 선택을 요구하지 않는다.

### 사장님

자동 입력된 공개 테스트 계정으로 별도 로그인 → 새 주문의 먹고 가기/가져가기·선택된 테이블·요청 사항 확인 → 접수·조리·완료 상태 변경 → 직원 호출 처리. 메뉴명·가격·재료·식이 태그·알레르기 상태·공개/품절·옵션과 추가금을 관리한다. 텍스트 또는 설정된 AI 이미지 읽기로 메뉴판을 초안화하지만, 점주가 재료와 10개 알레르기 항목을 확인하기 전에는 공개할 수 없다.

### 실제 API 경계

- `GET /api/bootstrap/`, `/api/cart/`, `/api/orders/`, `/api/health/`: 가상 매장/메뉴·내 장바구니·내 주문·DB 상태.
- `POST /api/visit/`, `/api/profile/`, `/api/conversation/`, `/api/cart/`, `/api/checkout/`, `/api/help/`: 식사 방식, 현재 세션 조건, 다중 발화 추천·지시어 주문, 장바구니, 모의 주문, 직원 호출. 장바구니 수량은 `PATCH`, 삭제는 `DELETE`.
- `/api/merchant/login/`, `/dashboard/`, `/menu/`, `/import/`, `/orders/:id/`, `/help/:id/`: 점주 전용 메뉴·옵션·초안·주문·호출.
- API 응답의 메뉴명·옵션·금액은 항상 DB 값이다. 클라이언트가 보낸 총액은 받지 않는다. 주문은 트랜잭션에서 최신 값으로 확정하고 같은 idempotency key에는 같은 주문을 반환한다.

핵심 데이터 모델은 `Store`, `StoreTable`, `MenuCategory`, `MenuItem`, `MenuOptionGroup`, `MenuOption`, 메뉴/옵션 알레르기 검증, `GuestSession`, `CartItem`, `Order`/`OrderLine`, `HelpRequest`, `MerchantSession`이다. 주문 행은 메뉴명·옵션명·단가·합계를 스냅샷으로 보존한다. 원문 대화나 카드정보는 DB에 저장하지 않는다. `GuestSession.context.dialogue`에는 파악한 인원·조건·마지막 추천 ID·주문 확인 상태만, `Order.fulfillmentType`에는 식사 방식을 저장한다.

### 다중 턴 해석의 데이터 경계와 활성화 상태

스마트폰 자체 음성 키보드의 결과와 타이핑 문장은 `POST /api/conversation/`의 동일한 `message`로 처리한다. 서버는 세션에 인원, 일행별 채식·알레르기·맵기, 예산, 마지막 추천 ID와 주문 확인 상태를 구조화해 보관한다. 한 턴에서 새로 추출한 정보만 여기에 합치고 “한 명 더 왔어”, “민수는 채식”, “두 번째 담아줘”, “그거 말고”처럼 이전 턴을 가리키는 말은 **서버 안에서** 해석한다. 원문 대화 이력·장바구니·추천 목록·알레르기 목록을 LLM 요청에 넣지 않는다. 이름 없는 대명사가 여러 사람을 가리킬 수 있으면 다시 묻는다.

OpenRouter 호출은 현재 문장 하나에 한정하고 `json_schema` 엄격 응답, `require_parameters`, `zdr`, `data_collection: deny`로 제한한다. 응답은 Zod로 검증한 뒤 서버의 안전·가격 검증을 통과해야 한다. 가상 문장을 이용한 모델 실호출, 공개 HTTPS 2턴 실호출, 활성 LLM 상태의 전체 주문 스모크와 네트워크 없는 단위 테스트는 통과했다. 자동 승인 검토 이후 사용자가 **현재 발화 한 개의 OpenRouter 전송**을 명시적으로 승인했다. 대화 전용 `POC09_CONVERSATION_PROVIDER=openrouter`로 운영하고 메뉴판 이미지용 `POC09_AI_PROVIDER=mock`은 별도로 유지한다. 모델 장애 시 규칙 해석으로 돌아간다. 매 호출의 모델·상태·토큰 메타데이터만 PoC7 공용 장부에 기록하며 발화 원문과 응답·세션 ID는 기록하지 않는다.

## 5. 안전·AI 판단 순서

1. 현재 공개 모드는 OpenRouter LLM이며 **현재 발화 한 개만** 구조화된 의도로 바꾼다. 오류가 나면 Rules 파서로 돌아간다. 이전 대화·알레르기·장바구니 전체를 외부로 보내지 않는다. LLM은 실제 메뉴 사실이나 안전 여부를 만들거나 판정하지 않으며, 서버가 검증한 후보의 ID만 고른다.
2. 코드가 DB의 실제 게시·판매 메뉴만 로드한다. 알레르기별 메뉴와 선택 옵션에 `merchant_verified + excludes`가 없으면 해당 조건의 추천·주문에서 제외한다. `contains`, `unknown`, AI 추정은 통과하지 않는다. 엄격 식이조건과 맵기 상한, 예산도 같은 단계에서 검사한다. 서버가 명시된 메뉴 종류·커피 여부·카페인 표시·잔 수·총예산을 마지막 추천 결과와 다시 대조한다. 불일치한 제안은 내보내지 않는다.
3. 서버가 검증된 실제 후보를 넓게 생성한다(한 사람 최대 60개, 그룹 전체·메뉴 종류별 조합 최대 14개). 선택적 Jev는 앞선 후보 ID의 순위만 조정한다. 활성 OpenRouter 메뉴 선택 LLM은 **현재 발화와 공개 메뉴 사실만** 보고 후보 ID를 고른다. 명시적으로 요청한 음식이 후보에 없으면 높은 신뢰도의 `no_match`만 허용한다. 외부 호출 실패·형식 오류·낮은 신뢰도는 Rules 첫 후보로 돌아가며, 없는 메뉴 ID는 무시한다. 선택 결과를 2단계 제약으로 다시 검사한다.
4. 옵션 선택·장바구니와 주문 확정에서 안전과 가격을 다시 검사한다. 그룹 주문은 각 멤버 조건을 합쳐 검사하고 전체 예산 안에서 조합한다.
5. 실매장에서는 재료뿐 아니라 제조·교차 접촉을 점주가 확인해야 한다. 현 seed의 검증 상태는 자동 생성된 가상 데이터이며 법적 안전 보증이 아니다.

**2026-09-24 실제 사용자 대화 오류 수정:** “2살 아이·와이프·나”를 세 명으로 인식하고, “나는 매운 것 / 아이는 맵지 않고 달달한 키즈 / 와이프는 국물”을 사람별 취향으로 저장한다. 취향을 설명하며 끝에 “주문해줘”라고 말한 요청은 메뉴 선택으로 해석한다. 이어 “추천한 거 전부 주문해줘”로 담고, 장바구니 확인 뒤 명시적 주문 확정으로 진행한다. 가상 키즈 메뉴 1개를 seed에 추가했다. 실제 매장에 키즈 메뉴가 없거나 조건에 맞지 않으면 임의의 일반 메뉴로 대체하지 않고 질문한다. 2살에게 적합한 재료·식감은 보호자와 점주가 확인해야 한다. 이 경로는 규칙 fallback 회귀 테스트와 공개 HTTPS의 실제 OpenRouter 대화로 검증했다.

**후속 대화 품질 수정:** 첫 가족 추천 뒤 “와이프꺼는 더 얼큰한걸로 보여줘”를 와이프의 국물 취향 변경으로 적용하고, 이어지는 “알러지는 없고 얼큰한걸로”도 직전 와이프 메뉴의 추가 설명으로 처리한다. 저장된 3명이라는 숫자만으로 새 발화를 인원 확인으로 오판하지 않는다. 변경된 추천에서도 다른 두 사람의 조건과 전체 장바구니 흐름을 유지한다. 가상 성인 세 명의 공개 HTTPS 3턴 대화에서도 특정 손님만 순한 수프에서 얼큰한 수프로 바뀌고 다른 두 추천은 유지됨을 확인했다.

**재방문 세션 수정:** 채팅 화면 문장이 새로 시작해도 서버 대화 조건은 남아, 사용자가 가족의 한 끼를 다시 자세히 설명할 때 오래된 채식·예산·다른 일행 정보가 섞여 메뉴가 없어질 수 있었다. 전체 식사 설명이 다시 들어오면 이전 메뉴 취향·예산·익명 일행을 교체하고, 같은 이름의 알레르기·엄격한 식사 조건 및 별도로 저장한 내 취향은 보존한다. 새 일행에 연결할 수 없는 이전 알레르기는 누락하지 않고 이번 주문의 공통 제한으로 보존한다. 저장된 내 취향 때문에 결과가 비면 적용 중인 제한을 답변에 표시한다. 재방문 상태를 만든 회귀 테스트 25개와 가상 성인 일행의 공개 HTTPS 재방문 검증, 전체 주문 스모크를 통과했다.

**연속 대체 추천 수정 (2026-09-24):** 첫 대화에서 한 사람의 순한 국물을 고른 뒤 “더 얼큰하게” 요청하면 그 사람의 순한 맛과 맵기 상한을 매운맛으로 교체한다. 이어 “아니면 덮밥류로” 요청하면 직전 사람의 국물 조건을 덮밥으로 바꾸되 얼큰한 맛과 다른 일행의 추천은 유지한다. 갑각류 제한으로 해물 수프가 제외되어도 선택 가능한 가상 얼큰 닭고기 수프·덮밥 2개를 seed에 추가했다(총 22개 메뉴). 실제 매장에서는 점주가 메뉴별 재료와 알레르기 정보를 직접 검증해야 한다. 제한 때문에 후보가 없으면 적용 중인 알레르기 종류를 보여주며, 사용자가 “알러지는 없어”라고 명시한 경우에만 공통 프로필의 알레르기를 지운다. 특정 일행에게 붙은 알레르기는 유지한다. 도메인 회귀 테스트 29개, 타입 검사, 린트, 빌드, 전체 HTTP 스모크가 통과했다. 실제 OpenRouter를 사용하는 **가상의 성인 3명** 공개 서비스 4턴 대화에서 갑각류 제한 유지 → 순한 국물 → 얼큰 닭고기 수프 → 얼큰 닭고기 덮밥 → 명시적 공통 알레르기 해제를 확인했다. 실제 사용자 세션의 제한 정보는 조회하지 않았다.

**재료 확인·주문 확정 대화 수정 (2026-09-24):** “내꺼에 오이가 들어갔는지 확인해봐”는 LLM의 질문 되풀이를 그대로 응답하지 않고, 서버가 직전 추천 또는 장바구니의 `나` 메뉴를 찾는다. 메뉴의 등록 재료와 선택한 옵션만 확인하며, 목록에 없는 일반 재료는 미포함으로 단정하지 않고 점주 확인이 필요하다고 안내한다. 본인 메뉴를 특정할 수 없거나 여러 개면 이름·추천 번호를 되묻는다. 이 조회는 LLM을 호출하지 않고 직전 추천 상태도 지우지 않는다. 빈 장바구니에서 완성된 일행별 추천 직후 “주문해줘”라고 말하면 각 메뉴를 안전 검증 후 담고 합계·모의 결제 확인을 요청한다. “응” 이후에만 최종 주문을 접수한다. 혼자 여러 후보를 받은 경우에는 자동으로 전부 담지 않고 메뉴 선택을 묻는다. 가상 성인 2명 API 대화에서 재료 확인 → 추천 2개 담기 → 명시적 최종 확인을 재현했다. 단위 테스트 34개와 타입 검사·린트·빌드·HTTP 스모크가 통과했다.

**2026-09-27 구현·합성 평가:** 이름이 있는 가상 성인 3명의 개별 취향을 규칙 fallback에서도 분리하고, 후속 얼큰한 국물·덮밥 변경이 다른 사람의 선택에 영향을 주지 않게 했다. `npm run ai:evaluate -- --both`는 합성 발화 6턴의 14개 기대 조건에서 Rules와 OpenRouter가 각각 14/14를 통과했다. OpenRouter 평균 2,674ms, p95 3,259ms, 입력 6,054·출력 990토큰, 제공자 보고 비용 $0.004006, fallback 0턴이었다. 작은 고정 세트이므로 실제 사용자 발화의 정확도 보증은 아니다. 외부에는 가상 성인 발화만 보냈다.

선택적 Jev는 [OpenRouter Decisions API](https://openrouter.ai/blog/tutorials/how-to-use-jev/)로 수정했다. `npm run decision:evaluate -- --live`의 가상 후보 3개 평가에서 Jev가 536ms, 입력 438·출력 52토큰, $0.000018396으로 응답했다. 코드가 확인된 메뉴 ID 집합만 재정렬하며 낮은 신뢰도·형식 오류·API 실패는 Rules 순위로 돌아간다. 기본 운영 설정은 계속 `POC09_DECISION_PROVIDER=rules`다. 대화 해석, 메뉴 선택, Jev, 선택적 이미지 메뉴판의 호출 상태·토큰·비용은 동일한 PoC7 장부에 `order_interpretation`/`order_selection`/`order_ranking`/`menu_import` 작업명으로 기록한다. 장부에는 원문·응답·세션 ID·이미지를 보내지 않는다.

**2026-09-27 최종 추천 검증 추가:** “카페인 없는 커피 2잔, 1만원 이하”처럼 여러 필수 조건을 말한 경우, 규칙 추천과 선택적 AI 정렬을 거친 **최종 카드 전체**를 서버에서 다시 검사한다. `2잔`은 손님 2명이 아닌 수량이고, 2잔 합계가 예산 이하여야 한다. 이 데모 매장에는 카페인 없음으로 점주가 표시한 커피가 없어 추천 0개와 명확한 안내를 반환한다. 오렌지 에이드·감자튀김·일반 커피·디카페인을 임의 대체하지 않는다. 디카페인으로 범위를 넓히려면 손님의 명시적 정정이 필요하다. 점주 메뉴 편집기에 일반 커피/디카페인/카페인 없음 확인 필드를 추가했고, 카테고리 태그는 서버가 정규화한다. 가상 발화의 실제 HTTP 스모크와 42개 도메인 테스트로 확인했다. 카페인 표시의 진실성은 실제 점주가 원료·제조 과정을 확인할 책임이 있다.

**2026-09-27 연속 범위 변경 수정:** 첫 요청이 “카페인 없는 커피”였더라도 다음 요청에서 “카페인 없는 음료”로 넓히면 커피 제한만 해제한다. 카페인 없음·2잔·전체 예산 1만원은 유지한다. 가상 오렌지 에이드·생수·달콤 사과 주스에 `caffeine_free` 테스트 태그를 두었다. 합성 대화의 공개 경로에서 첫 턴은 커피 추천 0개, 두 번째 턴은 오렌지 에이드 2잔/9,000원, 세 번째 턴은 장바구니 수량 2·합계 9,000원을 확인했다. 실제 매장에서는 점주가 원료와 제조 내용을 확인한 뒤 표시해야 한다.

**2026-09-27 단맛·신맛 후속 발화 수정:** “신거 말고 달달한거로”를 장바구니 삭제가 아닌 추천 조건 변경으로 처리한다. 서버는 기존 카페인 없음·2잔·1만원을 유지하고 달콤한 맛을 필수 조건으로, 신맛을 제외 조건으로 추가한다. 가상 메뉴에 달콤 사과 주스 4,500원(카페인 없음·달콤함 표시)을 더해 현재 23개 메뉴다. 생수는 달콤한 맛 조건에 맞지 않아 추천되지 않는다. 모델이 요청 문장을 되풀이하는 clarification을 반환해도, 서버에서 조건이 명확하면 최종 추천 검증을 계속한다. 이유 문구와 “2잔을 담을게요” 조사도 수정했다. 가상의 다중 턴 HTTP 스모크는 사과 주스 2잔/9,000원 추천·담기를 통과했고, 도메인 테스트 44개가 통과했다. 점주 화면에서 커피 여부와 카페인 표시를 분리하고 달콤함·새콤함을 편집할 수 있다.


**2026-09-27 메뉴 선택 책임 변경:** 사용자가 지적한 대로 규칙 점수만으로 음식을 최종 결정하면 자연어의 새로운 취향을 계속 조건식으로 추가하게 된다. 서버는 판매·안전·가격·수량·명시된 종류와 다중 턴 누적 제한만 후보 생성에 사용하고, OpenRouter LLM이 현재 발화와 공개 메뉴 이름·설명·가격·태그에서 최종 메뉴 ID를 고른다. 예를 들어 기존 규칙 1순위가 오렌지 음료라도 “사과 맛”이라는 새 선호가 있으면 실제 사과 주스를 선택한다. 특정 블루베리 스무디처럼 후보에 없는 음식을 명시하면 높은 신뢰도의 `no_match`를 허용한다. “무카페인 음료”처럼 넓은 요청은 서버가 후보의 확인된 카페인 표시를 먼저 검증하고, LLM이 존재하는 음료를 고른다. 한 번의 선택에 세션 식별자·이전 대화·저장된 개인 조건·일행 이름은 보내지 않는다. 저장된 조건은 서버가 후보 단계에서만 적용한다. 모델이 오답을 내거나 장애가 나면 기존 Rules 첫 후보로 돌아갈 수 있으므로 팀 UAT에서는 추천 적합성과 `menuSelectionProvider`를 함께 기록한다. 선택된 ID는 카드 표시 전 `validateRecommendationResult`로 재검사한다. 실제 HTTP 주문 스모크, 50개 도메인 테스트, 합성 실 LLM 평가 3개(사과 선택·폭넓은 무카페인 선택·없는 블루베리 거절)가 통과했다. 메뉴 선택 호출은 공용 장부 `order_selection`으로 집계한다.


**2026-09-27 이전 예산 누수 수정:** 재방문 세션에 예산 10,000원이 남아 있을 때 “남자 4명인데 양이 많아서 든든히 먹을 수 있는 메뉴로 추천해줘”를 새 식사 요청으로 인식하지 못해 4인 전체 예산을 10,000원으로 제한했다. 새 일행 수와 식사 추천을 함께 설명하면 이전 대화의 예산·메뉴 종류·수량·추천 ID를 초기화한다. 모의 주문이 완료된 때에도 다음 주문으로 일회성 예산·추천이 넘어가지 않도록 대화 상태를 초기화한다. 이번 문장에 새 예산이 있으면 그것만 적용하며, “그럼 다른 메뉴로” 같은 짧은 후속 요청은 조건을 이어간다. 저장한 알레르기와 엄격 식이 조건은 기존 안전 정책대로 보존한다. 실제 홈페이지 프록시의 HTTP 스모크에서 1만원 예산 요청 직후 새 4인 식사 요청의 예산 표시가 사라지고 1만원을 넘는 4인 메뉴가 추천되는 것을 확인했고, 도메인 테스트 50개가 통과했다.


### 10개 독립 다중 턴 평가 (2026-09-27)

`scripts/evaluate-multiturn.ts`를 `npm run multi:evaluate`로 실행한다. 가상 문장만 PoC9 HTTP API와 활성 OpenRouter에 보내고, 각 사례마다 새 방문 세션을 만든다. **1번부터 순서대로 실행하고 첫 불일치에서 중단한다. 수정 뒤에는 반드시 1번부터 다시 실행한다.** 반환 메뉴가 현재 공개·판매 목록에 있고 합계가 누적 예산 안에 드는지 모든 턴에 공통 검사를 적용한다. 평가 종료 시 이 스크립트가 만든 게스트 세션과 장바구니를 삭제하며, 공용 AI 계량에는 호출 메타데이터만 남는다.

| 사례 | 멀티 턴 조건과 통과 기준 | 최종 |
| --- | --- | --- |

**발견·수정 후 처음부터 재실행한 오류:** 그룹 후보가 인기순 혼합 조합에 치우쳐 든든한 4인 식사에 음료·사이드가 섞였다. 식사/음료/사이드별 완전한 그룹 조합을 후보에 포함하고 LLM이 선택하게 했다. 알레르기 선언의 “있어”를 재료 질문으로 오인한 경계와, 조건만 말한 턴에 메뉴를 성급히 추천한 경계도 수정했다. “다른 매운 덮밥”의 직전 메뉴 제외가 누락된 점을 보완했다. **가장 중요한 발견은 새 게스트가 가변 기본 프로필 객체를 공유하여 한 테스트 손님의 땅콩 제한이 다른 손님에게 보일 수 있었던 점**이다. 새 프로필 인스턴스를 세션마다 생성하도록 수정하고 사례 10과 단위 테스트로 격리를 확인했다. 보조 파서가 “예산 제한은 없어”의 “제한”을 사람으로 만든 점은 문장 경계를 적용하고 정상 LLM 응답에 규칙 보조 인물 목록을 덧붙이지 않도록 수정했다. 마지막으로 LLM의 문장 요약 `clarification`이 명시적인 무카페인 음료 추천을 가로챈 사례를 발견해, 명확한 추천 요청을 계속 처리하도록 수정했다.

**최종 재검증:** 실제 홈페이지 프록시를 통한 10/10 사례·28/28턴, 기존 손님/사장님 `npm run smoke`, 도메인 테스트 54/54, `typecheck`, `lint`, 운영 `build` 통과. 모델 응답은 매번 같지 않을 수 있으므로 테스트는 고정 메뉴 순서가 아니라 요청 의미와 안전·가격 불변 조건을 검사한다.

열린 결정은 **실제 데모 매장과 검증 책임자**, 발표일·기기, OpenRouter 운영 비용과 다음 키 한도, 이미지 자동 인식의 발표 포함, 실제 메뉴 데이터 도입 시 법무·운영 검토, 전체 영어 UI 우선순위다. 공개 데모 계정은 가상 매장 내부 테스트 전용이며 로그인 화면에 자동 입력한다. 실제 매장 연결 전에는 데모 계정을 제거하고 점주별 권한과 비밀 인증을 도입한다. 팀 작업은 `poc9/<작업명>` 브랜치와 작은 PR로 남긴다. 가격·알레르기·주문 로직 변경은 도메인·제품 담당이 함께 검토하고, 마이그레이션에는 되돌리기 계획을 적는다.

## 8. 시연·완료 기준

**기본 시연:** 손님이 **가져가기** 선택 → “우리 3명인데 한 명은 채식하고 한 명은 매운 걸 못 먹어” → “따뜻한 거 4만원 안에서 추천해줘” → 개인별 추천 확인 → “추천한 거 전부 담아줘” → “주문할게”, “응” → 모의 결제 → 사장님 화면에서 기본 입력된 데모 계정으로 로그인하고 **가져가기** 주문을 접수. 이어서 알레르기 있는 손님의 추천 차단, 직원 호출과 메뉴판 초안 검토·공개를 보여준다. 대화·주문·점주 흐름은 자동 HTTP 및 Firefox 브라우저 검증을 통과했다.

**내부 테스트 종료 조건:** 팀원이 같은 흐름을 모바일·태블릿·PC에서 완주하고, 알레르기/엄격 식이/품절/옵션/가격 변경/중복 요청으로 잘못된 주문이 생성되지 않으며, 점주가 메뉴와 주문을 독립적으로 관리하고, 루트 홈페이지의 다른 PoC가 정상 동작한다. 실제 매장 도입 조건은 별도이며 가상 seed를 실재 알레르기 데이터로 간주하지 않는다.
