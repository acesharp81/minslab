# PoC 09 공유·실행 단일 계획 — ㅁㅁㅈ(뭐먹지?)

**상태 기준: 2026-09-24 · 내부 기능 테스트 단계.** 이 문서 하나로 새 팀원이 최종 제품의 방향, 이번 PoC의 범위, 실제 구현·배포 위치, 검증 근거, 남은 팀 결정과 다음 작업을 파악할 수 있도록 유지한다. 제품 사용·설치·운영의 상세 절차는 루트 [README](../README.md)에 있다. 원 설계 입력은 사용자 제공 「ㅁㅁㅈ — AI 대화형 주문 플랫폼 Architecture & Codex Implementation Specification」이며, 이후 사용자가 **QR·RF/NFC·STT는 이번 개발에서 제외**하도록 범위를 조정했다.

## 1. 최종 목적과 이번 단계

**최종 목적:** **Tap · Talk · Together**. 매장에 온 손님이 먹고 가기/가져가기를 탭으로 정하고, 평소 말로 일행·취향·제약을 설명하며, 여러 차례 대화로 음식을 함께 골라 주문한다. 메뉴 목록은 참고용 보조 기능이다. 실제 매장의 검증된 메뉴와 옵션·가격·안전 정보를 확인해 주문한다. 사장님은 메뉴 정보를 책임지고 주문을 접수한다. 장기적으로는 QR/NFC 진입, 음성 입출력, 운영 시스템 연동까지 확장한다. 핵심 원칙은 **“말은 자유롭게, 거래는 엄격하게.”** AI는 사용자의 말을 구조화하고 검증된 결과를 설명할 수 있지만, 메뉴·가격·알레르기·총액·주문 확정은 DB와 서버 코드가 결정한다.

**이번 PoC의 검증 질문:** 텍스트 대화와 간단한 터치 화면만으로도 손님이 취향·일행 조건을 반영해 안전 규칙을 깨지 않고 주문을 완료하고, 사장님이 즉시 처리할 수 있는가. 따라서 이번 단계는 **한 개 가상 매장, 대화에서 파악하는 한 기기 그룹 주문, 서버 내부 다중 턴 기억, 구조화 LLM 해석기와 규칙 추천, 선택적 Jev, 메뉴판 초안, 모의 결제**까지 제공한다. QR 발행·태그, RF/NFC, STT·마이크, 실제 결제·POS, 계정 기반 고객 프로필은 포함하지 않는다. 일반 `?table=` URL은 후속 QR/NFC에서 그대로 쓸 수 있도록 이미 제공한다.

**현재 사용 가능한 공개 진입:** `https://www.minslab.kr/mmj` → `/poc/mwomeokji/`. 손님 화면 `/poc/mwomeokji/s/orange-table/`, 사장님 화면 `/poc/mwomeokji/merchant/`. README의 데모 계정 위치를 참고한다. 메뉴·알레르기 정보와 자동 입력된 사장님 계정은 **공개 가상 테스트 데이터**로, 실제 음식 안전성 주장이 아니다.

## 3. MinsLab 홈페이지에 맞춘 구조와 버전 판단

```text
minslab.kr/mmj
  → 기존 Python ASGI 홈페이지의 307 단축 주소
  → /poc/mwomeokji/*만 PoC9 전용 프록시
  → 127.0.0.1:18090 Next.js (basePath=/poc/mwomeokji)
      ├─ 손님 화면 /s/[storeSlug]
      ├─ 사장님 화면 /merchant
      ├─ Route Handler /api/*
      ├─ 추천·안전·주문 코드
      └─ Prisma → 127.0.0.1:18091 PostgreSQL 16
```

같은 도메인에서 동작한다는 이유로 구형 Node/Prisma에 맞추지 않는다. 홈페이지는 **경로 프록시**이며 PoC9 프로세스만 Node 24와 Next 16/Prisma 7을 사용한다. 이는 루트 Python 서비스와 PoC7/8의 의존성 충돌을 피하고, `/mmj`·PoC 카드·쿠키 경로·정적 파일을 같은 출처에서 유지한다. 현재 서버 기본 Node 18은 그대로다. `.runtime/bin/node`는 배포 호스트에서 `scripts/prepare-node24.sh`로 준비하며 커밋하지 않는다. PostgreSQL도 PoC9 전용 컨테이너/볼륨이고 다른 DB를 수정하지 않는다.

프록시는 손님·점주 쿠키 중 `poc09_*`만 전달하고, 변경 메서드와 최대 6 MB 이미지 업로드를 허용한다. Root `.env` 값 중 PoC9에 필요한 변수만 `scripts/with-root-env.mjs`가 전달한다. 쿠키와 API 키는 클라이언트 번들에 넣지 않는다. 부모 홈페이지가 PoC9에 연결할 수 없으면 해당 경로만 503으로 실패한다. 운영 유닛·포트·백업·재시작 명령은 README에 있다.

## 4. 서비스 사용자 여정과 계약

### 손님 — 제품의 기본 경로

매장 방문 → **먹고 가기 / 가져가기** 중 하나 탭 → “우리 3명인데 한 명은 채식, 한 명은 매운 걸 못 먹어”처럼 입력 → 서버가 인원과 일행별 조건을 대화 맥락으로 저장하고 부족한 정보는 다시 질문 → 검증된 실메뉴를 사람별로 추천 → “추천한 거 전부 담아줘”, “첫 번째 담아줘”, “다른 거” 같은 후속 발화 → 옵션이 필요하면 검증된 기본 옵션을 선택하고 주문 전 재검증 → “주문할게”와 확인 대화 또는 장바구니 버튼 → 모의 결제 → 식사 방식이 적힌 주문을 사장님 화면에서 처리. 화면에서 멤버를 일일이 추가하는 입력란은 없다. 스마트폰 음성 키보드로 입력한 문자도 같은 대화 API로 들어간다. 앱 자체 STT/음성 출력은 이번 범위에서 제외한다.

알레르기·식이·큰 글씨 설정 패널, 추천 카드 상세, 장바구니, 내역, 직원 호출은 필요한 순간의 보조 조작이다. **전체 메뉴 참고**는 후순위 링크로만 제공한다. 인식되지 않는 말이나 후보가 없는 조건은 임의로 확정하지 않고 재질문·직원 호출로 연결한다. `?table=A1`은 미래 QR 진입 호환용이며 손님 화면에서 테이블 선택을 요구하지 않는다.

### 사장님

자동 입력된 공개 테스트 계정으로 별도 로그인 → 새 주문의 먹고 가기/가져가기·선택된 테이블·요청 사항 확인 → 접수·조리·완료 상태 변경 → 직원 호출 처리. 메뉴명·가격·재료·식이 태그·알레르기 상태·공개/품절·옵션과 추가금을 관리한다. 텍스트 또는 설정된 AI 이미지 읽기로 메뉴판을 초안화하지만, 점주가 재료와 10개 알레르기 항목을 확인하기 전에는 공개할 수 없다.

### 실제 API 경계

- `GET /api/bootstrap/`, `/api/cart/`, `/api/orders/`, `/api/health/`: 가상 매장/메뉴·내 장바구니·내 주문·DB 상태.
- `POST /api/visit/`, `/api/profile/`, `/api/conversation/`, `/api/cart/`, `/api/checkout/`, `/api/help/`: 식사 방식, 현재 세션 조건, 다중 발화 추천·지시어 주문, 장바구니, 모의 주문, 직원 호출. 장바구니 수량은 `PATCH`, 삭제는 `DELETE`.
- `/api/merchant/login/`, `/dashboard/`, `/menu/`, `/import/`, `/orders/:id/`, `/help/:id/`: 점주 전용 메뉴·옵션·초안·주문·호출.
- API 응답의 메뉴명·옵션·금액은 항상 DB 값이다. 클라이언트가 보낸 총액은 받지 않는다. 주문은 트랜잭션에서 최신 값으로 확정하고 같은 idempotency key에는 같은 주문을 반환한다.

핵심 데이터 모델은 `Store`, `StoreTable`, `MenuCategory`, `MenuItem`, `MenuOptionGroup`, `MenuOption`, 메뉴/옵션 알레르기 검증, `GuestSession`, `CartItem`, `Order`/`OrderLine`, `HelpRequest`, `MerchantSession`이다. 주문 행은 메뉴명·옵션명·단가·합계를 스냅샷으로 보존한다. 원문 대화나 카드정보는 DB에 저장하지 않는다. `GuestSession.context.dialogue`에는 파악한 인원·조건·마지막 추천 ID·주문 확인 상태만, `Order.fulfillmentType`에는 식사 방식을 저장한다.

### 다중 턴 해석의 데이터 경계와 활성화 상태

스마트폰 자체 음성 키보드의 결과와 타이핑 문장은 `POST /api/conversation/`의 동일한 `message`로 처리한다. 서버는 세션에 인원, 일행별 채식·알레르기·맵기, 예산, 마지막 추천 ID와 주문 확인 상태를 구조화해 보관한다. 한 턴에서 새로 추출한 정보만 여기에 합치고 “한 명 더 왔어”, “민수는 채식”, “두 번째 담아줘”, “그거 말고”처럼 이전 턴을 가리키는 말은 **서버 안에서** 해석한다. 원문 대화 이력·장바구니·추천 목록·알레르기 목록을 LLM 요청에 넣지 않는다. 이름 없는 대명사가 여러 사람을 가리킬 수 있으면 다시 묻는다.

OpenRouter 호출은 현재 문장 하나에 한정하고 `json_schema` 엄격 응답, `require_parameters`, `zdr`, `data_collection: deny`로 제한한다. 응답은 Zod로 검증한 뒤 서버의 안전·가격 검증을 통과해야 한다. 가상 문장을 이용한 모델 실호출, 공개 HTTPS 2턴 실호출, 활성 LLM 상태의 전체 주문 스모크와 네트워크 없는 단위 테스트는 통과했다. 자동 승인 검토 이후 사용자가 **현재 발화 한 개의 OpenRouter 전송**을 명시적으로 승인했다. 대화 전용 `POC09_CONVERSATION_PROVIDER=openrouter`로 운영하고 메뉴판 이미지용 `POC09_AI_PROVIDER=mock`은 별도로 유지한다. 모델 장애 시 규칙 해석으로 돌아간다. 매 호출의 모델·상태·토큰 메타데이터만 PoC7 공용 장부에 기록하며 발화 원문과 응답·세션 ID는 기록하지 않는다.

## 5. 안전·AI 판단 순서

1. 현재 공개 모드는 OpenRouter LLM이며 **현재 발화 한 개만** 구조화된 의도로 바꾼다. 오류가 나면 Rules 파서로 돌아간다. 이전 대화·알레르기·장바구니 전체를 외부로 보내지 않는다. LLM이 메뉴 사실이나 안전 여부를 결정하지 않는다.
2. 코드가 DB의 실제 게시·판매 메뉴만 로드한다. 알레르기별 메뉴와 선택 옵션에 `merchant_verified + excludes`가 없으면 해당 조건의 추천·주문에서 제외한다. `contains`, `unknown`, AI 추정은 통과하지 않는다. 엄격 식이조건과 맵기 상한, 예산도 같은 단계에서 검사한다.
3. Rules 점수가 남은 후보를 정렬한다. 선택적 Jev는 후보 **ID의 순서**만 바꿀 수 있다. 존재하지 않는 ID, 중복, 낮은 신뢰도, 시간 초과, API 오류는 무시하고 Rules 결과를 쓴다.
4. 옵션 선택·장바구니와 주문 확정에서 안전과 가격을 다시 검사한다. 그룹 주문은 각 멤버 조건을 합쳐 검사하고 전체 예산 안에서 조합한다.
5. 실매장에서는 재료뿐 아니라 제조·교차 접촉을 점주가 확인해야 한다. 현 seed의 검증 상태는 자동 생성된 가상 데이터이며 법적 안전 보증이 아니다.

**2026-09-24 실제 사용자 대화 오류 수정:** “2살 아이·와이프·나”를 세 명으로 인식하고, “나는 매운 것 / 아이는 맵지 않고 달달한 키즈 / 와이프는 국물”을 사람별 취향으로 저장한다. 취향을 설명하며 끝에 “주문해줘”라고 말한 요청은 메뉴 선택으로 해석한다. 이어 “추천한 거 전부 주문해줘”로 담고, 장바구니 확인 뒤 명시적 주문 확정으로 진행한다. 가상 키즈 메뉴 1개를 seed에 추가했다. 실제 매장에 키즈 메뉴가 없거나 조건에 맞지 않으면 임의의 일반 메뉴로 대체하지 않고 질문한다. 2살에게 적합한 재료·식감은 보호자와 점주가 확인해야 한다. 이 경로는 규칙 fallback 회귀 테스트와 공개 HTTPS의 실제 OpenRouter 대화로 검증했다.

**후속 대화 품질 수정:** 첫 가족 추천 뒤 “와이프꺼는 더 얼큰한걸로 보여줘”를 와이프의 국물 취향 변경으로 적용하고, 이어지는 “알러지는 없고 얼큰한걸로”도 직전 와이프 메뉴의 추가 설명으로 처리한다. 저장된 3명이라는 숫자만으로 새 발화를 인원 확인으로 오판하지 않는다. 변경된 추천에서도 다른 두 사람의 조건과 전체 장바구니 흐름을 유지한다. 가상 성인 세 명의 공개 HTTPS 3턴 대화에서도 특정 손님만 순한 수프에서 얼큰한 수프로 바뀌고 다른 두 추천은 유지됨을 확인했다.

**재방문 세션 수정:** 채팅 화면 문장이 새로 시작해도 서버 대화 조건은 남아, 사용자가 가족의 한 끼를 다시 자세히 설명할 때 오래된 채식·예산·다른 일행 정보가 섞여 메뉴가 없어질 수 있었다. 전체 식사 설명이 다시 들어오면 이전 메뉴 취향·예산·익명 일행을 교체하고, 같은 이름의 알레르기·엄격한 식사 조건 및 별도로 저장한 내 취향은 보존한다. 새 일행에 연결할 수 없는 이전 알레르기는 누락하지 않고 이번 주문의 공통 제한으로 보존한다. 저장된 내 취향 때문에 결과가 비면 적용 중인 제한을 답변에 표시한다. 재방문 상태를 만든 회귀 테스트 25개와 가상 성인 일행의 공개 HTTPS 재방문 검증, 전체 주문 스모크를 통과했다.

**연속 대체 추천 수정 (2026-09-24):** 첫 대화에서 한 사람의 순한 국물을 고른 뒤 “더 얼큰하게” 요청하면 그 사람의 순한 맛과 맵기 상한을 매운맛으로 교체한다. 이어 “아니면 덮밥류로” 요청하면 직전 사람의 국물 조건을 덮밥으로 바꾸되 얼큰한 맛과 다른 일행의 추천은 유지한다. 갑각류 제한으로 해물 수프가 제외되어도 선택 가능한 가상 얼큰 닭고기 수프·덮밥 2개를 seed에 추가했다(총 22개 메뉴). 실제 매장에서는 점주가 메뉴별 재료와 알레르기 정보를 직접 검증해야 한다. 제한 때문에 후보가 없으면 적용 중인 알레르기 종류를 보여주며, 사용자가 “알러지는 없어”라고 명시한 경우에만 공통 프로필의 알레르기를 지운다. 특정 일행에게 붙은 알레르기는 유지한다. 도메인 회귀 테스트 29개, 타입 검사, 린트, 빌드, 전체 HTTP 스모크가 통과했다. 실제 OpenRouter를 사용하는 **가상의 성인 3명** 공개 서비스 4턴 대화에서 갑각류 제한 유지 → 순한 국물 → 얼큰 닭고기 수프 → 얼큰 닭고기 덮밥 → 명시적 공통 알레르기 해제를 확인했다. 실제 사용자 세션의 제한 정보는 조회하지 않았다.

## 8. 시연·완료 기준

**기본 시연:** 손님이 **가져가기** 선택 → “우리 3명인데 한 명은 채식하고 한 명은 매운 걸 못 먹어” → “따뜻한 거 4만원 안에서 추천해줘” → 개인별 추천 확인 → “추천한 거 전부 담아줘” → “주문할게”, “응” → 모의 결제 → 사장님 화면에서 기본 입력된 데모 계정으로 로그인하고 **가져가기** 주문을 접수. 이어서 알레르기 있는 손님의 추천 차단, 직원 호출과 메뉴판 초안 검토·공개를 보여준다. 대화·주문·점주 흐름은 자동 HTTP 및 Firefox 브라우저 검증을 통과했다.

**내부 테스트 종료 조건:** 팀원이 같은 흐름을 모바일·태블릿·PC에서 완주하고, 알레르기/엄격 식이/품절/옵션/가격 변경/중복 요청으로 잘못된 주문이 생성되지 않으며, 점주가 메뉴와 주문을 독립적으로 관리하고, 루트 홈페이지의 다른 PoC가 정상 동작한다. 실제 매장 도입 조건은 별도이며 가상 seed를 실재 알레르기 데이터로 간주하지 않는다.
