# PoC 09 공유·실행 단일 계획 — ㅁㅁㅈ(뭐먹지?)

**상태 기준: 2026-10-02 · Groq 무료 문맥 해석과 일행별 상태 변경을 공개 서비스에 적용. 현재 수정 빌드에서 Groq 핵심 10대화·28턴과 새 4인 조별 식사·가족 관련 사례 3건, 규칙 경로 200대화·1,000턴 3회, 주문 스모크 통과. 2026-09-28의 Groq 32대화·74턴은 이전 빌드의 이력이다. 팀의 새 발화 블라인드 평가와 실기기 검증 전까지 내부 최종 수용은 보류.** 이 문서 하나로 새 팀원이 최종 제품의 방향, 이번 PoC의 범위, 실제 구현·배포 위치, 검증 근거, 남은 팀 결정과 다음 작업을 파악할 수 있도록 유지한다. 제품 사용·설치·운영의 상세 절차는 루트 [README](../README.md)에 있다. 원 설계 입력은 사용자 제공 「ㅁㅁㅈ — AI 대화형 주문 플랫폼 Architecture & Codex Implementation Specification」이며, 이후 사용자가 **QR·RF/NFC·STT는 이번 개발에서 제외**하도록 범위를 조정했다.

## 1. 최종 목적과 이번 단계

**최종 목적:** **Tap · Talk · Together**. 매장에 온 손님이 먹고 가기/가져가기를 탭으로 정하고, 평소 말로 일행·취향·제약을 설명하며, 여러 차례 대화로 음식을 함께 골라 주문한다. 메뉴 목록은 참고용 보조 기능이다. 실제 매장의 검증된 메뉴와 옵션·가격·안전 정보를 확인해 주문한다. 사장님은 메뉴 정보를 책임지고 주문을 접수한다. 장기적으로는 QR/NFC 진입, 음성 입출력, 운영 시스템 연동까지 확장한다. 핵심 원칙은 **“말은 자유롭게, 거래는 엄격하게.”** AI는 사용자의 말을 구조화하고 검증된 결과를 설명할 수 있지만, 메뉴·가격·알레르기·총액·주문 확정은 DB와 서버 코드가 결정한다.

**이번 PoC의 검증 질문:** 텍스트 대화와 간단한 터치 화면만으로도 손님이 취향·일행 조건을 반영해 안전 규칙을 깨지 않고 주문을 완료하고, 사장님이 즉시 처리할 수 있는가. 따라서 이번 단계는 **한 개 가상 매장, 대화에서 파악하는 한 기기 그룹 주문, 서버 내부 다중 턴 기억, 구조화 LLM 해석과 서버의 검증된 메뉴 조합, 무료 모델 장애 시 상태 보존, 선택적 Jev 실험, 메뉴판 초안, 모의 결제**까지 제공한다. QR 발행·태그, RF/NFC, STT·마이크, 실제 결제·POS, 계정 기반 고객 프로필은 포함하지 않는다. 일반 `?table=` URL은 후속 QR/NFC에서 그대로 쓸 수 있도록 이미 제공한다.

**현재 사용 가능한 공개 진입:** `https://www.minslab.kr/mmj` → `/poc/mwomeokji/`. 손님 화면 `/poc/mwomeokji/s/orange-table/`, 사장님 화면 `/poc/mwomeokji/merchant/`. README의 데모 계정 위치를 참고한다. 메뉴·알레르기 정보와 자동 입력된 사장님 계정은 **공개 가상 테스트 데이터**로, 실제 음식 안전성 주장이 아니다.

## 3. MinsLab 홈페이지에 맞춘 구조와 버전 판단

```text
minslab.kr/mmj
  → 기존 Python ASGI 홈페이지의 307 단축 주소
  → /poc/mwomeokji/*만 PoC9 전용 프록시
  → 127.0.0.1:18090 Next.js (basePath=/poc/mwomeokji)
      ├─ 손님 화면 /s/[storeSlug]
      ├─ 사장님 화면 /merchant
      ├─ Route Handler /api/*
      ├─ 추천·안전·주문 코드
      └─ Prisma → 127.0.0.1:18091 PostgreSQL 16
```

같은 도메인에서 동작한다는 이유로 구형 Node/Prisma에 맞추지 않는다. 홈페이지는 **경로 프록시**이며 PoC9 프로세스만 Node 24와 Next 16/Prisma 7을 사용한다. 이는 루트 Python 서비스와 PoC7/8의 의존성 충돌을 피하고, `/mmj`·PoC 카드·쿠키 경로·정적 파일을 같은 출처에서 유지한다. 현재 서버 기본 Node 18은 그대로다. `.runtime/bin/node`는 배포 호스트에서 `scripts/prepare-node24.sh`로 준비하며 커밋하지 않는다. PostgreSQL도 PoC9 전용 컨테이너/볼륨이고 다른 DB를 수정하지 않는다.

프록시는 손님·점주 쿠키 중 `poc09_*`만 전달하고, 변경 메서드와 최대 6 MB 이미지 업로드를 허용한다. Root `.env` 값 중 PoC9에 필요한 변수만 `scripts/with-root-env.mjs`가 전달한다. 쿠키와 API 키는 클라이언트 번들에 넣지 않는다. 부모 홈페이지가 PoC9에 연결할 수 없으면 해당 경로만 503으로 실패한다. 운영 유닛·포트·백업·재시작 명령은 README에 있다.

## 4. 서비스 사용자 여정과 계약

### 손님 — 제품의 기본 경로

매장 방문 → **먹고 가기 / 가져가기** 중 하나 탭 → “우리 3명인데 한 명은 채식, 한 명은 매운 걸 못 먹어”처럼 입력 → 서버가 인원과 일행별 조건을 대화 맥락으로 저장하고 부족한 정보는 다시 질문 → 검증된 실메뉴를 사람별로 추천 → “추천한 거 전부 담아줘”, “첫 번째 담아줘”, “다른 거” 같은 후속 발화 → 옵션이 필요하면 검증된 기본 옵션을 선택하고 주문 전 재검증 → “주문할게”와 확인 대화 또는 장바구니 버튼 → 모의 결제 → 식사 방식이 적힌 주문을 사장님 화면에서 처리. 화면에서 멤버를 일일이 추가하는 입력란은 없다. 스마트폰 음성 키보드로 입력한 문자도 같은 대화 API로 들어간다. 앱 자체 STT/음성 출력은 이번 범위에서 제외한다.

알레르기·식이·큰 글씨 설정 패널, 추천 카드 상세, 장바구니, 내역, 직원 호출은 필요한 순간의 보조 조작이다. **전체 메뉴 참고**는 후순위 링크로만 제공한다. 인식되지 않는 말이나 후보가 없는 조건은 임의로 확정하지 않고 재질문·직원 호출로 연결한다. `?table=A1`은 미래 QR 진입 호환용이며 손님 화면에서 테이블 선택을 요구하지 않는다.

### 사장님

자동 입력된 공개 테스트 계정으로 별도 로그인 → 새 주문의 먹고 가기/가져가기·선택된 테이블·요청 사항 확인 → 접수·조리·완료 상태 변경 → 직원 호출 처리. 메뉴명·가격·재료·식이 태그·알레르기 상태·공개/품절·옵션과 추가금을 관리한다. 텍스트 또는 설정된 AI 이미지 읽기로 메뉴판을 초안화하지만, 점주가 재료와 10개 알레르기 항목을 확인하기 전에는 공개할 수 없다.

### 실제 API 경계

- `GET /api/bootstrap/`, `/api/cart/`, `/api/orders/`, `/api/health/`: 가상 매장/메뉴·내 장바구니·내 주문·DB 상태.
- `POST /api/visit/`, `/api/profile/`, `/api/conversation/`, `/api/cart/`, `/api/checkout/`, `/api/help/`: 식사 방식, 현재 세션 조건, 다중 발화 추천·지시어 주문, 장바구니, 모의 주문, 직원 호출. 장바구니 수량은 `PATCH`, 삭제는 `DELETE`.
- `/api/merchant/login/`, `/dashboard/`, `/menu/`, `/import/`, `/orders/:id/`, `/help/:id/`: 점주 전용 메뉴·옵션·초안·주문·호출.
- API 응답의 메뉴명·옵션·금액은 항상 DB 값이다. 클라이언트가 보낸 총액은 받지 않는다. 주문은 트랜잭션에서 최신 값으로 확정하고 같은 idempotency key에는 같은 주문을 반환한다.

핵심 데이터 모델은 `Store`, `StoreTable`, `MenuCategory`, `MenuItem`, `MenuOptionGroup`, `MenuOption`, 메뉴/옵션 알레르기 검증, `GuestSession`, `CartItem`, `Order`/`OrderLine`, `HelpRequest`, `MerchantSession`이다. 주문 행은 메뉴명·옵션명·단가·합계를 스냅샷으로 보존한다. 원문 대화나 카드정보는 DB에 저장하지 않는다. `GuestSession.context.dialogue`에는 파악한 인원·조건·마지막 추천 ID·주문 확인 상태만, `Order.fulfillmentType`에는 식사 방식을 저장한다.

### 다중 턴 해석의 데이터 경계와 활성화 상태

스마트폰 자체 음성 키보드의 결과와 타이핑 문장은 `POST /api/conversation/`의 동일한 `message`로 처리한다. 서버는 세션에 인원, 일행별 취향·채식·알레르기·맵기, 예산, 현재 추천 ID와 대체 제안·주문 확인 상태를 구조화해 보관한다. Groq 무료 모델에는 **현재 발화, 익명 자리 ID와 열린 취향, 직전 추천의 공개 메뉴명·ID·담당 자리, 전체 예산·종류, 직전 대체 제안 요약**만 보낸다. 저장된 일행 이름은 번호로 치환하고, 모델 응답의 번호는 서버 내부에서 원래 사람에게 되돌린다. 원문 대화 이력·장바구니 상세·알레르기·엄격 식이·세션 ID·비밀값은 Groq에 보내지 않는다.

Groq의 구조화 응답은 일행별 인원·맛·메뉴 태그, 이번에 바꿀 자리, 대체 제안의 수락·거절을 담는다. 서버는 대상과 태그가 실제 발화와 현재 추천에 근거하는지 확인하고, DB의 판매 가능 메뉴·가격·옵션·알레르기·식이·맵기·예산으로 최종 검증한다. 모델이 429나 형식 오류를 반환하면 인기 메뉴로 임의 대체하지 않고 상태와 장바구니를 보존한다. 결제 확정은 서버의 별도 확인 단계다. 현재 운영은 `POC09_CONVERSATION_PROVIDER=groq`, `POC09_LLM_MODEL=openai/gpt-oss-20b`, 메뉴 선택·실험 판단 `rules`이며 유료 OpenRouter 호출로 자동 복귀하지 않는다. PoC7 공용 장부에는 모델·결과·토큰 메타데이터만 남는다. Groq 계정의 ZDR 활성 여부와 PoC4·7·8·9의 키별 원자적 한도 예약은 아직 확인·구현 전이다.

## 5. 안전·AI 판단 순서

1. 현재 공개 모드는 Groq 무료 `openai/gpt-oss-20b`다. 현재 발화와 필요한 익명 일행·직전 추천 요약을 구조화된 상태 변경안으로 바꾼다. 실패하면 그 턴의 대화 상태를 보존하고 재시도를 안내한다. LLM은 실제 메뉴·가격·안전 여부나 주문 확정을 만들지 않는다.
2. 코드가 DB의 실제 게시·판매 메뉴만 로드한다. 알레르기별 메뉴와 선택 옵션에 `merchant_verified + excludes`가 없으면 해당 조건의 추천·주문에서 제외한다. `contains`, `unknown`, AI 추정은 통과하지 않는다. 엄격 식이조건과 맵기 상한, 예산도 같은 단계에서 검사한다. 서버가 명시된 메뉴 종류·커피 여부·카페인 표시·잔 수·총예산을 마지막 추천 결과와 다시 대조한다. 불일치한 제안은 내보내지 않는다.
3. 서버가 DB에서 적격 후보를 만들고 일행별 열린 취향과 점주 메뉴 태그를 조합한다. 현재 운영의 메뉴 선택과 선택적 판단은 `rules`다. 실험용 OpenRouter 메뉴 선택·Jev 코드는 운영 대화 경로에서 호출하지 않는다. 후보 조합 수의 상한과 메뉴 적격 후보 누락 계측은 9절의 남은 개선 항목이다. 최종 선택 결과를 2단계 제약으로 다시 검사한다.
4. 옵션 선택·장바구니와 주문 확정에서 안전과 가격을 다시 검사한다. 그룹 주문은 각 멤버 조건을 합쳐 검사하고 전체 예산 안에서 조합한다.
5. 실매장에서는 재료뿐 아니라 제조·교차 접촉을 점주가 확인해야 한다. 현 seed의 검증 상태는 자동 생성된 가상 데이터이며 법적 안전 보증이 아니다.

**2026-09-24 실제 사용자 대화 오류 수정:** “2살 아이·와이프·나”를 세 명으로 인식하고, “나는 매운 것 / 아이는 맵지 않고 달달한 키즈 / 와이프는 국물”을 사람별 취향으로 저장한다. 취향을 설명하며 끝에 “주문해줘”라고 말한 요청은 메뉴 선택으로 해석한다. 이어 “추천한 거 전부 주문해줘”로 담고, 장바구니 확인 뒤 명시적 주문 확정으로 진행한다. 가상 키즈 메뉴 1개를 seed에 추가했다. 실제 매장에 키즈 메뉴가 없거나 조건에 맞지 않으면 임의의 일반 메뉴로 대체하지 않고 질문한다. 2살에게 적합한 재료·식감은 보호자와 점주가 확인해야 한다. 이 경로는 규칙 fallback 회귀 테스트와 공개 HTTPS의 실제 OpenRouter 대화로 검증했다.

**후속 대화 품질 수정:** 첫 가족 추천 뒤 “와이프꺼는 더 얼큰한걸로 보여줘”를 와이프의 국물 취향 변경으로 적용하고, 이어지는 “알러지는 없고 얼큰한걸로”도 직전 와이프 메뉴의 추가 설명으로 처리한다. 저장된 3명이라는 숫자만으로 새 발화를 인원 확인으로 오판하지 않는다. 변경된 추천에서도 다른 두 사람의 조건과 전체 장바구니 흐름을 유지한다. 가상 성인 세 명의 공개 HTTPS 3턴 대화에서도 특정 손님만 순한 수프에서 얼큰한 수프로 바뀌고 다른 두 추천은 유지됨을 확인했다.

**재방문 세션 수정:** 채팅 화면 문장이 새로 시작해도 서버 대화 조건은 남아, 사용자가 가족의 한 끼를 다시 자세히 설명할 때 오래된 채식·예산·다른 일행 정보가 섞여 메뉴가 없어질 수 있었다. 전체 식사 설명이 다시 들어오면 이전 메뉴 취향·예산·익명 일행을 교체하고, 같은 이름의 알레르기·엄격한 식사 조건 및 별도로 저장한 내 취향은 보존한다. 새 일행에 연결할 수 없는 이전 알레르기는 누락하지 않고 이번 주문의 공통 제한으로 보존한다. 저장된 내 취향 때문에 결과가 비면 적용 중인 제한을 답변에 표시한다. 재방문 상태를 만든 회귀 테스트 25개와 가상 성인 일행의 공개 HTTPS 재방문 검증, 전체 주문 스모크를 통과했다.

**연속 대체 추천 수정 (2026-09-24):** 첫 대화에서 한 사람의 순한 국물을 고른 뒤 “더 얼큰하게” 요청하면 그 사람의 순한 맛과 맵기 상한을 매운맛으로 교체한다. 이어 “아니면 덮밥류로” 요청하면 직전 사람의 국물 조건을 덮밥으로 바꾸되 얼큰한 맛과 다른 일행의 추천은 유지한다. 갑각류 제한으로 해물 수프가 제외되어도 선택 가능한 가상 얼큰 닭고기 수프·덮밥 2개를 seed에 추가했다(총 22개 메뉴). 실제 매장에서는 점주가 메뉴별 재료와 알레르기 정보를 직접 검증해야 한다. 제한 때문에 후보가 없으면 적용 중인 알레르기 종류를 보여주며, 사용자가 “알러지는 없어”라고 명시한 경우에만 공통 프로필의 알레르기를 지운다. 특정 일행에게 붙은 알레르기는 유지한다. 도메인 회귀 테스트 29개, 타입 검사, 린트, 빌드, 전체 HTTP 스모크가 통과했다. 실제 OpenRouter를 사용하는 **가상의 성인 3명** 공개 서비스 4턴 대화에서 갑각류 제한 유지 → 순한 국물 → 얼큰 닭고기 수프 → 얼큰 닭고기 덮밥 → 명시적 공통 알레르기 해제를 확인했다. 실제 사용자 세션의 제한 정보는 조회하지 않았다.

**재료 확인·주문 확정 대화 수정 (2026-09-24):** “내꺼에 오이가 들어갔는지 확인해봐”는 LLM의 질문 되풀이를 그대로 응답하지 않고, 서버가 직전 추천 또는 장바구니의 `나` 메뉴를 찾는다. 메뉴의 등록 재료와 선택한 옵션만 확인하며, 목록에 없는 일반 재료는 미포함으로 단정하지 않고 점주 확인이 필요하다고 안내한다. 본인 메뉴를 특정할 수 없거나 여러 개면 이름·추천 번호를 되묻는다. 이 조회는 LLM을 호출하지 않고 직전 추천 상태도 지우지 않는다. 빈 장바구니에서 완성된 일행별 추천 직후 “주문해줘”라고 말하면 각 메뉴를 안전 검증 후 담고 합계·모의 결제 확인을 요청한다. “응” 이후에만 최종 주문을 접수한다. 혼자 여러 후보를 받은 경우에는 자동으로 전부 담지 않고 메뉴 선택을 묻는다. 가상 성인 2명 API 대화에서 재료 확인 → 추천 2개 담기 → 명시적 최종 확인을 재현했다. 단위 테스트 34개와 타입 검사·린트·빌드·HTTP 스모크가 통과했다.

**2026-09-27 구현·합성 평가:** 이름이 있는 가상 성인 3명의 개별 취향을 규칙 fallback에서도 분리하고, 후속 얼큰한 국물·덮밥 변경이 다른 사람의 선택에 영향을 주지 않게 했다. `npm run ai:evaluate -- --both`는 합성 발화 6턴의 14개 기대 조건에서 Rules와 OpenRouter가 각각 14/14를 통과했다. OpenRouter 평균 2,674ms, p95 3,259ms, 입력 6,054·출력 990토큰, 제공자 보고 비용 $0.004006, fallback 0턴이었다. 작은 고정 세트이므로 실제 사용자 발화의 정확도 보증은 아니다. 외부에는 가상 성인 발화만 보냈다.

선택적 Jev는 [OpenRouter Decisions API](https://openrouter.ai/blog/tutorials/how-to-use-jev/)로 수정했다. `npm run decision:evaluate -- --live`의 가상 후보 3개 평가에서 Jev가 536ms, 입력 438·출력 52토큰, $0.000018396으로 응답했다. 코드가 확인된 메뉴 ID 집합만 재정렬하며 낮은 신뢰도·형식 오류·API 실패는 Rules 순위로 돌아간다. 기본 운영 설정은 계속 `POC09_DECISION_PROVIDER=rules`다. 대화 해석, 메뉴 선택, Jev, 선택적 이미지 메뉴판의 호출 상태·토큰·비용은 동일한 PoC7 장부에 `order_interpretation`/`order_selection`/`order_ranking`/`menu_import` 작업명으로 기록한다. 장부에는 원문·응답·세션 ID·이미지를 보내지 않는다.

**2026-09-27 주제별 추천 확대:** 가상 매장에 브런치 3종과 디저트 2종을 더해 메뉴 28개·카테고리 5개로 확장했다. 점주는 메뉴 편집 화면에서 추천 키워드를 관리한다. 브런치·밥·빵·든든·대표메뉴·데이트·직장동료 같은 점주 표시는 현재 발화와 대화 상태에 반영하고, 판매·알레르기·예산 검증을 거친 후보만 모델에 보낸다. 점심·저녁은 식사 요청으로 해석하며 판매 시간은 아직 모델링하지 않는다. “추천이 많은”은 데모 인기 점수로 비교할 뿐 실제 추천 횟수는 주장하지 않는다. 완료 주문의 메뉴를 다시 요청하면 같은 익명 세션의 주문 내역만 조회하고 현재 판매 가능 여부와 안전 조건을 재검사한다. 모델이 ‘예산을 다시 추천’처럼 다른 문장을 과거 주문으로 오해해도 명시적인 이전 주문 표현이 없으면 기록을 조회하지 않는다. 단어 경계(덮밥의 ‘밥’), ‘말고’로 이전 메뉴 제외, ‘바꿔줘’ 후속 요청과 모델의 불필요한 확인 문장도 평가 중 수정했다. 아이용 메뉴에는 보호자의 재료·식감 확인 문구를 붙인다. 가상 주문과 세션은 평가 종료 시 삭제한다.

**2026-09-27 가상 메뉴 3배 확장:** 기존 28개에 `prisma/scenario-recipes.ts`의 가상 레시피 56개를 추가해 총 84개로 편성했다. 현재 공개·판매 메뉴는 식사 39, 국물 9, 사이드 12, 디저트 10, 음료 14개이며 운영 DB의 카테고리별 조회로 확인했다. 맵기 0–4, 채식·비건, 고기·해산물, 10종 알레르기, 음료 카페인 상태, 1,500~15,900원 가격대, 브런치/밥/빵/든든/데이트/직장동료 등의 요청을 시험할 수 있다. 기존 점주 수정 메뉴는 seed 재실행으로 덮어쓰지 않는다. 후보가 84개로 늘어도 현재 발화와 이름이 겹치는 낮은 인기 메뉴를 LLM 후보에 우선 포함하고, 총액·안전은 서버가 재검증한다. 데이터 테스트는 추가 56개의 이름·분포·식이·알레르기·카페인 표기를 검사한다. 확대 평가에서 ‘다른 국물’을 덮밥으로 바꿔 추천한 문제를 국물 후보 제한으로 해결했고, 디카페인에서 완전 무카페인으로 정정한 뒤 이전 상태가 남는 문제도 해결했다. 수정 때마다 평가를 1번부터 다시 실행하여 당시 **22/22 사례·51/51턴**을 통과했고, 단위·데이터 테스트 **61/61**을 통과했다. 가상 메뉴의 `merchant_verified` 표시는 실매장 성분 보증이 아니다.

**2026-09-27 음성 중심 다중 턴 주문 보완:** 실제 팀 시나리오에서 새로고침 시 화면 대화만 사라지고 숨은 4인 상태가 남는 문제를 확인했다. 손님 화면은 장바구니가 비어 있는 재진입에서 대화 인원·일회성 조건을 함께 초기화한다. 담은 메뉴가 있으면 일행별 안전 검증을 위해 상태를 유지한다. 그룹 후보 생성은 서로 다른 메뉴가 가능하면 우선 사용하고, “겹치지 않게”를 명시하면 중복 조합을 반환하지 않는다. 직전 제안이 1개 또는 일행별 완성된 조합일 때 “좋아 담아줘”와 “담아줘”는 그 제안을 담고, “주문할께”는 새 추천 대신 장바구니 합계와 최종 확인을 요청한다. “응” 이후에만 모의 주문을 접수한다. “4명 모두 채식”을 모델이 한 사람 조건으로 오해해 다른 세 명에게 고기를 제안한 오류를 수정했으며, 같은 유형의 “모두 알레르기” 발화도 공통 안전 제한으로 보존한다. 공개 HTTP 경로의 합성 평가를 수정마다 1번부터 다시 실행하여 당시 **25/25 사례·64/64턴**, 단위·데이터 테스트 **64/64**를 통과했다. 이 평가는 합성 문장 검증이며 실제 팀 기기 UAT는 남아 있다.

**2026-09-27 구어체 인원별 취향과 메뉴 지목 보완:** “다섯명인데 둘은 맵찔이고, 셋은 매운거 잘 먹어”처럼 `명`이 생략된 그룹 조건을 서로 다른 다섯 자리의 취향으로 기록한다. 2명 순한 맛·3명 매운맛은 추천 전 후보 필터와 추천 후 검증에서 모두 적용하며, 일부 사람의 맵기 제한을 전체 일행 제한으로 승격하지 않는다. 후속 대화에서 직전 추천의 “샐러드”처럼 메뉴 이름의 일부를 지목하면 그 메뉴가 배정된 사람을 찾아 새 취향(“해장되는”은 국물 선호로 해석)을 그 사람에게만 적용하고, 다른 네 메뉴는 그대로 둔다. 국물 메뉴를 제안할 뿐 숙취 해소 효능은 주장하지 않는다. 지목한 메뉴가 직전 추천에 없으면 임의로 전원을 재추천하지 않고 교체 대상을 묻는다. 명확한 메뉴 변경 발화는 모델의 해석 요약문으로 대체하지 않는다. 합성 HTTP 사례 26·27과 도메인 단위 테스트를 추가했다. 실제 홈페이지 프록시에서 전체 평가를 수정 후 1번부터 재실행해 **27/27 사례·67/67턴**을 통과했고, 단위·데이터 테스트 **65/65**, `typecheck`, `lint`, 운영 `build`와 주문·점주 `smoke`도 통과했다.

현재 `lib/ai.ts`의 모델은 이번 문장만 보고, `lib/menu-selector.ts`는 이번 문장과 사전 구성된 최대 14개 조합만 본다. `lib/dialogue.ts`가 별도의 표현 규칙으로 이전 인원·취향·추천을 결합하므로, 새 표현이나 지시어의 대상과 범위가 사라진다. 최종 안전 검사는 **기록된 조건**만 검사하므로 누락된 사람별 취향을 복구할 수 없다. 지금까지의 소수 회귀 사례 통과는 열린 멀티턴 발화의 품질 승인 근거가 아니다.

**결정:** 한 턴을 `현재 발화 → 문맥을 근거로 한 구조화 변경안 → 서버의 원자적 상태 적용 → DB 메뉴·안전 검증 → 손님 답변`으로 처리한다. 사람·조건·메뉴의 대상과 범위를 상태에 명시한다. 모델은 자연어가 상태를 어떻게 바꾸는지만 제안한다. 메뉴 사실, 가격, 알레르기, 장바구니, 주문 확정은 서버와 DB가 결정한다. 기존 표현별 조건식은 호환 경로로만 두고 새 대화 흐름의 주 판단기로 쓰지 않는다.

**무료 이용 정책(승인 후 실제 구현은 11절):** 최신 유료 모델을 추가하자는 앞선 제안은 철회한다. 새 대화 엔진의 해석, 추천 선택, 재시도, 평가에는 **루트 `.env`에 키가 있고 실제 무료 이용 자격·잔여 한도가 확인된 플랫폼만** 쓴다. 기존 `openai/gpt-4.1-mini`는 현재 배포 상태를 설명하는 모델 ID일 뿐 새 평가의 호출 기준선이나 자동 복귀 경로가 아니다. 전환할 때 유료 대화 모델과 유료 Jev 호출을 활성 라우팅에서 제거한다. 무료 경로가 막혀도 유료 호출로 넘어가지 않는다. 상태와 장바구니를 보존하고 구체적인 질문·직원 호출을 제공한다. 이미 담긴 장바구니의 주문은 서버 검증으로 계속 가능해야 한다.

### 루트 `.env`와 무료 공급자 후보

값을 출력하지 않고 루트 설정에 `GROQ_API_KEY`, `OPENROUTER_API_KEY`, `Google_AI_STUDIO_API_KEY`, `NVIDIA_API_KEY`, `UPSTAGE_API_KEY`, `MISTRAL_API_KEY`가 마련된 것을 확인했다. **키 존재는 무료 자격이나 잔여량의 증거가 아니다.** 승인 전에는 PoC9가 OpenRouter 키만 전달·기록했다. 승인 후 Groq 키 allowlist와 공급자별 계량을 연결했으며, 현재 구현은 11절에 기록했다.

### 수용 게이트·개인정보·음성 범위

- **자동 평가:** 사용자 제보 전부와 200개 이상 대화·1,000턴의 상태 전이, 메뉴 존재·할당·가격·안전·주문 단계는 오프라인 하네스에서 매 변경마다 **100% 통과**해야 한다. 실제 무료 모델 평가도 동일한 전체 대화를 여러 무료 한도 주기에 나눠 실행하며, 핵심 실패 유형은 3회 반복한다. 보류 세트의 명확한 발화는 대상/행동/범위 정확도 **98% 이상**, 모호한 발화는 주문 대신 확인 질문이 기준이다. 새 오류를 찾으면 원인 수정 후 오프라인 전량과 실제 무료 모델 순차 평가를 첫 사례부터 다시 실행한다. 알려진 심각한 오주문 0건이 전환 조건이다.
- **사람 평가:** 팀원이 모바일·태블릿·PC에서 최소 30개 새 대화를 블라인드로 진행하고 메뉴 적합성·대상 유지·질문 품질을 채점한다. p95 응답 시간, 요청/토큰 소비, 한도 소진 시 동작도 기록한다. 유한한 평가가 모든 미래 발화의 무오류를 보증하지는 않는다.
- **외부 전송:** 2026-09-28 사용자가 Groq 무료 모델에 **현재 발화와 필요한 일행·추천 요약**을 전송하도록 승인했다. 11절의 구조화 해석 경로에서 그 범위로만 전송한다. 세션 ID·원문 대화 이력·장바구니 전체·비밀값·알레르기·식이 제한은 보내지 않고 서버에서 처리한다. 무료 계정의 실제 Data Controls/ZDR 활성 여부는 API 키만으로 입증할 수 없으므로 운영 점검 사항으로 남긴다.
- **음성 범위:** 스마트폰 자체 음성 키보드의 텍스트는 현재 같은 대화 API로 들어온다. 앱 자체 녹음·STT·음성 출력은 아직 구현 전이다. 음성 키보드의 오탈자·구두점 생략은 평가에 넣고, 자체 STT는 대화 품질 게이트 뒤에 같은 API로 연결한다.

**승인 전 기준선 기록(현재 상태는 11절 참조):** 위 표는 전체 목표다. 2026-09-28 승인 전에는 규칙 경로 검증과 합성 평가 전용 무료 호출 어댑터 일부만 구현했다. 현 공개 설정에는 유료 `openai/gpt-4.1-mini`가 남아 있으며 문맥 기반 무료 모델 연결·원자적 상태 전이·공용 예약은 미완료다. 10절의 통과는 규칙 경로의 회귀 근거다. 이 절의 무료 이용 정책이 5절의 과거 운영 기록보다 이후 작업에 우선한다.

## 11. 2026-09-28 승인 후 Groq 문맥 해석과 가족 대화 오류 보완

**승인·목적:** 사용자는 Groq 무료 모델에 현재 발화와 필요한 일행·추천 요약 전송을 명시적으로 승인했다. 신규 유료 모델에 의존하지 않는다. 합성 로컬 평가의 대화 모델은 Groq `openai/gpt-oss-20b`로 고정하고 메뉴 선택·주문 검증은 서버 규칙으로 둔다. 기존 OpenRouter 유료 모델을 무료 평가의 숨은 대체 경로로 사용하지 않는다. 공급자 429·형식 오류가 나면 그 턴의 상태를 바꾸지 않고 재시도를 요청한다.

**상태 변경 계약:** Groq는 현재 발화와 익명 `seat_N` 일행, 현재 추천의 공개 메뉴명·ID·담당 자리, 전체 예산·종류, 직전 대체 제안 요약을 받고 `peopleCount`, 일행별 `count/tastes/labels`, 전체 조건, 바꿀 자리, 제안 수락·거절을 구조화해서 반환한다. 저장된 실명은 외부 전송 전에 일행 번호로 치환한다. 서버는 모델이 제시한 자리·공개 메뉴 태그가 실제 발화와 현재 상태에 근거하는지 확인하고, 판매 가능·가격·예산·알레르기·엄격 식이·맵기·수량을 검증한 뒤에만 제안한다. 이 구분은 LLM이 **뜻과 변경 범위**를 해석하고 DB가 **사실과 주문 가능 여부**를 확정하도록 만든다. 메터에는 공급자·모델·작업·상태·HTTP 코드·토큰만 남기며 발화·세션 ID는 보내지 않는다.

**무료 모델 초기 실패 기록:** 처음에는 기존의 긴 구조화 스키마가 Groq에서 HTTP 400 `json_validate_failed`를 반환했다. 필요한 필드만 있는 상태 변경 스키마와 낮은 추론 강도로 축소했고, 엄격 JSON 검증 실패 때는 스키마를 명시한 JSON 모드로 한 번만 다시 시도한 뒤 로컬 스키마 검사로 확정한다. 이름별 순한맛이 빠지거나 발화하지 않은 달콤함을 모델이 추가한 사례는 각각 현재 발화의 명시 근거와 대조하는 검증으로 막았다. 임의의 새 메뉴나 사용자가 말하지 않은 알레르기·가격은 모델에서 받지 않는다.

**새 사용자 사례와 원인:** “4식구, 아이 둘은 키즈, 나와 와이프는 든든, 와이프는 안 맵게”를 이전 응답 스키마로 실행했을 때 모델은 총 4명만 읽고 아동 두 명과 본인의 개인 조건을 누락했다. 서버는 `든든`을 전원 필터로 적용하거나 키즈 메뉴가 없다고 잘못 안내할 수 있었고, 직전 질문을 상태에 저장하지 않아 “그래 그러게 해줘”를 새로운 요청으로 재해석했다. 스키마에 각 그룹의 인원 수와 일행별 매장 태그를 추가하고, 전체 태그와 일행 태그를 분리했다. 답변할 대체 제안은 세션 상태에 기록하고, 후속 수락 여부는 Groq가 직전 제안 요약과 현재 발화를 보고 결정한다. 수락하면 해당 아동 자리에서 키즈 요구를 순한 일반 식사로 바꾸고 다른 가족의 조건은 보존한다. 실제 키즈 메뉴가 있으나 다른 전원 조건 때문에 가려진 경우를 무조건 품절로 말하지 않도록, 대체 조합의 가능성을 먼저 확인한다.

**추가 검토와 재시작:** 기존 이름을 `일행 N`으로 익명화한 후 Groq가 같은 번호로 개인별 변경을 반환하면 로컬 세션의 실제 이름에 다시 연결하지 못하는 경로를 확인했다. 외부 전송에는 원래 이름을 넣지 않고, 서버 내부의 자리 번호 → 기존 일행 이름 표에서만 되돌리도록 수정했다. 전송 payload에 실명이 없는 단위 테스트를 추가하고 31개 전체 검증을 1번부터 다시 시작했다.

**번호로 지목한 후속 변경:** “첫 번째 거 더 맵게 바꿔줘”처럼 메뉴 번호만 말한 경우에는 모델의 대상 자리 ID를 현재 추천 순서와 대조한다. 같은 번호의 담당자에게만 매운맛을 적용하고 다른 일행 메뉴는 보존한다. 번호와 모델 자리 ID가 서로 다르면 변경하지 않는다. 실제 Groq 통합 사례가 이 한 사람 변경을 통과했다.

**실행 기록:** 변경 전 Groq 경로의 기존 27개 대화·67턴은 연속 통과했지만 새 4인 가족 사례는 아동 배정 누락으로 실패했다. 수정 후 그 가족 사례는 4명 각각에 맞는 제안과 “좋아 담아줘” 장바구니 연결을 통과했다. 보류 제안이 있는 상태의 “그래 그러게 해줘”, “그렇게 해달라고” 두 발화도 Groq 해석 후 순한 일반 메뉴로 연결됐다. 채식 제한으로 키즈 메뉴가 실제 불가능한 상황을 별도 생성해, 대체 제안 생성 → 짧은 동의 → 4인 재추천을 통과했다. 핵심 10개 대화·28턴도 1번부터 연속 통과했다. 최종 코드로 무료 Groq 경로 **32/32개 대화·74/74턴**을 1번부터 연속 통과했다. 모델이 필요한 5개 신규 사례는 Groq 평가에만 포함하고, 외부 모델을 끈 규칙 경로는 기존 **27/27개·67/67턴**을 1번부터 다시 통과했다. 현재 코드의 규칙 경로에서 200개 독립 세션·1,000턴을 1번부터 **3회 모두 통과**했다(각 28.2초, 27.2초, 27.0초). 매 회차 독립 세션으로 다시 시작하고 종료 시 시험 세션을 정리했다. 이 3,000턴은 외부 모델 호출 0회의 서버 상태·메뉴·주문 회귀 검사이며 Groq 자유 발화 3,000턴으로 표시하지 않는다. TypeScript·ESLint·Vitest 70개, 운영 `build`, 격리 운영 빌드의 손님·점주 `smoke`, `git diff --check`도 통과했다.

**그룹 주제 확대 평가 중 일일 한도:** 공개 Groq 경로에서 32개 그룹 주제×5턴 중 첫 7개·35턴은 통과했고, 8번째 대화의 두 번째 턴이 HTTP 429 `rate_limit_exceeded`로 중단됐다. 직접 서버 재현과 동일한 구조화 요청의 Groq 오류 본문을 확인했다. 조직 전체 **200,000 TPD 중 199,410토큰 사용, 이번 요청 752토큰**으로 일일 토큰 한도 초과다. PoC9 장부의 사용량만으로는 같은 키를 쓰는 다른 PoC 호출을 알 수 없다. 분당 토큰(TPM) 8,000이라는 헤더만 보고 한도 종류를 처음에 잘못 짚었으나, 응답 본문에서 TPD를 확인해 정정했다. 평가 스크립트는 HTTP 상태·오류 코드를 남기고 공유 키 충돌을 완화하려고 호출 간격을 35초로 늘렸지만 **간격 조정으로 TPD 초과는 해결되지 않는다**. 모델 기능의 실패로 판정하지 않으며, 거절된 턴은 서버가 상태와 장바구니를 보존한다. 제한 회복 후 32개 그룹 전체를 1번부터 재실행해야 한다. 이것을 통과한 평가로 표시하지 않는다. Groq가 `Retry-After`를 제공하면 손님 화면에 대략적인 재시도 시간을 안내하는 응답을 추가했다.

**공개 적용 확인:** 루트 `.env`의 PoC9 대화 공급자를 `groq`, 모델을 `openai/gpt-oss-20b`, 메뉴 선택·실험 판단을 `rules`로 설정하고 PoC9 서비스만 재시작했다. `poc09.service=active`, 홈페이지 프록시의 `/api/health/`는 `{"ok":true}`, `https://www.minslab.kr/mmj`는 주문 화면 경로로 307 포워딩을 확인했다. 공개 프록시로 4인 가족 Groq 사례(추천·4개 담기)가 통과했고, Groq 설정의 공개 경로에서 손님·점주·주문 `smoke`가 통과했다. 루트 비밀값은 저장소에 넣지 않았고 PoC4·7·8 설정은 수정하지 않았다.

**현재 해석 경계와 남은 표현 리스크:** Groq가 대화 맥락에서 일행별 조건·대상 자리·직전 제안에 대한 동의를 구조화하지만, 명확한 담기·주문 명령의 분류, 새로운 식사 설명으로 상태를 초기화할지의 판단, 메뉴 태그 추출, 한 사람의 일부 취향 갱신에는 기존 `parseIntent`·서버 문구 판정이 남아 있다. 이 판정은 현재 검증 사례에 필요한 서버 계약이며 모든 자유 발화가 이해된다는 뜻은 아니다. 다음 개선은 모델의 상태 변경 계약에 장바구니 명령과 새 대화/기존 대화 구분까지 포함하고, 서버는 실제 장바구니·주문 안전·확인 단계만 검증하는 것이다. 그 과정에서는 동일 세션의 동시 발화를 버전으로 직렬화하고, 실패 사례를 표현별 정규식 추가 대신 독립 대화 회귀 사례로 남긴다.

**남은 수용 작업:** 기존 메뉴 선정은 검증된 후보를 서버가 조합하므로 LLM이 임의의 메뉴를 지어내지 않는다. 다만 고정 후보 상한, 동시 발화의 버전 있는 원자적 갱신, 같은 무료 키를 쓰는 PoC4·7·8·9의 원자적 요청 예약은 아직 계획 단계다. 200개/1,000턴 3회는 규칙 엔진 회귀이며 무료 LLM의 열린 발화 3,000턴 검증을 뜻하지 않는다. 무료 모델 실호출은 계정의 일일 요청·토큰 한도를 넘길 수 있어 날짜별 분할 검증이 필요하다. 실제 계정의 데이터 통제 설정·공유 키 잔여량을 운영자가 확인하고, 팀원이 모바일·태블릿·PC에서 새로운 발화를 블라인드 평가해야 최종 내부 수용이다.

## 12. 2026-10-02 4인 조별 식사 종류 보존 오류

**사용자 재현:** “조별 활동으로 4명이서 식사… 여자 두분은 매운거 잘 못 드신다”는 발화에서 여자 1명에게 음료, 남자 1명에게 사이드를 추천했다. “음료나 사이드 말고 식사류”라고 정정하면 네 명 모두 음료로 바뀌었다. 두 턴 모두 식사 종류와 여자 두 분의 순한맛 조건을 함께 만족해야 한다.

**원인:** 기존 규칙 파서는 한 문장에 여러 메뉴 종류가 있으면 부정된 앞 단어 `음료`를 먼저 선택했다. Groq가 후속 발화를 `식사`로 해석해도 서버가 규칙 파서의 값이 이미 있다는 이유로 모델 결과를 버렸다. 첫 턴에서는 일행별 맛 조건을 적용하는 함수가 전원 식사 종류를 지웠다. 카탈로그 후보 조합은 종류가 비어 있을 때 음료·사이드를 허용하므로, 모델의 사람별 취향 해석만으로 이 문제를 막을 수 없었다.

**보완 계약:** Groq 경로에서는 모델이 반환한 전원 메뉴 종류가 규칙 파서의 종류보다 우선한다. 모델이 종류를 지정하지 않고 일행 한 사람만 변경했다면, 그 사람의 국물·맛 언급을 전원 메뉴 종류로 확대하지 않는다. 일행별 맛과 전원 식사 종류를 분리해 상태에 보존한다. 그룹 추천과 최종 검증에서 아이용 메뉴는 해당 자리의 키즈 요청 또는 전원 키즈 요청이 있을 때만 허용한다. 이 변경은 임의 문구별 새 응답 분기가 아니라 모델 상태 변경의 적용 범위와 DB 메뉴 검증 계약을 바로잡는다.

**후속 회귀 실패와 재시작:** 식사 종류를 보존한 뒤 기존 4인 가족 사례 28이 실패했다. 메뉴판의 키즈 음식 두 개 모두 `식사` 태그가 있어 DB 분류 문제는 아니었다. 모델이 어른 두 명에게만 지정한 `든든` 태그를 `memberUpdates`와 `globalLabels`에 중복 반환했고, 서버가 전원 태그를 수락해 아이 키즈 메뉴를 후보에서 지웠다. 모델 출력의 같은 태그가 일부 일행의 개인 조건에도 있으면 전원 태그로 확대하지 않도록 검증했다. 가족 사례는 아이 둘 키즈 식사 + 어른 둘 든든 식사 + 네 메뉴 담기로 재통과했고, 사용자 조별 식사 2턴도 다시 통과했다. 그 뒤 핵심 Groq 10개 대화를 1번부터 재실행한다.

**현재 검증:** 사용자 발화 그대로의 Groq 2턴을 신규 독립 사례 33으로 실행했다. 첫 추천과 정정 뒤 추천 모두 4개 실메뉴가 `식사`이고 음료·사이드·키즈 메뉴가 없으며, 여자 두 분의 메뉴는 맵기 0이었다. 기존 규칙 경로 27개 대화·67턴과 200개 독립 세션·1,000턴을 새 세션으로 3회 통과했다.
