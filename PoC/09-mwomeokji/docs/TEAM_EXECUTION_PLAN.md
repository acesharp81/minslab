# ㅁㅁㅈ 팀 프로젝트 진행 계획

상태: **팀 공유 준비**. 이 문서는 팀원에게 전달할 작업 순서와 합의 지점을 정한다. 제품·기술 근거와 홈페이지 적합성 검토는 [PLAN.md](PLAN.md)에 있다. 팀 공유 전에는 구현·서비스 공개를 시작하지 않는다.

## 1. 공유할 자료와 시작 조건

팀원에게 이 폴더의 `README.md`, `docs/PLAN.md`, 본 문서와 원본 요구사항을 함께 전달한다. 첫 회의에서 데모 매장·대상 사용자·팀 인원·발표일을 확정하고, 아래 역할의 담당자를 정한다. 결정사항은 이 폴더의 `docs/DECISIONS.md`에 날짜·대안·근거와 함께 기록한다.

| 역할 | 맡을 일 |
| --- | --- |
| 제품·UX | 고객/점주 여정, 모바일 화면, 접근성, 한국어·영어 문구, 사용성 검증 |
| 도메인·데이터 | 메뉴/옵션/알레르기 검증 모델, 룰 추천, 가격·주문 무결성, seed |
| 대화·AI | Mock/실 LLM·STT adapter, 발화 구조화, Jev 실험과 실패 시 룰 복귀 |
| 통합·운영 | 독립 실행, DB, 루트 환경변수 전달, 홈페이지 경로, CI·데모 운영 |

한 사람이 여러 역할을 맡아도 된다. 코드 소유권은 작업 단위로 나누고, 메뉴·가격·안전 규칙 변경은 도메인 담당과 제품 담당이 함께 검토한다.

## 2. 첫 회의에서 확정할 결정

1. 핵심 데모 사용자와 매장 유형, 15~50개 데모 메뉴의 실제 정보 출처.
2. 땅콩 등 알레르기와 선택 옵션·교차 접촉 정보를 누가 어떤 근거로 확인할지.
3. 매장/테이블 QR을 실제 인쇄할지, 화면 시연으로 대체할지.
4. 한국어·영어 외 언어와 OCR, 실 AI, Jev를 발표 범위에 넣을지.
5. 최종 시연 환경의 HTTPS 주소, 점주 데모 계정, 테스트 기기.

합의 전에도 Mock 기반 주문 흐름의 설계·테스트 데이터 작성은 가능하다. 외부 API 키나 실매장 데이터는 팀 문서·채팅·커밋에 붙이지 않는다.

## 3. 작업 순서

| 순서 | 결과물 | 팀 검토 기준 |
| --- | --- | --- |
| 0. 공유·합의 | 역할, 데모 범위, 메뉴 확인 책임, 결정 기록 | 팀 전체가 주문 안전 원칙과 Mock 결제 범위를 이해 |
| 1. 독립 기반 | Next.js/TypeScript, 전용 PostgreSQL, seed, Mock provider, 실행 문서 | 루트 API 키 없이 앱 실행, 기존 PoC 영향 없음 |
| 2. 한 주문 완주 | QR 진입, 메뉴·텍스트 추천, 장바구니, 서버 총액, Mock 결제, 점주 접수 | 고객 요청부터 점주 화면까지 E2E 1건 통과 |
| 3. 안전·접근성 | 알레르기/식이 확인, 옵션 검증, 품절·가격 변경, 큰 글씨, 텍스트 폴백 | unknown을 안전 추천하지 않고 잘못된 주문을 거부 |
| 4. 음성·그룹 | 마이크/STT Mock, 권한 거부 폴백, 한 기기 그룹 조합 | 모바일 실기기와 그룹 예산·개인 제약 테스트 통과 |
| 5. 홈페이지 연결 | 전용 프록시, 공개 카드, 전체 화면 링크, 데모 대본 | 동일 출처 URL·HTTPS·장애 격리 확인 후 공개 |
| 6. 선택 실험 | 실 LLM, Jev batch, OCR 초안·점주 승인 | 룰 단독 주문 유지, 비용/품질 측정, 승인 전 게시 없음 |

일정은 공유 시점부터 역산한다. 발표까지 4주라면 0~5를 필수로 하고, 6은 검증된 기능만 시연한다. 매 단계 종료 시 타입 검사·린트·핵심 단위/통합 테스트·관련 Playwright smoke test를 실행한다.

## 4. 함께 작업하는 방법

- 브랜치는 `poc9/<작업명>`으로 만들고 작은 PR로 병합한다. PR에는 사용자 흐름, DB/안전 영향, 실행 방법, 테스트 결과를 적는다.
- 마이그레이션은 되돌리는 방법을 함께 기록한다. 가격/알레르기/주문 로직의 변경은 테스트와 데모 데이터를 같은 PR에 포함한다.
- API 키는 저장소 루트 `.env`에서 서버 런타임으로 필요한 값만 전달한다. 팀원은 각자 로컬 루트 `.env`를 관리하고, 저장소에는 변수 이름과 Mock 설정만 문서화한다.
- UI는 360px 모바일 화면과 키보드 조작을 기준으로 검토한다. 음성 실패 시에도 동일한 주문을 텍스트/터치로 완료할 수 있어야 한다.
- 팀원 간 결정이 필요한 항목은 추측해 구현하지 말고 `docs/DECISIONS.md`의 열린 결정으로 남긴다. 이미 확정한 기술 선택은 [PLAN.md](PLAN.md)를 따른다.

## 5. 완료 판정

데모는 “알레르기와 맵기 설정 → 3인·예산 조건 추천 → 메뉴 수정 → 서버 재계산 → Mock 결제 → 점주 접수”를 한 번에 보여준다. 메뉴/가격/옵션을 AI가 만들지 않고, 알레르기 정보가 불명확한 메뉴를 안전 추천하지 않으며, 주문 중 품절·가격 변경과 중복 전송을 서버가 처리해야 한다. 룰 단독·키 없는 Mock 모드에서도 이 흐름이 완성되어야 한다.
