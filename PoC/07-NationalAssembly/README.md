## 1. 문서 이용과 독자별 매뉴얼 제작

### 1.1 독자별 읽기 범위

| 독자 | 먼저 읽을 범위 | 제작할 매뉴얼의 목적 |

| 유지관리사업자·서비스 운영자 | 8~13장, 15~16장 | 수집·보고서 생성 상태 점검, 장애 복구, 사용량 관리, 배포·백업·인수 |

## 2. 서비스 범위·용어·자료 권위

### 2.1 제공 범위

| 영역 | 제공 내용 | 출처·처리 방식 |
|---|---|---|
| 국회 | 예정 일정, 감시 대상 생방송, 자막, 회의 보고서, 공식 회의록·연결 의안 | 검증된 국회 공식 API·중계·회의록. 행안위·법사위·예결위·본회의 등을 대상으로 구성 |
| 정부·국무회의 | KTV 일정·방송, 전사, 회의 결과, 부처보고·대통령 지시·추가 발표 | KTV 공개 방송과 정부 공식 발표. 음성 전사는 AI 결과 |
| 관심주제 | 문구 감지, 화면 알림, 선택형 카카오 전송, 지금까지 보고서 | 저장된 발언과 사용자가 등록한 규칙 |
| 주제별 보고서 | 기관·주제·기간 검색, 요청형 보고서, 외부도구용 자료 | 현재 서비스에 저장된 회의·공식 자료 |
| 인사이트 | 정부↔국회 흐름, 쟁점 추세, 제도화 연결, 일정·온톨로지 | 저장 자료의 근거 관계와 결정론적 집계 |

검색은 인터넷 전체 검색이 아닙니다. 수집하지 않은 회의나 아직 발표되지 않은 공식 문서는 결과에 포함되지 않습니다. 외부 출처의 계약과 확인 기록은 [DATA_SOURCES.md](docs/DATA_SOURCES.md)를 따릅니다.

### 2.2 세 종류의 상태

| 축 | 값 | 의미 |
|---|---|---|
| 회의 생명주기 | `SCHEDULED / LIVE / ENDED / CANCELED` | 회의가 예정·진행·종료·취소 상태인지 |
| 자료 권위 | `LIVE / PROVISIONAL / OFFICIAL` | 방송 원문·AI/규칙 잠정 결과·공식 문서인지 |
| 출처 매칭 | `MATCHED / UNRESOLVED / CONFLICT` | 방송과 공식 자료를 연결했는지, 미확정인지, 충돌하는지 |

`ENDED + PROVISIONAL + UNRESOLVED`이면 회의는 종료됐고 잠정 보고서는 있지만 공식 자료 연결은 끝나지 않은 상태입니다. 그 조합만으로 장애라고 판단하지 않습니다.

공식 자료를 근거로 작성한 **AI 요약도 요약 자체는 AI 해석**입니다. 공식 원문과 같은 권위로 승격하지 않습니다. 공식 자료가 도착하면 초안을 삭제하지 않고 별도 버전과 대조 관계를 저장합니다.

### 2.3 화면에서 쓰는 단위

| 용어 | 의미 |
|---|---|
| 자막 조각·revision | 수집한 텍스트 조각과 그 수정 버전 |
| 발언 묶음 | 같은 화자의 연속 자막 등을 연결한 원문 열람 단위. 정확한 인물명 확인과는 별개 |
| 대주제 | 관련 세부 쟁점을 묶어 보고서를 읽는 상위 제목 |
| 소주제·세부 쟁점 | 특정 사안의 질의·답변·입장·요구를 정리한 단위 |
| 도출 과제 | 직접 근거가 있는 자료 제출·검토·개선·조치 요청 등 후속 행동 |
| 근거 발언 | 요약·쟁점·과제에 연결된 원문. 같은 발언이 여러 쟁점의 근거일 수 있음 |
| 온톨로지 | 세부 쟁점을 공통 정책 분야·기관·개념으로 연결하는 분류 체계 |
| 비공식 정리 완료 | 잠정 보고서의 처리·검증 단계가 완료됨. 공식 사실 확정을 뜻하지 않음 |
| 공식 정리 완료 | 공식 자료 반영 단계가 완료됨. 비공식 정리 완료 태그도 유지 |

대주제 수, 세부 쟁점 수, 발언 묶음 수, 과제 수는 서로 다른 단위입니다. 발언이 여러 쟁점을 포함하거나 여러 발언이 한 쟁점으로 합쳐지므로 숫자가 같을 필요는 없습니다.

## 3. 처음 사용자 한 장 안내 — U-01

### 3.1 네 메뉴에서 바로 시작하기

| 원하는 일 | 누를 순서·입력 예 | 확인할 결과 |
|---|---|---|
| 지금 회의 보기 | **알람·실시간 → 진행 중 회의 선택 → 영상·발언 보기** | 현재 방송, 화자별 발언, 누적 주제·과제 초안 |
| 지난 회의 읽기 | **회의 보고서 → 회의 카드 → 대주제 펼치기 → 근거 발언** | 대주제별 요약·세부 논의·도출 과제와 연결된 원문 |
| 여러 회의에서 자료 찾기 | **주제별 보고서 → 소관 부처 `행안부` 또는 주제 입력 → 기간 설정 → 자료 검색** | 전체 검색 결과. 항목 클릭으로 해당 회의 보고서 이동 |
| 흐름·일정 보기 | **인사이트 → 관심 카드의 전체 보기 → 찾기**, 또는 **달력 날짜 선택** | 관련 전체 목록·세부 근거·선택일 일정 |

### 3.2 필요한 결과 저장하기

- 요약한 문서: **회의 보고서 → 요약 문서 · 인쇄/PDF → 인쇄 · PDF 저장**.
- 발언 원문: **회의 보고서 → 전체 발언 기록 보기 → MD 다운로드**.
- 여러 회의 종합 문서: **주제별 보고서 → 자료 검색 → 보고서 작성**. 작성에는 카카오 계정 연결이 필요합니다.
- 직접 외부 AI 도구에서 작성: **자료 검색 → 외부도구 사용 → 프롬프트 복사 또는 MD 파일 다운로드**.

처음에는 로그인 없이 공개 회의와 근거를 읽을 수 있습니다. 관심주제는 브라우저 세션에 저장되고, 같은 카카오 계정을 연결하면 다른 기기에서도 계정에 저장된 설정을 불러옵니다. 두 서비스 주소는 동일 데이터를 사용하지만 브라우저 쿠키는 도메인별이므로 새 주소에서는 다시 연결할 수 있습니다.

## 4. 사용자 기능: 알람·실시간

### 4.1 생방송과 실시간 초안 — U-02

1. **알람·실시간**에서 진행 중이거나 최근 24시간 내 진행된 회의를 선택합니다.
2. 영상과 화자별 발언을 읽습니다. **이전 발언**으로 이동하면 최신 추적이 해제되고 **최신으로**를 누르면 다시 따라갑니다.
3. 영상 아래 **실시간 초안 보고서**에서 주제·과제를 누릅니다. 해당 논의 카드와 근거 팝업으로 이동합니다.
4. 필터에 주제·기관·문구를 넣어 관련 초안을 찾습니다. 시네마 모드는 영상을 넓히며 초안 보고서는 유지합니다.
5. 보고서가 준비되면 **회의 보고서 보기**로 완성된 잠정 보고서를 엽니다.

같은 화자의 진행 중 발언은 계속 누적됩니다. 요약·논의 분류는 저장된 완료 발언을 후처리하므로 원문보다 늦게 나타날 수 있습니다. 비슷한 질의·답변·자료 요구는 문맥상 같은 논의로 묶고, 발언 하나를 무조건 주제 하나로 만들지 않습니다.

| 표시 | 읽는 방법 |
|---|---|
| 방송없음 | 감시 대상 공식 중계에 현재 방송이 없는 상태 |
| 정회·계속예정 | 재개를 기다리는 회의. 저장된 발언·초안은 계속 열람 |
| 상태 확인 필요 | 최근 상태 조회가 오래됐거나 실패함. 방송 종료로 단정하지 않음 |
| 정리중·단계별 `n/m` | 저장된 발언을 보고서로 처리 중. 완료된 보고서는 회의 보고서 메뉴에서 확인 |
| 화자 미확인 | 원문에 이름이 없거나 신뢰할 만한 이름 연결이 없음 |

국회는 공식 자막을 우선 수집합니다. 자막 장애 때 설정된 STT 보완 경로를 사용할 수 있습니다. 국무회의는 공개 HLS 음성을 전사하는 경로가 있으므로 맞춤법·인명·전문용어에 오류가 있을 수 있습니다. 화자 번호를 실제 인물로 추정하지 않습니다.

### 4.2 관심주제와 카카오 연결 — U-03

1. **알람·실시간**의 관심주제 등록 영역을 엽니다.
2. 주제명·감지 문구·국회/정부 범위를 입력하고 저장합니다. 설정 후 들어오는 발언부터 감지합니다.
3. 휴대전화 알림이 필요하면 카카오를 연결하고 메시지 전송 선택 동의 후 해당 규칙의 **카카오로도 받기**를 켭니다.
4. 알림함에서 감지 내용을 누르면 주제 요약·발언 흐름·근거 원문을 확인합니다.
5. 규칙 수정·삭제, 개별 알림 삭제, **읽은 기록 정리**로 관리합니다.

현재 알림은 **최초 문구 감지 → 주제 전환 후 관련 발언이 5분간 없을 때 주제 요약 → 정회·종료 시 누적 요약**의 3단계입니다. 과거의 빈도 선택·반복 발송·종료 요약 선택 기능을 현행 조작법으로 안내하지 않습니다. 정회 판단은 공식 상태나 명확한 선포를 사용하며 자막 공백만으로 정회 알림을 보내지 않습니다.

규칙은 최대 20개입니다. 화면 알림은 최신 12건을 표시하며 서버에는 사용자별 최근 50건을 보존하되 발송 대기는 별도로 취급합니다. 카카오 장애가 화면 알림과 근거 저장을 중단시키지는 않습니다.

### 4.3 지금까지 보고서·계정 복귀 — U-03

- 규칙의 **지금까지 보고서**는 진행 중인 회의를 우선하고 없으면 최근 감지 회의를 팝업으로 표시합니다. 저장 요약·원문을 확인하고 Markdown 또는 인쇄/PDF로 보관할 수 있습니다.
- 선택형 관심주제 AI 기능이 켜져 있고 새 근거가 충분하면 요청 시 비동기 보고서가 예약됩니다. 같은 근거의 저장본은 재사용합니다.
- 다른 기기에서 같은 카카오 계정을 연결하면 기존 서버 규칙과 저장 결과를 불러옵니다. 로그인 전에 만든 규칙은 중복 기준에 따라 병합합니다.
- 카카오 연결 해제와 서비스의 전체 기기 세션 폐기는 다른 작업입니다. 공유 기기에서는 세션 종료 범위를 확인합니다.
- 알림이 오지 않으면 규칙 활성 여부, 설정 이후 새 발언 여부, 카카오 연결·선택 동의를 확인합니다. 운영자 재현 방송은 일반 사용자 기능이 아닙니다.

## 5. 사용자 기능: 회의 보고서

### 5.1 열기와 읽기 순서 — U-04

1. **회의 보고서** 메뉴에서 회의 카드를 선택합니다. 초기 목록 이후 항목은 목록 끝으로 이동하면 추가로 불러옵니다.
2. 회의 제목·전체 요약과 **대상 주제 / 도출 과제**를 확인합니다.
3. 대주제를 펼쳐 **소주제 제목 → 발언 묶음의 AI 요약 → 세부 발언 요약 → 관련 과제** 순서로 읽습니다.
4. **근거 발언 N개**, **발언 확인**, **원문 보기**를 눌러 해당 내용의 실제 근거를 확인합니다.

보고서를 처음 열면 첫 번째 주요 논의의 근거 발언이 기본 선택됩니다. Alt+Tab 등 창 포커스 복귀만으로 보고서 전체를 다시 로딩하지 않습니다. 처리 중 결과 갱신과 사용자의 회의 선택은 별도 동작입니다.

PC에서는 근거 패널이 본문과 나란히 표시되고 작은 화면에서는 아래로 배치됩니다. `?report=<방송 ID>#reports` 주소는 회의 선택 복원에 사용합니다. 개인정보를 포함한 계정 보고서 링크와 공개 회의 링크를 구분합니다.

### 5.2 주요 요약·세부 쟁점·원문의 차이 — U-04

| 영역 | 읽을 내용 | 건수가 달라지는 이유 |
|---|---|---|
| 주요 논의 요약 | 대주제·소주제로 정리한 논지와 발언 요지 | 여러 발언을 묶어 요약 |
| 세부 쟁점·과제 연결 | 각 쟁점의 역할·과제·근거 연결 | 하나의 발언에서 여러 쟁점이 나올 수 있음 |
| 근거 발언 | 선택한 주제·요약·과제에 연결된 원문 | 같은 근거가 여러 항목에 쓰일 수 있음 |
| 전체 발언 기록 | 저장된 전체 방송 원문을 시간순으로 열람 | 요약에 직접 연결된 발언만으로 제한하지 않음 |

완료 보고서는 세부 쟁점의 요약 포괄 여부를 검증합니다. “상단에 제목이 적다”는 이유만으로 누락이라고 할 수는 없지만, 독립된 논의나 직접 요구가 요약·상세·근거 어디에도 없으면 점검 대상입니다.

### 5.3 도출 과제와 자료 제출 요구 — U-04

- 과제는 **실제로 요청·약속·지시한 후속 행동**이 근거에 있어야 합니다. 질의·답변·입장·비판을 모두 과제로 표시하지 않습니다.
- **자료 제출 요구는 관련 주제의 도출 과제에 배치**합니다. 자료 요구라는 이유만으로 모든 정책 사안과 분리된 독립 대주제로 모으지 않습니다.
- 같은 주제 안의 중복 요구는 묶을 수 있지만 제출 대상·수치·기간·담당 기관·직접 근거를 보존합니다.
- “자료 요구부터 받겠습니다” 같은 진행 안내는 제출 과제가 아닙니다. 실제 제출 요구가 같은 발언에 함께 있으면 그 직접 요청은 별도로 추출합니다.
- **원문 보기**는 가능한 경우 과제를 직접 언급한 구간을 보여 줍니다. 동일 화자의 주변 발언 전체에 과제를 반복 부착하지 않습니다.
- 대상이나 기관을 특정할 근거가 부족한 요구는 별도 사유와 원문을 보존합니다. 연결률을 높이기 위해 임의의 주제에 넣지 않습니다.

### 5.4 보조 원문 접기·펼치기 — U-05 · 2026-10-28 갱신

보고서의 부가 정보는 강조 상자 대신 **한 줄의 텍스트 버튼**으로 표시합니다. 예시는 `실시간 논의 재분석 후 원문 불명확 N묶음`, `재분석 후 원문 불명확 N건`, `회의 진행·의례 원문 N건`입니다. 실제 존재하는 항목만 표시하므로 회의마다 종류와 건수가 다릅니다.

- 처음에는 모두 접혀 있습니다.
- 제목·펼침 표시를 누르면 **그 항목에 속한 내용만** 바로 아래에 표시합니다.
- 다른 항목을 누르면 이전 항목은 접힙니다. 같은 항목을 다시 누르면 닫힙니다.
- Tab으로 이동하고 Enter/Space로 조작할 수 있습니다. 좁은 화면에서는 제목 줄이 자연스럽게 줄바꿈됩니다.
- `자동 재분류 대기`는 시스템 작업 대기이며, `재분석 후 원문 불명확`은 재분석 후에도 대상·내용을 특정하기 어려운 원문입니다. 일반 사용자에게 수동 분류를 맡기는 기능이 아닙니다.

### 5.5 요약 문서·그래프·인쇄/PDF — U-06

1. 보고서 상단의 강조된 **요약 문서 · 인쇄/PDF**를 누릅니다.
2. 미리보기 첫머리의 **회의 전체 요약 → 주제별 분포 → 키워드 빈도**를 확인합니다.
3. 아래의 **대주제 → 소주제 → 발언 요약·과제** 본문을 읽습니다.
4. **인쇄 · PDF 저장**에서 프린터 또는 브라우저의 PDF 저장 대상을 선택합니다.

| 그래프 | 집계 기준 | 해석 시 주의 |
|---|---|---|
| 주제별 분포 | 고유 소주제 수. 상위 대주제 6개와 나머지 합계 | 발언 시간·정책 중요도·찬반 비중이 아님 |
| 키워드 빈도 | 소주제 제목 중 해당 단어를 포함한 제목 수. 상위 8개 | 원문 전체 단어 출현 횟수가 아님 |

전체 보고서 데이터를 읽은 뒤 문서를 구성합니다. 화면에서 접힌 주제도 출력 본문에 포함합니다. A4 인쇄는 전체 요약·그래프 뒤에 본문을 이어 배치하며 브라우저·글꼴에 따라 페이지 나눔은 달라질 수 있습니다. 미리보기를 닫으면 읽던 보고서로 복귀합니다.

### 5.6 전체 발언 팝업·MD 다운로드 — U-07 · 2026-10-28 추가

1. 회의 보고서에서 **전체 발언 기록 보기**를 누릅니다.
2. 현재 보고서 위 팝업에서 **번호 → 수집 시각(KST) → 화자 → 발언 원문**을 시간순으로 읽습니다.
3. **MD 다운로드**를 누르면 `<회의명>_전체발언.md` 파일을 저장합니다.
4. **닫기** 또는 Esc로 팝업을 닫습니다. 읽던 회의·보고서 상태는 유지됩니다.

MD는 미리보기 일부만이 아니라 **화면과 같은 전체 발언 목록**을 담습니다. 회의명, 전체 건수, 한국시간, 화자, 원문, 비공식 자료 안내, 회의 보고서 주소를 포함합니다. 요약문으로 대체하거나 긴 발언을 자르지 않습니다. 형식 문자가 제목·HTML로 오인되지 않게 Markdown용 이스케이프를 적용합니다.

이 기능의 원문은 **LIVE/STT 저장본**이며, 시각은 수집 시각입니다. 공식 속기록이나 영상의 정확한 타임코드로 안내하지 않습니다. 화자 이름이 없으면 `화자 미확인`으로 표시합니다. 로딩 실패 시 **다시 불러오기**를 제공하고 로딩 중·빈 기록에서는 다운로드를 비활성화합니다.

[실제 데스크톱 화면](docs/evidence/REPORT_NAVIGATION_20261028/transcript-desktop.png) · [모바일 화면](docs/evidence/REPORT_NAVIGATION_20261028/transcript-mobile.png)

### 5.7 공식 자료와 국무회의 결과 — U-04

- 자료 선택은 보고서의 준비 상태에 따라 구조화 보고서·LIVE/STT 초안·공식 대조본을 제공합니다. 공식 원문이 준비돼도 모든 AI 요약을 공식 문장으로 취급하지 않습니다.
- 공식 근거의 완성형 문장과 화자 정보를 확인할 수 있습니다. 변경 비교는 의미 있는 수치·담당 기관·결정·과제의 변화를 중심으로 표시합니다.
- 공백·문장부호·단순 문체 차이를 사실 변경으로 과장하지 않습니다. 저유사도 전체 재작성은 원문 대안과 대조 근거를 보존합니다.
- 국무회의 결과는 **부처 보고 내용 → 대통령 지시 → 부처 추가 발표**를 구분하며 심의안건은 별도로 제공합니다. 회차·한국시간 날짜 등으로 연결이 확인된 자료만 함께 표시합니다.
- 공식 자료가 아직 없으면 비공식 보고서를 계속 읽을 수 있습니다. `공식 정리 완료`가 생겨도 `비공식 정리 완료`와 초안 이력은 보존합니다.

## 6. 사용자 기능: 주제별 보고서

### 6.1 자료 검색과 해당 회의 이동 — U-08 · 2026-10-28 갱신

1. **주제별 보고서**에서 소관 부처 또는 주제를 하나 이상 입력합니다. 주제는 두 글자 이상입니다.
2. 시작일·종료일, 국회/정부/전체 범위를 선택합니다.
3. **자료 검색**을 누릅니다. 검색은 저장 자료를 조회하며 외부 AI를 호출하지 않습니다.
4. 검색 건수와 결과 목록을 확인합니다. 목록 내부를 스크롤해 전체 자료를 읽습니다.
5. **결과 항목을 클릭하거나 Tab → Enter**로 해당 회의 보고서를 엽니다.
6. **주제별 보고서** 탭으로 돌아오면 같은 페이지에서 입력했던 검색 조건과 결과를 계속 볼 수 있습니다.

검색 결과는 특정 개수만 잘라 표시하지 않습니다. 현재 회의 카드에 아직 로딩되지 않은 과거 국회 보고서도 방송 ID로 직접 열 수 있습니다. 정부 공식 결과는 해당 공식 회의로 연결하며 찾을 수 없으면 오류를 안내합니다.

`행안부`와 `행정안전부`처럼 등록된 약어·정식 명칭은 양방향 검색을 지원합니다. 임의 오탈자까지 모두 해석하는 기능은 아닙니다. [기관명·약어 목록](docs/MINISTRY_SEARCH_ALIASES.md)을 기준으로 확장합니다.

### 6.2 서비스에서 보고서 작성 — U-09

1. 자료 검색 결과를 확인한 뒤 **보고서 작성**을 누릅니다. 작성에는 카카오 계정 연결이 필요합니다.
2. 검색 조건·선택 근거를 저장한 비동기 작업이 시작됩니다. 작성 중에는 상태를 확인하고 중복 요청을 반복하지 않습니다.
3. 결과는 **전체 요약 → 정책적 시사점 → 세부 논점 → 후속 과제·근거 → 전체 상세 내역** 순서로 읽습니다.
4. 근거 링크를 누르면 해당 회의 보고서로 이동합니다. 저장된 보고서는 최근 보고서 목록에서 다시 열 수 있습니다.
5. Markdown 다운로드나 브라우저 인쇄/PDF로 저장합니다.

핵심 시사점은 보통 2~5개로 통합합니다. **시사점 수 제한은 입력 근거를 버려도 된다는 뜻이 아닙니다.** 전체 논의·과제 상세 내역과 출력에는 저장 근거를 포함하며, 본문에 연결되지 않은 근거는 제한된 보완 단계로 처리합니다. 끝까지 검증하지 못하면 완료로 표시하지 않습니다.

같은 조건·근거·모델·프롬프트 버전의 완료본은 재사용합니다. 실제 생성은 검증·보완 때문에 여러 요청이 될 수 있으므로 “보고서 한 건은 외부 모델 정확히 한 번 호출”로 안내하지 않습니다.

### 6.3 외부도구용 자료 — U-09

**자료 검색 → 외부도구 사용**에서 작성 명령과 검색 근거를 묶은 Markdown을 만듭니다. **프롬프트 복사** 또는 **MD 파일 다운로드** 후 사용자가 선택한 외부 도구에 직접 전달합니다. 복사 용량이 큰 경우 파일 다운로드를 사용합니다.

이 내보내기 자체는 모델을 호출하지 않습니다. 사용자가 외부 도구에서 생성한 문서는 국정ON의 서버 검증·저장 보고서와 별개입니다.

### 6.4 범위·실패·기존 보고서 해석

- 입력 한도를 넘으면 자료를 몰래 줄이지 않고 범위를 줄이도록 안내합니다. 검색·근거 열람·외부도구용 내보내기는 별도로 사용할 수 있습니다.
- “입력 근거 중 본문에 연결되지 않은 내용” 안내는 전체 포괄 검증 실패입니다. 상세 자료를 보존하되 완성본으로 표시하지 않습니다.
- 과거 보고서의 **검색 범위 보완 근거**는 같은 조건에서 추가 확인한 자료입니다. 이전 본문이 추가 자료까지 새로 요약됐다는 뜻은 아닙니다.
- 보고서는 검색 당시의 자료를 기준으로 합니다. 이후 새 회의나 공식 자료가 들어오면 같은 검색어라도 결과 범위가 달라질 수 있습니다.
- 작성 제한·계정 연결·세션 오류는 화면 안내를 따릅니다. 공개 회의 조회와 개인 소유 보고서 API의 권한 범위는 다릅니다.

## 8. 처리 단계·분류 기준·완료 지표

이 장부터는 운영·개발 설명을 포함합니다. 일반 사용자용 매뉴얼에는 상태의 의미와 지표 해석만 발췌합니다.

### 8.1 회의 처리 흐름

```text
공식 일정·방송 감지
  → 원본 자막/오디오 저장 → 화자 발언 묶음
  → 발언 요약·실시간 논의 분류
  → 회의 종료 확인·남은 수집 마감
  → 발언 분석 → 통합 → 주제 검증 → 정책 분류 → 세부 요약 → 최종 확인
  → 비공식 정리 완료
  → 공식 회의록/브리핑 수집·매칭·대조
  → 공식 정리 완료 (비공식 정리 완료와 원문 이력 유지)
```

- 진행 태그의 `n/m`은 **해당 단계에서 저장 완료한 처리 단위 수 / 전체 대상 수**입니다. 발언 분석, 통합 배치, 쟁점 요약은 단위가 다릅니다.
- 처리 중에는 완료·진행·앞으로 할 단계를 함께 표시하고 완료되면 비공식/공식 완료 태그로 정리합니다.
- 같은 방송의 정회·속개·늦은 final 자막은 입력 cursor·fingerprint 변화로 판단합니다. 이전 결과를 보존하며 바뀐 범위를 반영합니다.
- 30분 자막 공백으로 만든 중간 회차 checkpoint는 잠정적인 화면·처리 구간입니다. 공식 종료나 정회 알림의 단독 근거로 사용하지 않습니다.
- 한 회의의 재시도 대기가 다른 처리 가능한 회의를 모두 막지 않도록 완료 배치 재사용·부분 진행·대기열 재개를 사용합니다.

### 8.2 분류·과제·요약 검증 규칙

| 검증 대상 | 유지할 규칙 | 실패 시 |
|---|---|---|
| 주제 | 기존 문맥·기관·대상·사안으로 묶고 독립된 논의는 보존 | 문맥 재분류, 필요하면 새 세부 쟁점 |
| 발언 역할 | 질의·답변·입장·요구·진행을 구분 | 과제 과잉 추출과 진행 문구 오분류 재검토 |
| 자료 요구 | 직접 제출 요구와 그 정책 주제를 연결 | 대상 불명확 사유와 원문 보존 |
| 직접 근거 | evidence ID와 원문 구간이 현재 발언에 존재해야 함 | 잘못된 ID·범위·주변 발언 전이는 거절 |
| 내용 포괄 | 독립된 쟁점·필수 근거가 요약 또는 상세 내역에 포함 | 누락 부분만 보완 후 전체 검증 |
| 표현 품질 | 원문 수치·날짜·이름·언어·문장 길이 검증 | 실패 필드 교정. 원문 또는 숫자를 지워 통과시키지 않음 |
| 완료 판정 | 구조화·재검토·정책 분류·세부 요약·근거 검증 상태 대조 | 대기·재시도·검토 상태 유지 |

문맥은 생략된 대상을 이해하는 데 사용할 수 있지만 **직접 인용의 범위는 해당 발언**이어야 합니다. 다른 화자의 주장이나 인접 발언의 과제를 현재 발언에 옮기지 않습니다.

원문 자체가 끊겼거나 불명확한 조각은 최종 요약 문장을 만들어 채우지 않습니다. `SOURCE_LIMITED` 등으로 사유를 남기고 보조 원문에서 확인하도록 합니다. 반면 단순 모델 통신 실패나 아직 실행하지 않은 재분류는 같은 상태로 숨기지 않습니다.

### 8.3 지표를 읽는 방법

| 지표 | 분자·분모 또는 확인 내용 | 의미하지 않는 것 |
|---|---|---|
| 단계 진행 `n/m` | 해당 단계 완료 단위 / 대상 단위 | 회의 전체의 동일한 발언 건수 |
| 세부 쟁점 요약 포괄 | 요약된 쟁점 수 / 대상 쟁점 수 | 문장 의미가 모두 정확하다는 보증 |
| 근거 포괄 | 요약에 연결된 원문 근거 / 대상 원문 근거 | 모든 원문이 단일 주제에만 속한다는 뜻 |
| 재분류 대기·분석 실패 | 아직 완료하지 못한 분류 작업 수 | 원문 자체가 불명확하다는 확정 |
| 원문 불명확 | 재검토 후에도 특정하기 어려운 조각 수 | 무조건 처리 실패 또는 삭제 대상 |
| 온톨로지 적용률 | 현재 집계 대상 중 공통 정책 분류에 연결된 비율 | 보고서 완성률·사실 정확도 |
| 도출 과제 수 | 직접 후속 행동 근거가 있는 과제 | 질의·답변 전체 수 |

온톨로지 수치를 전후 비교할 때에는 **같은 회의 집합, 같은 입력 버전, 같은 분모, 같은 제외 기준, 같은 분류 버전**인지 확인합니다. 새 쟁점이 늘어 분모가 커진 수치를 과거 요약 중심 수치와 바로 비교하지 않습니다. [분모 비교 검증](docs/ONTOLOGY_COVERAGE_COMPARISON_20261019.md)을 참고합니다.

### 8.4 최근 검증 표본의 범위

[2026-10-28 보고서 점검](docs/REPORT_COMPLETION_AUDIT_20261028.json)은 그 시점의 **56개 보고서, 7,084개 쟁점, 12,730개 원문 근거**에 대해 요약 포괄 완료와 재분류 대기 0건을 기록합니다. 원문 불명확 조각 25개와 특정 정책 주제로 연결하기 어려운 공통 요구 1개는 사유와 함께 보존했습니다.

## 9. 시스템 구성과 데이터

### 9.1 실행 경계

```text
브라우저
  ├─ kjon.aigov.go.kr의 Nginx 가상호스트
  └─ 기존 minslab 경로의 공개 프록시
          ↓
   PoC7 FastAPI + 정적 web/ (운영 loopback :18070)
          ↓
   PostgreSQL ← 수집·요약·분류·공식화·알림 워커
          ↕
   data/raw · data/processed · 사용량 장부

외부 공개 출처 → 수집 워커 → 원본 저장
AI 요청 워커 → NIM / OpenRouter 게이트웨이 / 선택형 보조 모델
Kakao outbox → notification-worker → 선택 동의한 사용자
```

- Python 3.12 기반 FastAPI, PostgreSQL 16, HTML/CSS/JavaScript 정적 프런트엔드를 사용합니다.
- 역할별 워커는 같은 코드 이미지·PostgreSQL을 공유합니다. 단일 “worker”라는 설명으로 현재 다중 워커 구성을 생략하지 않습니다.
- 원본과 공식값은 보존하고 화면용 읽기 모델을 별도로 생성합니다. 브라우저 조회 자체가 외부 LLM 요청을 만드는 구조는 아닙니다. **보고서 작성·지금까지 보고서**처럼 명시적 생성 요청은 예외입니다.
- 런타임은 PoC7 디렉터리·전용 환경 설정만 사용합니다. 부모 저장소의 `.env`·모듈·가상환경을 불러오지 않습니다.
- OpenRouter 게이트웨이는 계정 공유 사용량을 계량할 수 있습니다. 다른 PoC의 사용량이 공유 한도에 영향을 주는 것과 다른 PoC 파일을 런타임에서 읽는 것은 구분합니다.

## 10. 모델 배정·사용량·재시도 — O-02

### 10.1 작업별 우선순위

`MODEL_WORKLOAD_GROUPS_ENABLED=true`가 새 운영 정책입니다. false는 이전 정책의 복구용입니다.

| 그룹 | 작업과 경로 |
|---|---|
| 실시간 부분요약 | **GPT-5.4 mini + Nemo3.5 VL(OpenRouter)** 두 실행 경로가 서로 다른 발언 묶음을 병렬 처리. 일반 구조화·세부 요약은 Mini 우선, OpenRouter 대체 |
| 통합+공식자료 대조 | **GPT-5.4 → GPT-6.1 Terra**. 회의 합성·쟁점 통합·고난도 검증·주제별 보고서·공식화 비교. 호출 실패 또는 회의 합성의 의미 검증 실패 시 다음 경로 사용 |
| 음성 | Mistral Voxtral. 기존 수집·전사 경로 유지 |

NIM·Gemini·Groq는 기본 후보에서 제외합니다. Sol은 자동 호출하지 않습니다. 관심주제 알림의 작은 브리핑은 기존 OpenRouter 경로입니다.
실시간 경쟁은 같은 발언을 양쪽 모델에 동시에 전송하는 방식이 아닙니다. PostgreSQL 세션 잠금으로 원문 해시·프롬프트 버전별 작업을 점유하고, 회의마다 두 발언씩 처리한 뒤 다음 회의로 이동합니다. 저장된 유효 결과를 다시 확인하여 재사용합니다. 근거·한국어·과제 검증과 보고서 형식은 유지합니다.

### 10.2 내부 배정량과 초기화

**서비스 운영 장부이며 OpenAI 조직 전체의 실제 크레딧 잔액 API가 아닙니다.** 다른 프로젝트 사용분은 공유 장부나 `OPENAI_OTHER_PROJECTS_MINI_TOKENS` / `OPENAI_OTHER_PROJECTS_MAIN_TOKENS`로 차감해야 합니다.

| 모델 | 운영 배정 | 초기화 |
|---|---|---|
| GPT-5.4 mini | 입력+출력 하루 10,000,000토큰 | UTC 00:00 / 한국시간 09:00 |
| Nemo3.5 VL | OpenRouter 공유 게이트웨이 운영 950회, 계정 상한 1,000회 | UTC 00:00 / 한국시간 09:00 |
| GPT-5.4 | 입력+출력 하루 1,000,000토큰, Mini와 별도 | UTC 00:00 / 한국시간 09:00 |
| GPT-6.1 Terra | 이번 주기 잔여 $8에서 시작, 이후 월 $100의 사용자 지정 배정 | 한국시간 매월 말일 00:00. 실제 공급자 갱신 시각과 별도인 수동 정책 |
| Mistral | 기존 월 $10 설정, STT 시간·단가 기반 | 기존 월간 장부 |

Terra를 일일 무료 토큰 모델에 포함하지 않습니다. 계정에 표시된 무료 목록에 없으므로 유료 비용 장부에서 관리합니다. 첫 주기의 ID·종료 시각·배정액은 `OPENAI_CREDIT_GRANT_ID`, `OPENAI_CREDIT_EXPIRES_AT`, `OPENAI_CREDIT_BUDGET_USD`입니다. `OPENAI_CREDIT_MONTH_END_RENEWAL=true`와 `OPENAI_CREDIT_MONTHLY_BUDGET_USD=100`이 다음 말일의 새 장부를 엽니다. 31일→30일·윤년·연도 변경을 지원하며 1일에 다시 초기화하지 않습니다. 이는 사용자가 요청한 추정 예산이고 실제 무료 크레딧 충전을 보장하지 않습니다.

요청 전에 원자적으로 입력·최대 출력을 예약하고 실제 usage로 정산합니다. 응답 불명의 실패는 보수적으로 차감하고, HTTP 400/401/403/404/429로 거절된 요청은 토큰을 차감하지 않습니다. 날짜·주기를 넘긴 정산도 처음 예약한 장부로 돌아갑니다. Terra 비용은 Standard 기준 입력 $1/백만·출력 $5/백만, 입력 272K 초과 시 $2/$7.5로 계산하며 캐시 할인은 보수적으로 제외하며 캐시 쓰기는 보존 기간 미확인 시 12시간 요금의 추가분을 예약 범위에서 보수적으로 반영합니다. [공식 가격](https://developers.openai.com/api/docs/pricing)

조직 지출 상한에 의한 429는 다른 OpenAI 모델로 우회하지 않고 공유 차단 상태로 다음 배정 주기까지 대기합니다. 일반 속도 제한 429는 모델별 90초 대기입니다. OpenAI 조직 상한 $100 설정은 별도 보호 장치이며, 공급자 안내상 적용 지연으로 소폭 초과할 수 있습니다. 무료 크레딧과 현금 충전액을 프로그램이 직접 구분·조회하는 기능은 없습니다.

### 10.3 사용량 화면과 장부

우측 상단은 **실시간 부분요약 | 통합+공식자료 대조 | 음성**의 세 그룹입니다. 데스크톱 폭은 이전 560px의 70%인 392px이며, 작은 화면에서는 가독성을 위해 전체 폭으로 배치합니다. `GPT-5.4 mini`, `Nemo3.5 VL`, `GPT-5.4`, `6.1 Terra`, `Mistral` 각각의 남은 토큰·횟수·달러를 표시합니다. 모델명을 가리키거나 키보드 포커스로 상세 수치·주기·집계 범위를 확인합니다. 확인 실패를 100% 잔여로 표시하지 않습니다.

`GET /api/ai/usage`의 `workload_groups`가 새 표시의 기준이며 기존 `providers` 필드는 호환용으로 유지합니다. `openai_group_daily_usage`, `openai_credit_grant_usage`, `model_provider_cooldowns`가 운영 장부입니다. 이전 `openai_daily_token_usage`는 삭제하지 않고 전환 시 Mini 이력으로 보수적으로 이관합니다.

운영자 상세 확인:

```bash
curl -fsS http://127.0.0.1:18070/api/ai/usage
curl -fsS http://127.0.0.1:18071/internal/status
```

- OpenRouter의 게이트웨이 `reserved`는 무료 모델 요청 시도 기준입니다. 성공 보고서 수와 다릅니다.
- PoC4와 같은 계정을 공유하면 무료 요청이 합산될 수 있습니다. 별도 유료 사용처의 계량은 무료 950회와 구분합니다.
- 토큰 예산은 요청 전에 예약하고 성공 응답으로 정산합니다. 사용량을 알 수 없는 실패는 보수적인 예약량이 남을 수 있습니다.
- 대시보드 비율만으로 실제 선택된 모델을 단정하지 않습니다. 작업·provider·model·응답 오류·예산 차단 이력을 함께 봅니다.
- 사용량·비용 세부 설명과 화면 캡처는 운영자 매뉴얼에만 포함합니다.

### 10.4 다음 날 재개와 실패 분리

1. 일일 예산 때문에 대기한 영속 작업은 다음 사용일의 가용량이 생기면 worker가 이어서 처리합니다. UTC 일 기준 작업은 **다음 KST 09:00 이후 처리 주기**에 재개할 수 있습니다. 정확히 09:00에 완료된다는 예약 보장은 아닙니다.
2. NIM의 일반 429·일시 오류는 당일 cooldown·재시도 또는 다른 공급자 전환 대상입니다. 모든 429를 다음 날까지 차단하지 않습니다.
3. 인증 오류, 잘린 JSON, 근거 누락, 숫자·언어 검증 실패는 예산 초기화만으로 해결되지 않습니다. 오류별 교정과 제한된 재시도가 필요합니다.
4. 이미 검증된 발언·분할 통합 결과는 재사용하고 실패 부분만 보완합니다. 긴 통합은 전체 목차·배정 조건을 유지한 부분 작업으로 재개합니다.
5. 원문 재검증은 UTC 일별 제한을 적용합니다. 현재 관련 경로의 최대 9회 등 코드의 retry allowance를 준수하고 수동 실행으로 무제한 반복하지 않습니다.

실제 정책 근거: [model_workloads.py](backend/app/services/model_workloads.py), [작업별 풀 검증](docs/FREE_MODEL_WORKLOAD_POLICY_20261027.json), [재시도 복구 기록](docs/RETRY_RECOVERY_20261027.json).

### 12.1 읽기 전용 기본 점검

sudo python3 scripts/check_runtime.py --scope all
sudo docker ps -a --format '{{.Names}} | {{.Status}}'
sudo docker inspect --format 'status={{.State.Status}} restart={{.HostConfig.RestartPolicy.Name}}' poc07-national-assembly-db

현재 `check_runtime.py`는 운영 컨테이너 16개, DB 네트워크 별칭·영구 볼륨·준비 상태, 내부/공개 HTTP를 포함한 25개 점검을 수행합니다. 이름·포트·배포 구성이 달라지면 검사 계약도 함께 갱신합니다. 전체 `docker inspect`의 환경변수 출력 대신 위처럼 필요한 필드만 조회합니다.

### 12.2 매일·방송 단계별 운영

| 시점 | 확인 | 정상 판단 근거 |
|---|---|---|
| 방송 전 | 공식 일정, 대상 감지, 수집 worker, 저장공간, 모델별 가용량 | 실제 대상 회의·시간 일치, 필요한 worker 가동 |
| 방송 중 | 방송 ID별 final 자막 시각·cursor, 수집 lease, 요약 진행 | 각 방송 원문이 증가하고 다른 방송과 섞이지 않음 |
| 자막 장애 | 공식 자막·STT 상태, 오디오 청크, 전사 실패 | 원본과 전환 사유가 남고 복구 후 공식 자막으로 복귀 |
| 정회·속개 | 공식 상태와 저장 구간, 목록·초안 유지 | 회의가 사라지거나 원문이 초기화되지 않음 |

상태 로그에는 방송 ID·cursor·단계·건수·오류 코드를 남기고 API 키·Authorization·개인 토큰·회의 원문 전체를 진단용 로그에 복사하지 않습니다.

### 12.3 재발 방지 점검

2026-10-19 장애는 Compose 파일과 달리 **실제 DB 컨테이너의 restart policy가 `no`**여서 재부팅 뒤 DB가 복귀하지 않은 사례였습니다. API·worker의 `db` 이름 조회 실패와 두 공개 주소의 장애가 뒤따랐습니다.

현재 저장소의 재발 방지 구성:

- API·worker 배포 전 `check_runtime.py --scope database`로 기존 DB 상태·정책·별칭·볼륨을 확인하고 실패 시 기존 서비스를 중지하기 전에 배포를 중단합니다.
- `poc07-runtime-check.timer`는 부팅 후 및 약 1분 간격으로 점검합니다.
- timer의 `--repair-restart-policy`는 **실행 중인 컨테이너의 정책 이탈만** 교정합니다. 중지한 DB를 자동 시작하거나 DB 볼륨을 재생성하지 않습니다.
- 실패는 systemd 결과와 journal에 남습니다. 외부 운영자 알림 전송 기능까지 포함된 것은 아닙니다.

```bash
sudo systemctl is-enabled poc07-runtime-check.timer
sudo systemctl list-timers poc07-runtime-check.timer
sudo systemctl show poc07-runtime-check.service -p Result -p ExecMainStatus
sudo journalctl -u poc07-runtime-check.service -n 10 --no-pager
```

신규 설치는 [install_runtime_check.sh](scripts/install_runtime_check.sh)와 [systemd 정의](deploy/systemd/)의 설치 경로·계정을 먼저 조정합니다. `unless-stopped`는 명시적 수동 중지 의도를 유지하므로 이것만으로 모든 중단이 자동 복구된다고 안내하지 않습니다.

| 두 주소 모두 502/연결 불가 | DB 상태·기존 볼륨·`db` 별칭 → API → Nginx upstream | DB가 의도적 점검 중인지 확인 후 기존 컨테이너 복귀. 새 빈 DB로 교체하지 않음 |
| health는 200인데 보고서 실패 | 실제 DB 조회 API·migration·API 오류 | health만으로 정상 판정하지 않음 |
| 방송이 목록에서 사라짐 | 공식 상태, 정회·재개 값, 상태 수집시각, UI 필터 | 상태와 마지막 저장본 확인, 종료·미감지를 구분 |
| 영상은 있으나 자막 없음 | caption worker·WebSocket·final 증가·STT 보완 | 수집 계약·청크·전사 오류 확인. 수집 누락과 요약 지연 분리 |
| 정리중 수가 멈춤 | 단계·배치·최근 오류·재시도시각·모델 예약량 | 실패 부분만 재개. 전체 요약 초기화 금지 |
| 원문 불명확이 증가 | 원문 품질·자동 검토 완료 여부·분류 사유 | 원문 한계와 미실행/통신 오류를 구분 |
| 과제가 지나치게 많음 | 역할 판정·직접 요청 span·중복 과제 | 질의/답변·진행 안내를 과제에서 분리, 근거 보존 |
| 요약에 한자·불필요 외국어·숫자 오류 | 원문과 응답·검증 실패 이력 | 실패 필드 교정, 유효한 나머지 요약 재사용 |
| NIM/Groq 잔량은 있는데 다른 모델 사용 | 작업 경로·입력/출력 한도·429·cooldown·enabled | 경로별 채택/제외 사유 확인. 잔여 비율만으로 판단하지 않음 |
| 온톨로지 로딩 지연 | 집계시각·캐시·background 응답·브라우저 3D | 이전 성공본·호환 지도 확인, 집계와 렌더링 장애 분리 |
| 검색/다운로드 세션 오류 | HTTPS·Secure cookie·Origin·프록시 path | 정상 공개 주소로 재접속, 인증 상태 복구 |
| 카카오 KOE006·메시지 미수신 | Redirect URI·선택 동의·outbox·token | 연결/재동의·전송 실패를 구분. 화면 알림 확인 |
| 최신 화면이 안 나옴 | 정적 파일 응답·index의 버전·mount 경로 | web 배포·캐시 버전 확인 후 새로고침 |

의도하지 않은 DB 중단의 복구는 기존 볼륨·네트워크·작업 종료 여부를 확인한 후 운영 절차에 따라 수행합니다. 정확한 예시는 [OPERATIONS.md](docs/OPERATIONS.md)의 DB 복구 절을 따릅니다. 외부 DNS 장애와 Docker의 `db` 내부 DNS 실패를 같은 원인으로 단정하지 않습니다.

### 12.5 미완료 보고서 점검과 제한 재처리

1. 방송 ID, 현재 입력 fingerprint/cursor, 브리프·구조화·세부 요약 버전을 고정해 조회합니다.
2. `overview`와 `brief`에서 단계별 완료/대상 수, 최종화 상태, 재시도 사유를 대조합니다.
3. 분류 대기·실패, 미요약 쟁점, 누락 evidence ID, 자료 요구 미연결, 온톨로지 대기 항목을 구분합니다.
4. 검증된 배치·요약을 재사용할 수 있는지 확인합니다. 원문 불명확을 없애기 위한 강제 분류를 하지 않습니다.
5. 대상·호출 범위·가용 예산을 정한 뒤 필요한 작업만 예약하고 최종 완료 게이트를 다시 확인합니다.

**아래는 상태 조회가 아닌 재처리 명령입니다.** 외부 모델 호출과 저장 상태 변경이 발생할 수 있습니다. 승인된 방송 UUID와 현재 입력을 확인하고 운영 worker와 중복 실행을 피합니다.

```bash
# 기존 운영 컨테이너의 환경을 사용. <방송UUID>를 실제 대상 하나로 치환.
sudo docker exec poc07-national-assembly-meeting-brief-worker \
  python -m app.ingestion.structured_narrative_worker --broadcast-id '<방송UUID>' --enqueue

# 공식 통합을 특정 회의에서 1회 처리하는 예시
sudo docker exec poc07-national-assembly-official-integration-worker \
  python -m app.ingestion.official_integration_worker --broadcast-id '<방송UUID>' --once
```

`--enqueue`는 보완 작업을 영속 등록해 재개할 수 있게 합니다. `--all`, `--drain`, `--repair`, `--force`는 영향 범위가 다르므로 각 모듈의 `--help`·입력 해시·원문 상태를 먼저 확인합니다. 전체를 재생성해야만 문제가 해결된다고 가정하지 않습니다.

일정·공식 API의 수동 수집은 `scripts/fetch_schedule.py`, `app.ingestion.schedule_worker`, `committee_sync`, `bill_sync`를 사용합니다. 외부 출처 조회·DB 저장이 있으므로 읽기 전용 진단 명령으로 분류하지 않습니다. Quick VOD 누락 복구는 [backfill_quick_vod.sh](scripts/backfill_quick_vod.sh)의 `--dry-run`과 실제 출처·시각 검증 후 별도로 수행합니다.

## 13. 배포·롤백·백업·보안 — O-03

### 13.1 변경 유형별 배포

| 변경 | 필요한 작업 |
|---|---|
| README·운영 문서만 변경 | 문서 검수·배포. API/worker 재시작 불필요 |
| `web/` JS/CSS/HTML | 정적 파일 반영, index asset 버전 갱신, 두 공개 경로와 브라우저 검수 |
| Python 서비스·worker | 새 이미지 빌드, 영향 컨테이너 재배포, 단계별 상태 확인 |
| migration | DB 백업·호환성 검토 → migration 적용 → 호환 코드·worker 배포 |
| 환경변수·모델 키 | 예시·config·허용목록·보안 범위 확인 후 대상 컨테이너 재생성 |
| Nginx·TLS | 대상 가상호스트만 변경, `nginx -t`, 승인된 reload·공개 경로 검수 |

운영 API는 호스트 `web/`를 읽기 전용 bind mount하므로 일반 정적 화면 변경만으로 이미지를 다시 만들 필요는 없습니다. 이미지에 내장된 정적 파일을 쓰는 다른 환경은 해당 배포 방식을 따릅니다.

기존 운영 스크립트 배포 예시:

```bash
# 배포 버전은 고정 가능한 태그로 지정
sudo docker build -t poc07-national-assembly-api:release-YYYYMMDD-N backend
sudo env POC07_IMAGE=poc07-national-assembly-api:release-YYYYMMDD-N bash scripts/deploy_api.sh
# 회의 처리 코드가 변경된 경우 해당 worker도 같은 버전으로 배포
sudo env POC07_IMAGE=poc07-national-assembly-api:release-YYYYMMDD-N bash scripts/deploy_secure_workers.sh meeting
sudo python3 scripts/check_runtime.py --scope all
```

수집 worker는 `deploy_live_capture_workers.sh`, 게이트웨이는 `deploy_openrouter_gateway.sh`를 사용합니다. `deploy_secure_workers.sh`의 대상은 `summary`, `meeting`, `official-minutes`, `official-integration`, `executive`, `schedule`, `review`, `watch`, `notification`, `watch-summary`, `topic-report`, `all` 등입니다. 수정 범위에 필요한 대상만 선택합니다. 게이트웨이 의존 변경은 worker보다 먼저 준비합니다.

### 13.2 배포 완료·롤백 기준

- 배포 전 commit/이미지 ID·migration 목록·설정 이름별 적용 여부·백업 세트를 기록합니다. 문서에 실제 비밀값을 넣지 않습니다.
- API 스크립트는 새 컨테이너 health 실패 시 이전 컨테이너를 복귀시키는 경로를 갖습니다. worker도 기동 실패 복구 경로를 갖지만 **업무 처리 성공까지 자동 보증하는 것은 아닙니다.**
- 배포 후 DB 조회, 두 공개 주소, JS/CSS, 선택 보고서·근거·검색·다운로드, worker 로그를 확인합니다.
- 적용한 migration을 수정하거나 `schema_migrations` 이력을 지워 롤백하지 않습니다. 이전 코드 호환성을 확인하고 후속 migration으로 복구합니다.
- 원본·revision·공식 문서를 지워 잘못된 파생 결과에 맞추지 않습니다. 실패 결과는 이력과 새 버전으로 관리합니다.
- 수집 중 배포는 현재 lease·미완료 청크·진행 배치에 영향을 줄 수 있으므로 해당 worker의 마감·재개 동작을 확인합니다.

### 13.3 백업 범위와 예시

필수 백업 세트는 **DB + 원본 파일 + 읽기 스냅샷 + 게이트웨이 장부 + 코드/이미지/설정 메타데이터 + 별도 보관한 암호화 키**입니다. `data/raw`와 PostgreSQL만 백업하고 공유 게이트웨이 장부를 빠뜨리지 않습니다.

아래는 기존 운영 컨테이너명 기준 예시입니다. 파일 원본과 DB 사이의 기준시각을 맞추는 snapshot 또는 수집 제어 정책을 별도로 정하고, 백업 저장소의 암호화·외부 복제를 적용합니다.

```bash
umask 077
poc07_backup_dir="backups/$(date -u +%Y%m%dT%H%M%SZ)"
mkdir -p "$poc07_backup_dir"
sudo docker exec poc07-national-assembly-db \
  pg_dump -U national_assembly -d national_assembly --format=custom > "$poc07_backup_dir/db.dump"
tar --create --gzip --file "$poc07_backup_dir/source-data.tar.gz" data/raw data/processed
# 실행 중인 SQLite 파일을 단순 cp하지 않고 일관 백업 API 사용
python3 - "$poc07_backup_dir" <<'PY'
import sqlite3
import sys
from pathlib import Path
source = sqlite3.connect('file:data/openrouter_gateway.sqlite3?mode=ro', uri=True)
target = sqlite3.connect(str(Path(sys.argv[1]) / 'openrouter_gateway.sqlite3'))
try:
    source.backup(target)
finally:
    target.close()
    source.close()
PY
sha256sum "$poc07_backup_dir/db.dump" "$poc07_backup_dir/source-data.tar.gz" \
  "$poc07_backup_dir/openrouter_gateway.sqlite3" > "$poc07_backup_dir/SHA256SUMS"
sudo docker exec -i poc07-national-assembly-db pg_restore --list < "$poc07_backup_dir/db.dump"
```

각 명령의 성공 여부와 checksum을 확인한 후 백업 성공으로 기록합니다. 일관된 파일 snapshot이 없는 상태에서 진행 중인 오디오를 tar로 복사한 결과만으로 완전한 복구를 보장하지 않습니다.

### 13.4 복구·보존

1. 운영과 격리된 빈 DB·디렉터리에 복원합니다. 기존 운영 DB에 무심코 `--clean` 복원을 실행하지 않습니다.
2. DB와 원본·읽기 스냅샷·게이트웨이 장부·암호화 키를 같은 백업 세트로 복원합니다.
3. 현재 코드의 미적용 migration을 실행하고 회의 건수·revision·evidence 관계·요약·계정·사용량을 대조합니다.
4. 복원 시험 중 외부 알림·모델·수집 worker는 자동 실행되지 않게 제어합니다. 검수 후 단계적으로 재개합니다.
5. 복구 소요시간·유실 가능 구간·남은 오류를 기록하고 RPO/RTO와 대조합니다.

자동 백업의 설치·주기·보존기간·복구목표는 배포기관이 정해야 합니다. 이 문서에 백업 명령이 있다는 것만으로 정기 백업이 구성된 것은 아닙니다. 원문·오디오의 보존·폐기는 계정 알림 삭제와 다른 정책이며 근거 추적 가능성을 검토합니다.

### 13.5 비밀값·권한·운영자 테스트

- 외부 AI 키는 필요한 worker에만 주입합니다. 운영 OpenRouter 실제 키는 게이트웨이가 소유하고 worker는 `gateway-local`과 내부 URL을 사용합니다.
- API에는 조회·OAuth에 필요한 범위만 전달합니다. 브라우저·정적 자산·API 응답에 모델 키를 넣지 않습니다.
- 세션은 Secure·HttpOnly·SameSite 쿠키를 사용하고 서버에는 세션 해시를 저장합니다. 변경 요청은 Origin과 사용자 권한을 확인합니다.
- Kakao token은 전용 Fernet 키로 암호화합니다. 암호화 키를 잃으면 기존 token을 복구할 수 없으므로 비밀관리소에 별도로 보관합니다.
- 관리자 token, 사용자 알림·계정·원문 개인정보를 화면 캡처·오류 사례·일반 사용자용 문서에 넣지 않습니다.
- 관리자 재현 방송은 별도 출처·사용자 범위로 격리하고 공개 목록·정상 보고서·모델 후보에서 제외합니다. 실제 카카오 발송 시험은 별도 선택·동의 범위에서 수행합니다.
- 격리 재현은 화면·알림 회귀 확인 수단이며 실제 동시 방송 수집, 외부 source 계약, 운영 부하 시험을 대체하지 않습니다.

| 주제 보고서 조회 | `GET /api/topic-reports`, `/{id}`, `/{id}/report.md` | 사용자 범위 결과·문서 |
| 세션 시작·폐기 | `POST /api/watch/session`, `DELETE /api/watch/session/current`, `/api/watch/session/all` | 사용자 세션 변경 |
| 관심주제 | `GET/POST /api/watch/rules`, `PUT/DELETE /api/watch/rules/{rule_id}` | 사용자 규칙·revision |
| 관심주제 보고서 | `GET /api/watch/rules/{rule_id}/report` | 저장 결과 및 설정에 따른 요청형 생성 경로 확인 |
| 알림함 | `GET /api/watch/notifications` 및 읽음·삭제 API | 사용자 소유 알림 |
| 카카오 | `/api/watch/kakao/status`, `/authorize`, `/callback` 등 | OAuth·동의·연결 관리 |
| 운영 검토·재현 | `/api/watch/admin/...`, `/api/watch/test-broadcasts...` | 관리자 인증 필요 |

표에서 묶어 쓴 suffix는 앞의 동일 기능 prefix를 따릅니다. 실제 경로·메서드·필수 query는 OpenAPI를 확인합니다. 단순히 GET이라는 이유로 모든 사용자 보고서 경로를 무제한 수집하지 않습니다. 생성 예약 가능성이 있는 요청형 보고서 API와 순수 조회를 구분합니다.

권한·프록시 계약:

- 공개 회의와 사용자 소유 알림·보고서는 접근 범위가 다릅니다. UI에서 숨기는 것만으로 권한을 대신하지 않습니다.
- 사용자 API는 Secure HttpOnly 세션 쿠키를 사용합니다. `X-Watch-Token`은 구형 세션 승격 호환 용도입니다.
- 관리자 API의 token·same-origin 검사와 공개 Nginx의 쓰기 제한을 함께 유지합니다.
- 새 API를 추가하면 응답 schema·권한·에러·페이지 조회·프록시 전달·문서 변경을 함께 검토합니다.

### 14.3 로컬 개발과 설정 로딩

운영 서버와 분리된 DB·계정을 사용합니다. 부모 프로젝트의 `.venv`나 `.env`를 런타임 의존성으로 사용하지 않습니다.

```bash
python3 -m venv .venv
. .venv/bin/activate
pip install -r backend/requirements-dev.txt
```

`Settings`의 코드상 기본 `.env` 탐색 경로는 `backend/.env`입니다. 프로젝트 최상위의 `.env`를 사용하는 직접 Python 실행에서는 아래처럼 **명시적으로 로드**합니다. Docker 운영은 허용목록으로 환경변수를 주입합니다.

```bash
# .env가 개발 DB를 가리키는지 먼저 확인. 이 명령은 DB schema를 변경함.
PYTHONPATH=backend python - <<'PY'
from dotenv import load_dotenv
import runpy
load_dotenv('.env', override=False)
runpy.run_module('app.db.migrate', run_name='__main__')
PY

# 로컬 개발 API. 아래 실행은 자동 reload를 사용하지 않음.
PYTHONPATH=backend python - <<'PY'
from dotenv import load_dotenv
import uvicorn
load_dotenv('.env', override=False)
uvicorn.run('app.main:app', host='127.0.0.1', port=8070)
PY
```

로컬 shell에 이미 있는 환경변수가 `.env`보다 우선합니다. `DATABASE_URL`의 컨테이너 이름 `db`는 호스트에서 바로 해석되지 않을 수 있으므로 개발 DB 접속 경로를 따로 구성합니다. 운영 DB 포트를 개발 편의를 위해 인터넷에 개방하지 않습니다.

### 14.5 확장 시 지킬 계약

1. 새 위원회·기관은 수집 adapter·대상 설정·어휘·공식 파서로 확장합니다. 별도 서비스 흐름을 복제하지 않습니다.
2. 새 주제 분류를 추가할 때 기존 상위 계층·근거 ID·과제 직접 구간·보고서 형식을 보존합니다.
3. 프롬프트·profile 변경은 저장 해시·재시도·캐시의 재사용 범위를 명시합니다. 모든 과거 보고서를 자동으로 재생성하지 않습니다.
4. 정적 파일 추가는 `index.html`의 로딩 순서·캐시 버전과 두 공개 경로의 상대 URL을 확인합니다.
5. 상태 완료는 화면 문구가 아니라 서버 검증 결과로 판정합니다. 미분류를 숨기거나 원문을 잘라 완료 수치를 만들지 않습니다.
6. 사용자 영향은 CHANGELOG, 기술 판단은 DECISIONS, API/데이터 변화는 해당 계약 문서와 README에 함께 반영합니다.

### 15.4 자주 묻는 질문

**보고서가 끝났는데 원문 불명확이 남아 있어도 되나요?**

자동 검토 대기와 원문 한계는 다릅니다. 검토가 끝났고 원문 자체로 대상을 특정할 수 없는 부분은 사유와 함께 남깁니다. 미실행·통신 오류를 같은 상태로 감추면 안 됩니다.

**근거 발언 47건인데 요약은 47줄이 아닙니다.**

요약은 여러 발언을 합칩니다. 세부 쟁점과 전체 근거의 포함 여부를 확인하며 원문 전체는 별도 팝업에서 읽습니다.

**자료 제출 요구가 왜 회의 진행 원문에 있나요?**

“자료 요구를 받겠습니다”는 진행 안내일 수 있습니다. 실제 제출 대상·요구가 있는 발언은 주제별 과제로 연결돼야 하므로 직접 원문을 기준으로 검수합니다.

**시사점이 5개이면 일부 내용이 빠진 것인가요?**

시사점은 통합 개수입니다. 본문·세부 논의·과제·근거 포괄을 함께 확인합니다. 연결 검증 실패를 완료 처리하지 않습니다.

**전체 발언 MD와 요약 PDF는 같은 문서인가요?**

MD는 시간순 LIVE/STT 원문 전체, 요약 PDF는 대주제·소주제별 요약과 과제입니다. 공식 원문 여부·수집 시각 안내를 유지합니다.

**모델 잔량이 있는데 왜 대기하나요?**

RPM, 입력 크기, 출력 예산, 작업별 우선순위, 원문 검증 실패가 각각 영향을 줍니다. 잔여량 표시만으로 처리 가능 여부를 판정할 수 없습니다.

### 실시간 OpenRouter 모델 검증 (2026-10-30)

실시간 부분요약은 **GPT-5.4 mini + OpenRouter Nemo3.5 VL** 두 경로에서 서로 다른 발언을 병렬 처리합니다. 매 공통 조회 주기에서 Nemo가 먼저 작업을 찾고 Mini가 1초 뒤 참여합니다. Nemo가 처리 중이거나 실패해도 Mini는 독립적으로 실행합니다. Nemo는 추론 OFF를 사용하며, 즉석 답변을 후속 과제로 섞은 결과는 저장 전에 보류해 다른 경로가 이어받습니다. 통합·공식 대조의 GPT 모델 구성은 유지합니다. 호출 제한·설정 오류와 의미 품질 실패를 구분한 [비교 결과 및 한계](docs/evidence/MODEL_REPLACEMENT_20261030/README.md)를 참고하세요.
