실제 단일/분할 통합의 공통 parent 목록과 JSON Schema, 과거 보고서 읽기, 주요 논의 요약, 인쇄/PDF 투영에 동일한 규칙을 사용한다. 세부 쟁점의 의미 통합이나 역할/과제 재분류는 하지 않았으며 원래 그룹은 `source_groups`로 추적할 수 있다.

## 권장사항 적용 순서

1. **진행 상태와 본문 버전 분리(0063)**: 최신 상태·이력은 작은 별도 테이블로 기록한다. 동일 본문은 SHA-256 공유 저장하며 원래 버전 ID·시각·사유와 당시 상태를 복원한다. 상태 10회 변경 시 본문 CTID가 바뀌지 않는지 확인했다. 늦은 본문 보완이 최신 진행 상태를 되돌리지 않도록 추가 보호했다.
2. **동일 요청 공유 저장(0064)**: 처리 시도/응답 5,454건을 보존하면서 요청 JSON은 3,396개로 공유한다. 배치별 결과·오류·사용량·출처는 유지한다.
3. **제공사/입력별 재시도 제한**: 통합과 세부 서술에서 동일 입력·동일 모델의 입력 크기 초과를 다시 시도하지 않는다. 일일 한도는 UTC 다음날 00:00(KST 09:00), 속도 제한은 Retry-After 이후에 재개한다. 다른 모델/달라진 요청과 실제 품질 교정은 별도로 허용한다. 모델 응답의 실제 이름과 시도한 모델 이름을 구분해 기록한다.
4. **공식 원문·주석의 중복 바이트 공유(0065)**: 모든 문서/발언/주석 ID와 원문 위치, 화자, 권위 상태, 참조 외래키 및 원본 파일을 유지한다. 새 쓰기는 트리거로 정규화하며 과거분은 페이지 단위로 처리한다. 각 배치는 전체 원래 JSON의 전후 해시와 건수가 같을 때만 커밋한다.
5. **후속 보완(0066–0067)**: 동일 UNIQUE 인덱스가 이미 지원하던 중복 보조 인덱스를 온라인 제거해 772,022,272 bytes(약 736MiB)를 회수했다. 확인 시각만 바뀌는 폴링은 최신 시각만 갱신하고 상태 이력을 늘리지 않는다.

## 운영·복구

- API: `poc07-report-storage-api:20261031-final`; 회의 후처리: `poc07-report-storage-worker:20261031-final`; 공식자료 수집: `poc07-official-storage:20261031-v2`. 기존 모델 우선순위와 공유 예산·마운트·네트워크 설정을 유지했다.
- 복구 백업: 프로젝트 내부 `data/maintenance-backups/20261031/`의 `report-storage-before.dump`, `official-payloads-before.dump`, `SHA256SUMS`. DB 데이터가 포함되어 Git 추적에서 제외하고 접근 권한을 제한했다. `pg_restore -l`로 두 custom archive의 목록을 확인했다.
- 정규화 재개: 검증된 백업이 있을 때 해당 서비스 이미지에서 `python -m app.ingestion.normalize_official_storage --blocks 2048`. 세션 advisory lock으로 중복 실행을 막고 완료 배치는 건너뛴다. 미완료 배치 실패 시 트랜잭션만 롤백되며 다음 실행은 마지막 커서에서 재개한다.
- 이관 후에는 기존 뷰 이름만 부분 덤프하지 않는다. 전체 DB를 백업하거나 새 base table·공유 payload·진행 상태와 뷰/함수를 함께 포함한다.
- 원문 조회는 기존 뷰 이름을 사용한다. 직접 INSERT/ON CONFLICT를 쓰던 유지관리 스크립트는 `OfficialPublicationRepository` 또는 새 base table을 사용한다. 복원 검증은 별도 DB에서 먼저 수행하며 운영 뷰 위에 과거 덤프를 덮어쓰지 않는다.
