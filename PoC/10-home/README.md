공급계획의 모집/공급 예정월과 공사 계약 준공예정일은 실제 공급·준공·입주 실적이 아닙니다. LH 지역본부 이름으로 소재지를 추정하지 않으며 위례 등 지역 배분 미확인 행은 제외합니다. SH·GH·지자체와 민간 정책관리 사업의 전체 모집단은 아직 확보하지 않았습니다.

청약홈·건축HUB·VWorld는 설정된 HOME 전용 키로 소량의 API 표본을 수집합니다. registry의 `TEST_SAMPLE`, `manual_only=True` 원천은 기본 24시간 수집에서 제외합니다. 관리자 → API 테스트 데이터 → `표본 다시 수집` 또는 아래 명령으로 실행합니다.

```bash
sudo docker exec poc10-home-api python -m scripts.collect --samples
```

청약은 정책 기원 연도(현재 2018-01-01)부터 오늘까지 서울·경기 × 연도별 필터 결과의 전체 페이지를 수집합니다. 인허가는 개포·고덕·진관·이의·다산·덕풍동 전체 조회 페이지를 수집하며 법정동당 안전 상한 10,000건을 둡니다. 주소 좌표는 이전 조회 결과를 건너뛰고 지역·유형별 최대 25개(한 배치 최대 100개)씩 누적 검증하며 이전 결과도 보존합니다. API에 자료가 없는 연도를 실적 0으로 단정하지 않습니다. 이 범위는 전체 정책 사업 목록이 아니며 최신순을 주장하지 않습니다. API 목록은 페이지당 100개, CSV는 해당 조건 전체를 제공합니다. 키를 제거한 API 응답만 SHA-256으로 저장합니다.

관리자 로그인 → 공급 현황 → 사업의 `목표 관리`에서 당해연도·향후 10년의 목표 단계·호수·근거를 입력합니다. 원천 일정은 별도로 유지합니다. 미등록 목표를 0호로 바꾸거나 전체 물량을 임의로 연도별 배분하지 않습니다.

신규 건축물대장은 6개 법정동 첫 100개 행 중 주거용 표제부, LH는 2018년부터 서울·경기 분양·임대 전체 페이지, 통계누리는 2018년부터 월별 분양승인·착공·준공과 연간 인허가 총계를 수집합니다. 홈페이지의 자료 연도 필터와 CSV에 같은 조건을 적용합니다. LH 복수지역·비주거 제외와 통계의 최신 공개 기간은 [검증 기록](docs/ADDITIONAL_API_VERIFICATION.md)을 참조하세요.

## 실행

Python 3.12와 전용 PostgreSQL/PostGIS를 Docker로 실행합니다. 기존 PoC의 Python 환경과 DB는 사용하지 않습니다.

```bash
cd PoC/10-home
cp .env.example .env
# POC10_DB_PASSWORD와 POC10_INTERNAL_SECRET을 충분히 긴 임의 값으로 설정
chmod 600 .env
docker compose up -d --build
```

이 서버는 Compose 플러그인이 없어 아래 Docker CLI 실행기를 사용합니다. 이미 설정된 `.env`와 DB 볼륨을 보존해 HOME API만 갱신합니다. 현재 서버의 기존 `.env`를 예제 파일로 덮어쓰지 마세요.

```bash
sudo python3 PoC/10-home/scripts/deploy.py
```

위 명령은 저장소 루트에서 실행합니다. 직접 조회: `http://127.0.0.1:18100/poc/home/`, health: `http://127.0.0.1:18100/health`. 부모 ASGI는 `/poc/home/*`를 이 주소로 프록시합니다. 부모 서비스의 `POC10_UPSTREAM`으로 기본 upstream을 변경할 수 있습니다.

### 사업별 수집·연계 화면 (2026-10-12)

`데이터현황 → 사업별 수집·연계` (`#project-collection`)에서 정책–사업화–인허가–건설–공급–입주 원천을 다이어그램과 사업별 표로 조회한다. 기본 정책은 9·7이며 정책·지역·사업명·수집 상태 필터와 같은 조건의 CSV를 제공한다. 예정 자료, 실제 진척, 확인 필요 연결을 구분한다.

조회 API는 `GET /poc/home/api/project-collection`, CSV는 `/api/project-collection/export.csv`다. 기존 정책/프로그램 연결과 `stage_evidence`를 읽으며, 모집공고·입주계획 후보는 `home_revision.kind=collection_link`에 최초/수집 시점에 저장한다. 화면 조회에서는 재매칭하거나 DB를 쓰지 않는다. 기존 선택이 있으면 자동 갱신이 유지하며, 미연결 항목만 원천/사업 판본 지문 변경 시 재검토한다.

미확보 원인은 `home_revision.kind=collection_assessment`의 `project_id:stage` 단위 판본과 `home_audit`에 보관한다. `POST /api/admin/project-collection/assessment`는 기존 관리자 인증, revision_no 충돌 확인, 확인 근거를 요구한다. 근거 없이 아직 계획 미수립으로 자동 판정하지 않는다. 기존 미확보 판정 후 자료가 확보되면 자료를 우선 표시하고 판정 재검토를 안내한다. `METHOD_UNKNOWN`은 원천의 데이터가 0이라는 의미가 아니라 사업별 제공처/확보 방법의 추가 확인이 필요하다는 의미다.

다이어그램은 보유 원천 → 실제 연결 필드 → 추가 확보·연결 보완 → 분석 결과의 구조다. 단계 탭과 사업 선택에 따라 저장된 근거를 다시 집계하며, 상자·화살표에서 필드 예시와 단절 원인을 조회한다. 실선(필드/저장 연결), 점선(후보·추정), 붉은 단절선(필드/연결 미확보), 노란 보완선(추가 작업)을 구분한다. 필드 보유 수는 사업 기록 기준이며 주택 호수나 검증 완료 수가 아니다.

`backend/collection_lineage.py`는 선택된 `source_entity_id`와 `source_revision_no`의 원천 판본에서 허가 PK·법정동 코드·주택관리번호 등 실제 필드를 읽는다. 판본이 고정된 연결은 최신 원천으로 바꾸지 않으며, 판본 미지정 연결만 기준일 내 최신 판본을 참조한다. PNU는 19자리 원본이 있을 때만 확보로 처리한다. 입주 예정일로 실제 시작일을 만들지 않으며, 단계별 예정/관측일을 분리한다. 기존 매칭 DB를 읽는 기능으로, 조회 중 새 연결을 생성하거나 저장하지 않는다.
