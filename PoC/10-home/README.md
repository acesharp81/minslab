운영 데이터와 미커밋 코드가 함께 존재할 수 있습니다. 배포·인수인계 때는 문서 날짜만으로 버전을 특정하지 말고 **소스 커밋, 작업 트리 변경 여부, 실행 이미지, DB migration, 데이터 기준시각**을 함께 기록합니다. 문서에 설명된 사용자 유형은 이용 목적의 구분이며, 제품에 각각 독립된 역할 기반 권한이 모두 구현됐다는 뜻은 아닙니다.

## 조원 공유 요약 — 3개 AI 에이전트가 담당하는 일

**현재 개발의 핵심은 ‘알고리즘 개선 → 자료 수집 → 업무 판단’을 세 에이전트로 나누고, 각 단계의 결과·근거·보류 사유·사람의 조치를 추적할 수 있게 만든 것입니다.** 기존 규칙 기반 수집기와 함께 동작하며, 화면에서 각 에이전트의 모델과 실행 여부를 따로 설정합니다.

| 순서·에이전트 | 담당하는 질문 | 주요 처리와 산출물 | 사람이 개입하는 지점 |
| --- | --- | --- | --- |
| **① 알고리즘 에이전트** | **왜 수집·추출에 실패했고, 어떤 패턴을 고쳐야 하는가?** | 실패 사례 진단, 본문 추출 선택자·접근 문제 개선안, 검토·시험 이력 | 원문 전후 비교 후 본문 CSS 패턴 승인 / 일시 오류로 종료 / 재분석 요청 / 적용 해제 |
| **② 수집 에이전트** | **새 자료는 무엇이며 어떤 사업명·물량·일정을 담고 있는가?** | 설정된 공식 출처·뉴스 탐색, 원문·해시 보존, 중복 검사, 비정형 정보 추출, 검토 후보 등록 | 접근 차단·첨부 미확보·추출 불확실성 보완. 수집 역할별 판단보류 CSV 제공 |
| **③ 업무담당자 에이전트** | **어느 사업의 근거이며 실제 단계에 반영할 수 있는가?** | 공식 본문과 기존 사업의 식별정보 대조, 조건 충족 시 자료 연결, 별도 단계 실적 제안·검증 | 동일성·범위·날짜·물량 충돌과 기존 사람 판단은 보류. 업무담당 역할별 판단보류 CSV 제공 |

```mermaid
flowchart LR
    A[① 알고리즘 에이전트<br/>실패 진단·개선안] --> V[사람의 원문 시험·승인]
    V --> R[승인된 본문 추출 규칙]
    R --> B[② 수집 에이전트<br/>탐색·중복 검사·정보 추출]
    B --> C[③ 업무담당자 에이전트<br/>사업·단계 근거 대조]
    C --> L[검증된 자료 연결]
    L --> S[별도 단계 실적 검증]
    S --> P[조건 충족 시 관리 실적 반영<br/>정책·사업 집계]
    B --> H[판단보류·사람 확인<br/>역할별·통합 CSV]
    C --> H
    S --> H
    B -. 수집 실패 피드백 .-> A
```

이 도식은 역할 간 자료 흐름입니다. **실행은 하나의 작업 큐에서 순차 처리**하며, 당일 알고리즘이 제안한 패턴도 사람이 승인하기 전에는 수집기에 적용되지 않습니다. 현재 운영 설정은 다음과 같습니다(2026-11-03 조회 기준).

| 에이전트 | 예약 시각·한국시간 | 자동 실행 | 선택 모델 |
| --- | --- | --- | --- |
| 알고리즘 | 01:00 | 켜짐 | Solar Pro 4 |
| 수집 | 02:00 | 켜짐 | Solar Pro 4 |
| 업무담당자 | 03:00 | 켜짐 | Solar Pro 4 |

자동 일괄 작업은 **01:00 이상~05:00 미만**에 실행합니다. 예약 시각은 실행 자격이 생기는 시각이며 앞 작업·한도·원문 접근 상태에 따라 시작이 늦어질 수 있습니다. 관리자 수동 실행은 별도입니다. 신규 설치 기본값과 현재 운영 설정은 다르므로 인수인계 시 화면의 저장 설정을 확인합니다.

### 자동화된 범위와 현재의 경계

- **구현:** 역할별 모델 선택·예약·수동 실행, 완료/보류 상세, 제한된 본문 CSS 규칙 시험·승인·해제, 자동 자료 연결의 근거 검증, 단계 실적 제안·승인 경로, 역할별/통합 CSV, PoC7·10·11 공통 사용량 관리.
- **사람의 확인을 유지:** 추출 규칙 운영 적용, 불명확한 사업 연결, 기존 확정값과 충돌하는 실적 정정. 모델의 확신이나 유사도만으로 승인하지 않습니다.
- **현재 범위 밖:** 운영 소스 코드·DB·배포 구성의 자율 수정, 모든 첨부 형식의 자동 복구, 업무담당자 에이전트의 독립 인터넷 재검색. 공식 HTML 본문 복구는 제한적으로 지원합니다.
- **완료의 의미:** 작업 종료·자료 연결·실적 반영은 별도 상태입니다. 진행률 100%여도 판단보류가 남을 수 있고, 자료 연결 승인만으로 정책 그래프의 호수가 증가하지 않습니다.

**AI 활용의 차별점:** 개발 과정에서 AI로 설계·검증한 추출 패턴을 코드로 축적하여 동일 형식은 건별 모델 호출 없이 반복 처리합니다. 새 에이전트는 실패 진단·비정형 분석·업무 판단을 맡습니다. 규칙 기반 반복 처리와 모델을 사용하는 분석 작업의 비용을 구분합니다.

### 모델 전환과 공동 사용량

다음은 **현재 코드의 역할별 선택 허용 목록**입니다. 제공사 전체 모델 목록이나 향후 접근 권한을 보장하는 표가 아닙니다.

| OpenRouter Nemotron 3.5 Super VL | — | 가능·텍스트 분석 | — | 공통 요청 횟수 |

역할별 기본 구성은 **모델 하나**입니다. 수집의 mini/Nemotron을 선택할 때만 애매한 건을 GPT-5.4 또는 Terra로 추가 검토하는 선택지를 제공합니다. Solar의 현재 무제한 혜택을 제외한 표준 단가로 경제성을 비교하며, 2단계 구성이 항상 저렴하다고 가정하지 않습니다. Sol·Astra는 현재 허용 목록에 없습니다.

국산 Solar와 해외 모델을 같은 업무 절차·검증 조건으로 전환할 수 있도록 구성했습니다. 모델을 바꿔도 사업 원장·판단 이력은 유지하지만, 같은 품질과 처리 속도를 보장하는 것은 아니며 실제 변경 모델로 검증해야 합니다. 운영 키·예산 설정은 서버에만 저장합니다.

PoC7·10·11이 **동일한 공통 한도·사용량·예약량·초기화 시각**을 공유합니다. 상단 작은 사용량 패널에서 잔여량/한도·비율을 보고 상세에서 사용·예약·미확정·초기화 시각을 확인합니다. Solar 무제한은 잔여량 막대 대신 사용량을 표시합니다. 이 값은 계측한 공통 운영 원장이며 제공사의 실제 청구 잔액과는 구분합니다. 상세는 [공통 예산 운영](docs/SHARED_AI_BUDGET.md)을 참고하세요.

### 조원이 먼저 확인할 화면

1. **데이터 관리 → 신규 자료 검토 → AI 작업자**에서 알고리즘·수집·업무담당 카드를 각각 선택합니다. 카드 선택은 조회이며 실행 버튼과 다릅니다.
2. **처리 완료 / 판단보류** 항목을 펼쳐 원문·이유·분석·판단 이력을 확인합니다. 알고리즘은 **개선안 검토·조치 대기**에서 시험과 사람의 조치를 확인합니다.
3. 외부 모델의 도움으로 보류 대상을 검토하려면 상단 **외부 검토용 · 대상별 통합 CSV**를 받습니다. 자료 연결 큐의 검토 대기·보류·등록 대기를 점검하려면 목록의 해당 상태 CSV/근거 JSON을 사용합니다.
4. **단계별 실적 반영 검토**에서 현재값과 제안값을 대조합니다. 자료 연결과 실적 반영을 따로 확인한 뒤 정책 추진현황을 조회합니다.

## 1. 서비스 목적과 사용 범위

HOME은 **정책 → 프로그램 → 사업**을 연결하고, 주택공급의 사업화·인허가·착공·공급·입주 진행을 목표와 비교하는 시스템입니다. 정책 전체 목표, 연결된 사업의 진행, 지역의 생활·수요 여건, 원천자료의 확보·검토 상태를 함께 확인합니다.

주요 질문은 다음과 같습니다.

- 정책 목표를 어떤 프로그램과 사업이 수행하는가?
- 기준일에 어느 단계까지 진행했고, 목표 대비 부족하거나 확인이 필요한 부분은 무엇인가?
- 공급 예정 사업은 언제 후속 단계로 넘어가며 지역 여건은 어떠한가?
- 숫자의 근거는 어느 원문·판본·담당자 판단인가?
- 새로 발견된 공고는 기존 사업의 후속 자료인가, 다른 사업인가, 검토 대상에서 제외할 자료인가?

**자료를 수집했다는 사실은 사업 실적이 아닙니다.** 수집·추출·연결·업무 판단·집계는 서로 다른 처리 단계입니다. 사업화·인허가·착공·공급·입주의 사건 및 물량이 확인되어야 해당 단계의 실적으로 해석할 수 있습니다. 일부 화면은 조건부 추정을 포함하므로 원천 측정·담당자 입력·추정을 구분해 읽습니다.

관리 정책에는 9·7 주택공급 확대방안, 1·29 도심 주택공급 확대 및 신속화 방안, 8·13 주택 신속공급 방안이 있습니다. 정책에 연결된 사업 원장은 지역 전체 주택시장 통계와 모집단이 다릅니다. 공식 발표와 비교하려면 지역·기간·단계·공급유형·계획/실적·포함 사업을 먼저 맞춥니다.

### 1.1 이용자와 권한

| --- | --- |
| 일반 사용자 | 공개 화면 조회, 지도·지역여건 확인, 보고서 및 허용된 CSV 다운로드 |
| 업무담당자 | 관리자 인증 후 검토 판단·연결·관리정보 저장. 원문과 적용 범위, 사유, 후속 과제 확인 |

| 동료 개발자 | 격리 개발환경에서 코드·스키마·테스트 변경. 권한·판본·집계 계약 보존 |

관리자 인증은 MinsLab 부모 서비스의 세션과 내부 API 서명을 사용합니다. 화면에 입력하는 담당자명은 **업무 이력의 표기값**이며 별도의 본인인증·전자서명을 의미하지 않습니다. 유지관리사업자·개발자 전용 RBAC, 기관별 결재선, 자동 외부 모델 심사 서비스가 모두 구현된 상태는 아닙니다.

### 1.2 AI 활용의 핵심 — 추출 패턴을 재사용 가능한 코드로 축적

이 프로젝트는 개발·보완 과정에서 **AI 모델과 함께 원천자료를 분석하고, 반복되는 추출 패턴과 예외를 찾아 코드로 구현하는 방식**을 활용했습니다. AI의 분석 결과를 일회성 답변으로 끝내지 않고, 정규식·HTML 선택자·표 구조 해석·필드 매핑·정규화·검증 조건과 테스트 사례로 남긴 것이 핵심입니다.

예를 들어 공고에서 사업명·게시일·공급 물량·입주 예정월을 읽는 위치와 표현을 파악해 파서를 구현하면, 이후 동일한 형식의 새 공고는 저장된 코드가 처리합니다. 자료가 추가될 때마다 전문을 모델에 보내 다시 해석하도록 요청할 필요가 없습니다. 여기서 ‘학습’은 모델 가중치를 재학습했다는 뜻이 아니라, **분석에서 얻은 지식을 사람이 검토할 수 있는 코드·규칙·테스트로 축적했다는 뜻**입니다.

```mermaid
flowchart LR
    A[원천자료 표본·오류 사례] --> B[AI와 추출 패턴·예외 규칙 설계]
    B --> C[파서·정규화·검증 코드 구현]
    C --> D[원문 대조·표본 및 회귀 테스트]
    D --> E[검증한 규칙 배포]
    E --> F[새 자료를 코드로 반복 처리]
    F --> G[추출 결과·근거·판본 저장]
    F --> H[형식 변경·미해석·상충 확인]
    H --> A
```

**일상 수집 경로에서는 배포된 규칙을 실행합니다.** 새로운 형식이나 누락·오추출 사례가 발견될 때 표본을 검토하고, 필요하면 AI 도움으로 규칙을 보완한 뒤 다시 검증·배포합니다. 운영 중 코드가 스스로 모델을 호출해 파서를 수정·배포하는 기능을 의미하지 않습니다.

#### 실제 구현 사례

| 처리 대상 | 재사용하는 추출·검증 규칙 | 코드와 확인 자료 |
| --- | --- | --- |
| 공고·보도자료 목록 | 기관별 HTML 선택자, 게시물 ID·URL·게시일 형식, 주택 키워드. SH는 제목 속 과거 날짜 대신 게시일 열 사용 | [publication_watch.py](backend/publication_watch.py), [목록 파서 테스트](tests/test_publication_watch.py) |
| LH 모집공고 상세 | 해당 지구·블록의 탭과 표를 선택하고 총세대·금회 공급·입주예정을 구분. 혼합단지 유형별 합계 검사, 추가·잔여·예비입주자·취소 공고 구분 | [lh_notice_detail.py](backend/lh_notice_detail.py), [상세 파서 테스트](tests/test_lh_notice_detail.py) |
| HWPX 계획·고시 문서 | 문서 내부 XML의 본문·표 구조 해석, 첨부 식별자·연도 검사, 원문 파일·해시 보존 | [route_documents.py](backend/route_documents.py), [문서 추출 테스트](tests/test_route_documents.py) |
| 다양한 예정일 표현 | 연·월·분기·반기·범위 표현을 규칙으로 정규화하고 원문·정밀도 보존. 미정·이후 등은 임의 확정일로 바꾸지 않음 | [schedule_period.py](backend/schedule_period.py) |

이 사례들은 현재 코드에서 확인할 수 있는 반복 처리 방식입니다. 모든 자료에 같은 정규식 하나를 적용하는 방식이 아니라 **기관·문서 유형별로 검증한 규칙을 적용**합니다. 목록 탐색은 검토 후보를 만들고, 상세 파서는 구현된 범위의 필드·사건을 추출합니다. 패턴 추출 성공을 곧바로 사업 연결 승인이나 전체 물량의 실적 확정으로 간주하지 않습니다.

#### 운영상 효과와 비용의 의미

- **반복 비용:** 위 규칙 기반 처리에는 건별 생성형 AI API 호출·토큰 비용이 추가되지 않습니다. 서버·저장소·네트워크·OCR 실행·원천 API 이용 및 규칙 유지관리 비용은 별도이며, 개발·보완 때 사용한 AI 비용까지 없다는 뜻은 아닙니다.
- **재현성:** 같은 입력과 같은 코드·설정에 대해 결과를 재현하고, 어떤 선택자·정규식·검증 조건으로 추출했는지 설명할 수 있습니다.
- **개선의 재사용:** 한 번 수정한 패턴을 이후 같은 형식의 자료에도 적용하며, 재처리 때는 기존 승인·판본 보존 규칙을 따릅니다.
- **변경 대응:** 원천 형식이 달라지거나 해석 범위를 벗어나면 오류·미확보·검토 대상으로 확인하고 규칙을 보완합니다. 자동 처리율이나 비용 절감률의 수치는 별도 측정 없이 주장하지 않습니다.

#### 다른 AI 활용·검증 활동과의 구분

| 활동 | 목적과 산출물 | 설명할 위치 |
| --- | --- | --- |
| AI를 활용한 추출 패턴 개발 | 원천 해석 지식을 재사용 가능한 코드·규칙·테스트로 축적 | 이 절 및 개발 매뉴얼 |
| 업무담당자의 외부 모델 활용 | 부족한 업무지식을 보완해 개별 공고의 업무 판단을 지원 | [4절](#review-workflow) |
| 동료의 데이터셋 외부 검증 | 별도 피드백을 내부 재검증해 데이터·규칙의 정합성 개선 | [6절](#verification) |

매뉴얼·발표자료에 사용할 요약 문구:

> **AI로 추출 패턴과 예외 규칙을 설계·검증해 코드로 축적하고, 이후 동일 형식의 자료는 모델 재호출 없이 자동 처리하여 반복 처리의 건별 AI 비용을 없애고 재현성을 확보했습니다.**

## 2. 일반 사용자 화면 안내

### 2.1 처음 사용하는 순서

1. [HOME](https://www.minslab.kr/poc/home/)에서 정책 또는 관심 지역을 선택합니다.

3. 상단 누적값과 그래프를 함께 봅니다. 색·사선·예상값의 의미는 [3절](#data-rules)을 따릅니다.

6. 공유할 때 보고서 또는 CSV를 내려받고 기준일·대상 범위를 함께 전달합니다.

### 2.3 지도와 지역여건 읽기

지도상의 대표점은 사업 경계·블록 정밀좌표·주소검색 좌표·지역 근사점 등 근거가 다를 수 있습니다. 마커가 있다는 이유만으로 필지 경계를 확보했다고 판단하지 않습니다. 근사 위치는 표시된 위치 근거와 함께 사용합니다.

주변 교통·학교·생활시설은 조회 반경과 기관별 자료 범위의 영향을 받습니다. 운영 중 시설과 계획 시설, 최근접 시설 예외 등을 구분합니다. 데이터 미확보는 주변에 시설이 없다는 뜻이 아닙니다.

1~4인 가구 변화 등 지역 통계는 해당 행정구역의 지표입니다. 개별 사업 입주자 구성이나 실제 수요를 직접 측정한 값으로 확대하지 않습니다. 가구·인구·세대·호·실의 단위와 조사연도, 공표일, 수집일을 확인합니다. 입지 통계 연결 실패나 `null`은 0으로 표시·판정하지 않습니다.

## 3. 데이터 판단·계산·표시 기준

### 3.1 계층과 동일성

| 구분 | 의미 |
| --- | --- |
| 정책 | 정부 정책 목표와 관리 기간 |
| 프로그램 | 정책을 수행하는 사업방식·유형·수단 |
| 사업 | 관리 대상 지구·구역·블록·건물 등의 원장. 원천에 따라 관리 단위가 다름 |
| 원천 레코드 | 기관 API·파일·공고에서 수집한 행 또는 문서 |
| 관리 대표사업 | 동일 사업의 여러 원천을 대조하여 집계에 사용하는 관리 범위 |
| 자료참조 연결 | 문서를 사업에 귀속시킨 근거 관계. 그 자체가 수량·단계 사건은 아님 |

이름 유사도는 검토 후보를 찾는 수단입니다. 동일성은 **지번·구역/블록·시행자·사업방식·공급유형·전체/부분 물량·원모공고**로 확인합니다. 지구 총량, 건설공사 총량, 분양분, 임대분, 금회 잔여 모집량을 모두 더하지 않습니다. 예를 들어 같은 A-1블록의 건설 1,791호와 행복주택 609호는 전체와 부분의 관계를 먼저 대조해야 합니다.

### 3.2 단계·날짜·결측

| 단계 / 사건 | 해석 |
| --- | --- |
| 사업화 | 해당 유형의 사업 추진·계획·공모 등 근거. 기획 확정과 정비구역 지정은 별도 사건 |
| 인허가 | 허가·사업계획 승인 등. 신청, 최초 승인, 변경 승인, 사용승인을 구분 |
| 착공(건설) | 실제 착공과 공사 진행·공정률. 보상·철거·부지조성 착공을 주택 본공사로 자동 변환하지 않음 |
| 준공 | 준공·사용승인 관련 별도 사건. 건설 단계 내부에서 관리되며 공급과 선후가 항상 고정되지는 않음 |
| 공급 | 분양·임대 모집 및 해당 대상 물량. 잔여 재모집과 신축을 구분 |
| 입주 | 입주계획·입주안내·입주 시작·실제 입주호수를 구분. 당첨자·예비자 발표는 입주 완료가 아님 |

- **원천 기준일:** 자료가 설명하는 상태의 기준시점.
- **사건일:** 승인·착공·공고 등 실제 사건 날짜.
- **목표/예정일:** 계획상 날짜. 경과만으로 실적이 되지 않음.
- **수집일:** 시스템이 자료를 가져온 시각.
- **등록/검토일:** 판본과 업무 판단을 저장한 시각.
- **보고 기준일:** 선택된 보고서의 조회 기준. 그날 모든 자료를 확보했다는 뜻은 아님.

월·분기·반기·연도 정밀도와 원문을 보존합니다. 기간 말 정규화가 필요한 집계에서는 원래 정밀도를 함께 표시합니다. `미정`, 잘못된 날짜, `2027년 이후` 등을 임의의 확정일로 만들지 않습니다. **미측정·미확보·상충·확인된 0**은 다른 상태입니다.

### 3.3 측정값 보완과 추정

같은 사업·단계의 수집 측정값을 우선 보존합니다. **측정값이 없다는 이유만으로 목표를 실적으로 채우지 않습니다.** 같은 단계의 확인 사건 또는 그 단계가 선행했어야 하는 후행 사건이 있고, 물량 범위와 날짜 순서가 맞는 경우에만 해당 목표값을 추정에 사용할 수 있습니다.

| 상황 | 처리 |
| --- | --- |
| 수집 측정값 존재, 0 또는 부분 물량 포함 | 수집값 보존 |
| 도달 근거 존재 + 목표일이 확인된 사건 순서 안에 있음 | 미확보 날짜만 조건부 목표 대체 추정 가능 |
| 도달·물량 근거 존재 + 동일 범위 목표량 확보 | 미확보 물량만 조건부 추정 가능 |
| 목표일 경과만 확인 / 추정값만 존재 / 선행 사건만 존재 | 실적 채우지 않음 |
| 일부 후행 물량 확인 | 사업 전체 목표량으로 확대하지 않음 |
| 일정 역전·범위 초과·원천 충돌 | 빈 값 또는 확인 대상으로 유지 |

공급만 확인된 사업을 일괄 착공 실적으로 포함하지 않습니다. 추정에는 `inferred`, `input_rule`, `input_basis`, `field_provenance` 등 근거·판본 정보를 남깁니다. 추정 포함 누적량은 독립적으로 측정한 실제 이행량과 같지 않습니다. 기존 승인·추정을 재검토할 때는 **당시 변경 사유를 먼저 확인**하고 새 근거와 차이를 이력으로 남깁니다.

### 3.4 정책·프로그램 누적 그래프

상단 카드에는 단계별 **누적 도달량**을 표시합니다. 그래프의 각 색 면적은 중복 합산을 피하려고 ‘해당 단계 누적 − 다음 단계 누적’으로 표현합니다. 마지막 입주는 자체 누적량입니다. 아래에서 위로 **사업화 → 인허가 → 착공(건설) → 공급 → 입주** 순서입니다.

설명용 기호: `Aᵢ(t)`는 단계 i의 누적 측정량, `Tᵢ(t)`는 목표 누적량이며, 다음 단계는 `i+1`입니다.

```text
단계의 실색 물량 aᵢ = Aᵢ − Aᵢ₊₁
단계의 목표 물량 qᵢ = Tᵢ − Tᵢ₊₁
붉은 사선 부족분 gᵢ = max(qᵢ − aᵢ, 0)
```

예시: 사업화 누적 90,746 − 인허가 누적 87,098 = 실색 3,648호. 목표 단계 물량 52,947호라면 사선은 52,947 − 3,648 = **49,299호**입니다. 목표 52,947호 전부를 실색 위에 더하지 않습니다. 실적이 목표보다 크면 사선 없이 실색을 유지하므로 전체 높이가 목표 사업화 누적보다 커질 수 있습니다.

| 표시 | 뜻 |
| --- | --- |
| 진한 면 | 현재까지의 단계별 물량. 입력·추정 구성은 근거에서 확인 |
| 붉은 사선 | 해당 단계 목표 대비 양수 부족분. 라벨 예: **미달성(공급)** |
| 오늘 이후 연한 면 | 현재 실적·목표 중 큰 단계 물량에 향후 목표 증감을 반영한 예상 |
| 곡선 | 날짜 사이 시각적 연결. 중간 좌표가 별도 관측값이라는 뜻은 아님 |
| 기준일·보조 기준일 막대 | 카드 조회값과 비교 위치. 움직여도 현재/미래 경계 자체는 이동하지 않음 |
| 회색 목표 배경 | 정책·프로그램의 전체 목표. 개별 연결 사업 소계와 다를 수 있음 |

미래 계산의 시작값은 **단계별 차이 물량의 실적과 목표 중 큰 값**입니다. `t₀`가 자료의 현재 경계라면:

```text
시작값 bᵢ = max(aᵢ(t₀), qᵢ(t₀))
목표 증가 ΔTᵢ(t) = max(Tᵢ(t) − Tᵢ(t₀), 0)
예상 단계 물량 = bᵢ + ΔTᵢ − ΔTᵢ₊₁
```

예를 들어 공급 예정 10호가 도래하면 건설에서 10호가 빠지고 공급에 10호가 더해집니다. 같은 물량의 단계 이동으로 전체량이 늘지 않습니다. 신규 사업화 계획 증가가 있을 때 전체량이 증가합니다. 부족분은 시작값에 포함되므로 미래에 다시 더하지 않습니다. 결측·음수 차이는 코드의 별도 처리와 툴팁을 확인하고 원천값을 변경하지 않습니다.

Y축은 **현재 표시 구간의 누적 최대 높이(실적·갭·예상 포함)의 약 1.3배**를 기준으로 눈금을 조정합니다. `전체 목표 범위`를 선택하면 정책 전체 규모를 확인합니다. `처음`은 포함 사업의 가장 이른 시작점, `현재`는 현재 위치, `마지막`은 마지막 구간으로 이동합니다. 단계 버튼과 상단 카드는 같은 선택을 공유하며 다시 누르면 전체 강조로 돌아갑니다.

### 3.5 부족률과 공정률

그래프 부족 안내 비율은 **부족분 ÷ (부족분 + 해당 단계 누적 달성분)**입니다. 단계 상태 판정의 누적 비교는 `max(도래 목표−최근 측정값, 0) ÷ 도래 목표`를 사용합니다. 서로 다른 분자·분모를 가진 지표이므로 같은 비율이라고 혼용하지 않습니다.

현재 관리 기준은 부족률 2% 이상 ‘지연’, 0% 초과~2% 미만 ‘주의’, 목표 도달·초과 ‘정상’입니다. 목표 미확보·미측정·미도래는 판정 보류입니다. 시각적 사선·경고표시와 실제 일정 지연에 대한 공식 판단은 구분합니다.

건설 공정계획의 0~100% 곡선은 착공~예정 준공 기간에 비례한 월별 추정일 수 있습니다. 공식 중간 공정목표가 아니며, 실제 공정률은 관측일과 함께 비교합니다.

## 4. 업무담당자의 신규 자료 검토

### 4.1 ‘외부 모델 도움’의 위치 — 업무 수행 지원

현재 사용자는 실제 업무담당자 역할을 가정해 업무를 수행하고 있습니다. 주택공급 업무지식이 충분하지 않은 부분에서 **외부 모델의 분석을 도움받아 자료를 이해하고 판단 후보를 마련한 것**입니다. 외부 모델은 담당자 업무를 보조하는 도구이며, 이 활동을 독립된 외부 검증·전문기관 인증·별도 승인으로 세지 않습니다.

```mermaid
flowchart LR
    A[담당자 역할의 사용자] --> B[CSV와 원문으로 업무내용 확인]
    B --> C[필요할 때 외부 모델의 분석 도움]
    C --> D[의견과 공식 근거·기존 사유 대조]
    D --> E[담당자 권한으로 판단 저장]
    E --> F[상태·사유·판본·이력 확인]
```

모델 의견은 오인·누락·과거 자료 인용 가능성이 있는 **검토 입력**입니다. 사용자 위임에 따른 시스템 처리는 기관 담당자에게 실제로 질의해 답변받은 것과 구분합니다. 과거 파일명이나 저장 사유의 ‘외부 검토’ 문구가 이 업무 보조를 가리키는 경우, 파생 문서에서는 ‘업무담당자의 외부 모델 활용’으로 설명합니다. 기존 감사 이력의 원문은 이 용어 정리 때문에 소급 변경하지 않습니다.

동료 피드백으로 데이터셋의 정확성을 개선한 **별도 외부 검증 과정**은 [6절](#verification)에서 다룹니다.

### 4.2 상태의 의미

| 화면 상태 | 코드 | 처리 의미 / 다음 행동 |
| --- | --- | --- |
| 검토 대기 | `REVIEW` | 아직 판단하지 않았거나 원문·연결 변경으로 재검토 필요. 자료별 질문과 근거부터 확인 |
| 보류 | `HOLD` | 검토했으나 동일성·범위·원문 등 필요한 근거가 부족. 보류 사유의 해소 자료를 확보 |
| 사업 등록 대기 | `REGISTRATION_REQUIRED` | 후보 사업/자산을 식별하고 등록 검토 승인. **실제 사업 생성·정책 귀속·물량 반영 완료가 아님** |
| 자료 연결 승인 | `APPROVED` | 기존 사업에 자료참조 연결 확정. 정책 매핑·호수·목표·실적은 자동 변경하지 않음 |
| 제외 | `EXCLUDED` | 해당 개별사업 연결 업무에서 제외. 원문과 판단 이력은 보존. 정책·교통·복지 참고자료도 이 범주일 수 있음 |

원문 판본이 달라지거나 승인 연결의 상태가 바뀌면 화면은 다시 `REVIEW`가 될 수 있습니다. 이전 승인이 사라진 것이 아니라 새 판본에 대한 재확인이 필요한지 이력을 봅니다. 좌측 메뉴 배지의 미완료 수에는 검토 대기뿐 아니라 보류·등록 대기가 포함됩니다.

### 4.3 실제 처리 순서

1. **데이터 관리 → 신규 자료 검토**에서 상태·우선순위·자료명으로 대상을 좁힙니다.
2. 목록 숫자만 보지 말고 자료를 선택해 검토 질문, 원문 URL, 게시일·판본, 이전 판단을 읽습니다.
3. 수동 수집 이력이 있으면 **수동 수집 원문·첨부 확인**을 펼칩니다. 이전 판본 표시가 있으면 현재 원문과 다시 대조합니다.
4. 기존 사업 대장과 지번·블록·시행자·유형을 비교합니다. 이름이 비슷하다는 이유로 연결하지 않습니다.
5. 기존 사업이 맞으면 자료 연결 승인, 다른 식별 가능한 대상이면 후보명을 구분해 등록 대기, 핵심 자료가 부족하면 보류, 관련 없는 사건이면 제외를 선택합니다.
6. 담당자명, 판단 사유, 확인한 원문, 적용 범위와 후속 과제를 기록합니다. 승인에는 원문 확인과 정책 선택이 필요합니다. 정책 귀속 근거가 없으면 `UNASSIGNED`를 사용하며 이름만으로 귀속시키지 않습니다.
7. 저장 후 상태와 **이 자료의 이전 검토 이력 보기**를 확인합니다. 충돌(409)이면 최신 판본을 재조회하고 조정합니다.

등록 대기는 자동 등록 큐가 아닙니다. 실제 사업 생성, 대표 단위·프로그램·정책 귀속, 목표/일정·실적 반영은 각각 후속 업무입니다. 현재 화면의 저장 결과를 ‘신규 사업 및 실적 반영 완료’라고 보고하지 않습니다.

### 4.4 사유 기록의 최소 내용

- 무엇을 확인했는가: 공고번호·지번·블록·기관·공급유형·판본·URL.
- 왜 같은/다른 사업인가: 대조한 기존 사업 ID와 일치·불일치 항목.
- 어떤 사건인가: 최초 모집, 정정, 잔여 모집, 계약안내, 착공 등.
- 무엇을 반영하는가: 자료참조, 등록 후보, 보류 또는 제외. 실제 물량·일정 변경 여부.
- 무엇이 남았는가: 필요한 원모공고·관리번호·공식 승인서·정정 확인.
- 이전 사유와 무엇이 달라졌는가: 유지·보완·정정의 이유. 당시 승인 근거 보존.

`261029 업무담당자 확인(김민)`은 10월29일 사용자 위임 업무에서 사용한 이력 표기 예입니다. 다른 담당자는 본인의 실제 업무 표기를 사용합니다. 외부 모델의 추론만으로 기관 확인 완료라고 기록하지 않습니다.

### 4.5 CSV·구조화 JSON으로 업무 지원받기

**현재 목록 CSV**는 상태·검색어·우선순위 조건을 적용하고, **전체 상태 CSV**는 모든 상태를 받습니다. 다운로드 버튼을 누를 때 생성되며 목록 진입 때 자동 다운로드하지 않습니다.

기존 CSV 열에는 자료ID·제목·상태·출처·원문URL·판본/해시·우선순위·질문·근거·연결 사업·등록 후보·담당자·사유·검토 이력 등이 포함됩니다. 다음 4열은 최근 수동 수집 보완 항목입니다.

| 열 | 뜻 |
| --- | --- |
| 수동수집상태 | 미수집 / 현재 판본 원문·첨부 수집 / 이전 판본 수집·재확인 필요 |
| 수동수집본문 | 별도 보관한 수동 수집 텍스트 |
| 수동수집확인내용 | 수집자가 확인한 내용과 불일치·추가 확인 사항 |
| 수동수집첨부_JSON | 첨부 이름·URL·해시 등 저장 정보 |

2026-11-02부터 `본문보유여부`는 탐색·수동·AI 본문을 함께 확인합니다. `통합유효본문`·`통합본문출처`·`통합본문품질`을 우선 확인하고, `본문판본별상태_JSON`으로 원문 판본·해시·길이·과거 판본 여부를 대조합니다. 목록·공유문구와 과거 판본만 있으면 유효본문으로 채택하지 않습니다. 요약만 있으면 `SUMMARY_ONLY`, 내용 문자열을 확보했어도 사실 확정 전이면 `TEXT_AVAILABLE_UNVERIFIED`로 표시합니다. 기존 원본·수동·AI 본문 열은 이력 비교용으로 유지합니다. `외부검증결과` 등 CSV 열 이름은 분석 의견을 적는 서식이며 독립 검증이 자동 수행됐다는 뜻이 아닙니다.

**현재 목록 근거 JSON** 버튼은 CSV와 같은 상태·검색·우선순위 범위를 `publication-review-evidence-2` 구조로 내려줍니다. 자료별 정확한 인용문·본문 해시, 확인 범위, 수치와 단위·모집/재고/계획 구분, 착공·공급·준공·입주 일정의 계획/예정/보도된 사실 구분, 미확인 필드, 정정·후속 사건 관계를 제공합니다. 검증되지 않은 사실은 빈 목록과 미확인 항목으로 남기며 추측해서 채우지 않습니다. 다운로드 시 외부 모델 호출이나 원문 재수집은 하지 않습니다.

담당자 재검증은 별도 `publication_assessment` 판본과 `PUBLICATION_EVIDENCE_REVIEW` 감사 이력으로 저장합니다. 현재 원문·검토 판본과 정확한 본문 해시·인용이 맞아야 구조화 사실을 유효하게 내보냅니다. `외부모델검토의견_JSON`은 **담당자 업무 보조 권고**이고, 동료에 의한 독립 외부검증과 구분합니다. 시스템 상태·확정 자료 연결·실적 합산 허용은 각각 별도입니다. 자료 연결 승인도 별도 실적 승인 전에는 호수를 합산하지 않습니다. 개인정보 식별번호·개인 연락처·명단 영역은 내보내기에서 제외하며 첨부 당첨자 명단을 자동 추출하지 않습니다.

여러 상태 CSV를 합칠 때 `자료ID`로 중복을 제거합니다. `OPEN`은 검토 대기·보류·등록 대기를 포함하므로 등록 대기 파일을 다시 더하면 중복됩니다. 모델의 응답은 자동 재수입·승인되지 않습니다. 원문 대조 후 화면 또는 승인된 관리 절차로 저장합니다. CSV의 스프레드시트 수식 방어용 접두 문자를 근거값으로 오인하지 않습니다.

### 4.6 수동 원문·첨부 보완의 경계

수동 보완은 `publication_supplement` 판본과 `PUBLICATION_MANUAL_COLLECTION` 감사 이력으로 저장됩니다. 원문 탐색 판본에 연결되어 자동 목록 재수집으로 본문이 덮어써지지 않습니다. 목록에는 요약·첨부 메타데이터만 제공하고 전체 본문은 CSV 생성 시 포함해 조회 부하를 줄입니다.

**일반 사용자용 파일 업로드·자동 승인 기능은 아닙니다.** 현재 수동 보완 저장은 유지관리자의 검증된 서버 작업 경로입니다. 사용자는 화면의 요약·첨부와 CSV를 이용합니다. 당첨자·서류심사 대상자 등 개인 명단은 모집·사업 근거와 분리하며 수집 필요성이 없는 개인 정보 목록은 가져오지 않습니다.

화면에서 현재 추출 방식, 발견한 패턴·제안 사유, 적용 범위, 시험 전후 본문과 판단 이력을 확인합니다. 담당자 이름과 판단 사유를 기록하고 다음 중 하나를 선택합니다.

직접 반영 범위는 **AI 자료 수집기의 HTML 본문 CSS 선택자**입니다. 설명문뿐인 제안은 승인할 수 없으며, 확인한 선택자를 입력하거나 재분석을 요청합니다. 접근 차단·첨부 문제는 선택자 변경으로 해결한 것으로 처리하지 않습니다. 날짜·물량 판정, API 수집기나 운영 소스 코드 변경은 이 기능의 승인 대상이 아닙니다.

시험 시 ‘반드시 보존할 핵심 원문 문장’을 입력합니다. ‘이 주소만’은 해당 원문에 한정하고, ‘같은 사이트·경로’는 저장된 서로 다른 과거 정상 자료 2건 이상에서 본문 보존 시험까지 통과해야 합니다. AI가 제안한 시험 항목 자체를 검증 성공으로 간주하지 않습니다. 시험에는 원문 조회 1회가 있고 모델 호출은 없습니다. 시험은 24시간 유효하며 원문 판본·진단·동일 범위 규칙이 바뀌면 다시 시험해야 합니다.

규칙·검증 결과·담당자 판단은 공유 SQLite 원장에 버전과 이력으로 저장합니다. HTML을 실행하거나 운영 코드를 생성·실행하지 않습니다. 승인 규칙이 새 원문과 맞지 않으면 기본 추출기로 복귀하면서 수집 오류를 남깁니다. 업무자료의 연결·정책 귀속·실적 승인은 별도 절차입니다.

### 외부 보류 의견의 교차 검토와 증빙 CSV (2026-11-03)

외부 모델 의견은 업무담당자의 지식 보조자료로 보존하고, 원문·현재 원장과 별도로 대조한 결과를 **외부 의견 교차검토**에 표시합니다. AI 작업자 항목과 단계별 실적 검토 항목에서 권고, 내부 확인 결과, 조치 및 남은 확인사항을 볼 수 있습니다. 검토 후 원천 판본이나 업무판단이 바뀌면 재확인 표시가 나옵니다. 이는 동료의 독립적인 데이터셋 검증이나 실적 승인과 별개입니다.

외부 모델에 전달할 때는 AI 작업자 상단의 **외부 검토용 · 대상별 통합 CSV**를 사용합니다. 같은 자료가 수집·업무담당 양쪽에 있으면 대상ID별 한 행으로 내보내며, 원래 역할별 판단은 `에이전트별기록_JSON`과 `합쳐진기록수`에 보존합니다. 기존 역할별·합본 CSV도 유지합니다.

단계 검토에는 `대상유형`, 실제 저장된 `수집본문`, `증빙상태`, `증빙패키지_JSON`, 사건군·중복 후보ID·상이한 값 후보ID, 교차검토 결과를 제공합니다. 본문이 없는 자료는 인용문을 본문인 것처럼 채우지 않고 `MISSING`으로 표시합니다. 저장 본문과 개인정보 제거 후 내보낸 본문의 해시를 구별합니다. 본문은 CSV 요청 때만 포함하며 일반 목록 조회에서는 가져오지 않습니다.

`can_apply`는 형식상 수동 검토 가능 여부이며 승인 완료가 아닙니다. `auto_eligible`는 별도의 자동 검증 조건입니다. 같은 사업·단계에 날짜나 물량이 다른 미해결 후보가 있으면 자동 반영을 차단합니다. 동일 사건 후보들은 같은 사건군으로 표시하되 출처 이력을 삭제하지 않습니다. 실적은 누적값 대체이므로 중복 후보를 증분으로 합산하지 않습니다.

### 수집 진행 표시 — 2026-10-30

`지금 수집` 아래에 현재 단계·출처/자료명·사용 모델·경과 시간과 진행 바를 표시합니다. 출처 탐색과 자료 처리는 각각 해당 단계의 완료 수/대상 수로 계산하며, 진행 중 상태는 5초, 대기 상태는 60초 간격으로 조회하며 숨겨진 화면에서는 멈춥니다. 완료율 100%는 처리 시도의 종료이며 원문 접근 실패·심층 검토 대기는 별도 표시합니다.

- **확인된 토큰:** 이번 실행의 공급자 응답에 포함된 입력+출력 합계. 모델별 내역도 표시합니다.
- **예약 토큰:** 응답 대기 중 요청의 보수적 예약 상한입니다. 현재 생성한 토큰량이 아닙니다.
- **남은 작업 예상:** 이번 실행의 완료 자료당 확인된 토큰 평균에 남은 자료 수를 곱하고, 현재 미완료 자료에서 이미 확인된 사용량을 뺍니다. 첫 자료 처리 전이나 변경 없는 자료만 처리한 경우에는 추정하지 않습니다. 원문 길이·캐시 생략·심층 검토 여부에 따라 실제 사용량과 달라집니다.
- 응답 미확정 예약은 확인된 소비와 구분하고 기존 공통 예산 정책대로 유지합니다. 이 표시는 추가 모델 호출을 하지 않습니다.

SQLite `run_progress`에 단계와 완료 건수를 별도 보존합니다. 기존 이력/호출 원장은 그대로 유지하며 세부 진행 기록이 없는 과거 실행은 실제 이벤트 수와 토큰만 표시합니다. 실행 중 새로고침해도 펼친 실행 이력은 유지됩니다.

### 단계별 실적 반영 검토 (2026-11-02 보완)

**신규 자료 검토 → 단계별 실적 반영 검토**를 펼치면 사업화·인허가·착공·준공·공급·입주별 기존 관리값, 새 근거의 날짜·물량, 원문 인용과 보류 사유를 볼 수 있습니다. ‘자료 연결 승인’과 ‘실적 반영 승인’은 별도이며, 목표량이나 예정일을 새 실적으로 생성하지 않습니다.

- 관리자: 원문·동일 사업·누적 물량·날짜 의미를 확인하고 담당자·사유를 입력한 뒤 승인/제외합니다. 기존 확정 실적 변경에는 별도 정정 확인이 필요합니다. 원문·사업·관리값·정책 연결 판본이 바뀌면 다시 조회해야 합니다.
- **판단보류 CSV 받기**: 단계별 현재값·후보값·인용·판본·보류 사유를 내보냅니다. 상단 수집/업무담당 통합 판단보류 CSV에도 이 제안들이 포함됩니다. 신규 자료 목록 CSV/JSON은 자료 연결 검토용이며, 실적 검토 CSV와 목적이 다릅니다.
- 공급의 추가·잔여·재모집과 부분 물량은 신규 총량에 더하지 않습니다. 공정률의 확인일은 실제 착공일과 구분하며 자동 승인하지 않습니다. 승인 시 같은 사업·단계의 **누적값을 대체**하므로 이미 반영한 물량을 다시 합산하지 않습니다.
- 업무담당자 야간 실행은 이미 연결된 자료도 실적 근거를 검토합니다. 같은 입력의 보류 자료가 처리 한도를 반복 소모하지 않으며, 원문·본문·사업 식별 판본이 바뀌면 다시 분석합니다. 공식 HTML 본문 복구는 실행당 최대 3건으로 제한합니다. PDF·비공식 자료의 공식 근거 미확보는 계속 사람 확인 대상으로 남을 수 있습니다.
- 화면 조회/CSV에는 외부 요청·모델 호출·DB 변경이 없습니다. 저장된 근거 점검은 관리자 버튼 또는 야간 업무담당자 실행에서 수행합니다. 기존 01~05시 예약·공통 모델 사용량 한도는 유지합니다.

대조 후보는 과거 실적의 근거 보강을 포함하며, 그 건수를 ‘새 실적’ 또는 ‘누락 호수’로 해석하지 않습니다. 점검 결과는 [전체 단계 진단](docs/evidence/CONSTRUCTION_PIPELINE_20261102/README.md)에 보관합니다.

## 5. 정책·사업 추진현황 보고서

### 5.1 보고서별 범위

| 보고서 | 주요 내용 | 저장·출력 |
| --- | --- | --- |
| 정책 추진현황 보고서 | 정책 목표·현재 도달량·전망, 유형·지역·사업별 분석 및 근거 | 본문과 붙임 3종 분리 |
| 프로그램 보고서 | 프로그램 범위의 진행·구성 사업·근거 | 해당 화면의 기존 보고서 경로. 정책/개별사업 전용 형식을 일괄 적용한 것으로 설명하지 않음 |
| 개별 사업 추진현황 분석보고서 | 기본정보, 단계 진행, 물량·변경, 행정절차, 건설·공급·입지·검토 내용 등 9개 장 | 두 진행 그래프 유지, 붙임 4종 분리 |

사업 보고서의 두 그래프는 **사업화~입주 단계별 진행 카드**와 **최초 데이터 시점부터 120개월의 목표·측정 시계열**입니다. 시계열은 아래부터 사업화·인허가·착공·공급·입주를 일정 간격으로 표시합니다. 목표는 옅은 파랑, 측정은 분홍, 수집 측정과 추정 표식을 구분합니다. 준공 사건은 별도 단계 카드·건설 내용에서 확인합니다.

### 5.2 생성 절차

1. 정책 또는 사업 화면에서 **추진현황 보고서 만들기**를 누릅니다.
2. 기준일·기간·지역·대상 사업, 보고서 유형 등 해당 창이 제공하는 조건을 확인합니다.
3. 보고서를 생성하고 대상 범위·입력 판본·최종 수집일·생성일을 확인합니다.
4. 본문은 HTML·CSV·산출근거 JSON 또는 브라우저 인쇄/PDF로 저장합니다.
5. 상세 명세가 필요하면 **붙임 자료 생성·다운로드** 또는 **붙임 생성·다운로드**를 별도로 누릅니다.
6. 공유할 본문·붙임·JSON의 기준일과 입력 SHA-256이 같은지 확인합니다.

붙임은 버튼을 누를 때 생성하며 **본문과 동일한 입력 기준본**을 사용합니다. 붙임을 받는 시점의 최신값을 다시 섞지 않습니다. 본문 다운로드만으로 붙임까지 전달됐다고 판단하지 않습니다. PDF는 브라우저 인쇄 기능으로 만들며 중앙 PDF 발급 서비스가 아닙니다.

달성률을 산정할 수 없는 열은 숨기도록 처리합니다. 열이 없다고 0% 달성이라고 해석하지 않습니다. 빈 표·미확보는 0호와 구별하며 긴 사유·URL은 표 안에서 줄바꿈합니다.

### 5.3 재현과 보관

개별 사업 보고서 생성이력은 **현재 브라우저의 IndexedDB**에 저장됩니다. 서버 공용 문서함이나 다른 사용자에게 공유되는 이력이 아닙니다. 브라우저 데이터 삭제·다른 기기 사용 시 그대로 보장되지 않으므로 장기 보관에는 JSON과 출력물을 내려받습니다. 계산 버전이 다른 저장본을 현재 산식으로 조용히 재해석하지 않습니다.

보고서의 기준일 조회와 엄밀한 ‘그날 시스템이 알고 있던 내용’은 다른 개념입니다. 원천 기준일·사건일·수집시각·판본·입력 해시를 함께 확인하고, 필요하면 당시 DB 스냅샷과 비교합니다. 생성자 표기가 브라우저 사용자 수준이면 인증된 담당자 서명으로 사용하지 않습니다.

## 6. 데이터 정합성 개선 — 동료 외부 검증과 내부 재검증

AI를 활용한 추출 패턴 개발은 [1.2절](#ai-patterns)에서 별도로 설명합니다. 이 절은 [4.1절](#review-workflow)의 **업무담당자가 외부 모델의 도움을 받아 개별 공고를 처리한 활동과 별개**입니다. 여기서 외부 검증은 데이터셋을 동료에게 제공하고, 동료가 검토한 피드백을 받아 데이터·규칙의 정합성을 개선한 과정입니다.

| 구분 | 담당자 업무의 모델 활용 | 데이터셋에 대한 동료 외부 검증 |
| --- | --- | --- |
| 목적 | 부족한 업무지식 보완, 자료 이해와 판단 후보 마련 | 데이터셋 오류·누락·중복·규칙의 문제 발견 |
| 주체 | 업무담당자 역할의 사용자와 보조 도구 | 데이터셋을 검토하는 동료, 반영·재검증하는 내부 개발·데이터 담당자 |
| 입력 | 미연결 공고·검토 CSV·원문·기존 판단 사유 | 버전이 특정된 데이터셋·산정 기준·근거·검토 과제 |
| 결과 | 승인·등록 대기·보류·제외의 업무 판단 | 수정 제안, 패턴 규칙 개선, 데이터 보강 및 다음 데이터셋 버전 |
| 검증 지위 | 독립된 검증 1회로 별도 집계하지 않음 | 동료 피드백에 의한 별도 외부 검증 활동 |
| 최종 반영 | 담당자 권한으로 사유·이력 저장 | 내부에서 원문·대장·테스트로 재검증한 뒤 반영 |

동료가 어떤 도구를 사용했는지는 확인된 이력만 기록합니다. 모델 산출물만 있고 독립된 동료 검토 기록이 없으면 이를 ‘동료 검증 완료’로 바꾸어 표현하지 않습니다. 외부 검증은 공인 인증이나 전수 정확도 보증과도 다릅니다.

```mermaid
flowchart LR
    V1[데이터셋 V1] --> P1[동료 피드백 1]
    P1 --> R1[내부 근거 대조·재검증]
    R1 --> I1[패턴 규칙 개선·데이터 보강]
    I1 --> V2[데이터셋 V2]
    V2 --> P2[동료 피드백 2]
    P2 --> R2[내부 재검증]
    R2 --> I2[규칙 개선·데이터 보강]
    I2 --> VN[다음 데이터셋 버전]
```

**데이터 정합성 확인**의 데이터셋 개선 과정은 위 반복을 요약하고, 노드를 선택하면 발견 사항·수정 내용·근거를 자세히 확인하는 용도로 사용합니다. 최초 공유 시점 이후 노드에는 날짜를 반복 표기하지 않는 화면 원칙을 적용하되, 실제 판본·시각·파일 해시는 내부 근거에서 보존합니다.

회차 기록에는 입력 데이터셋 버전·해시, 검토자/검토 범위, 발견 문제, 관련 자료ID, 내부 재검증 결과, 채택/보류/기각 사유, 변경 전후 값, 수정 규칙·코드·테스트, 남은 과제를 남깁니다. 제출된 의견 수를 그대로 오류 수정 수로 세거나 일부 검증 점수를 전체 정확도로 소개하지 않습니다.

현재 화면·과거 보고서의 ‘외부 검증’, ‘조원 피드백’, ‘외부 모델’ 표기는 생성 당시 이력의 맥락을 확인해야 합니다. 매뉴얼·발표자료에서는 이 절의 두 활동 구분을 적용하고, 실제 기록이 없는 독립 검증을 새로 주장하지 않습니다.

## 8. 유지관리 운영

### 8.1 수집 흐름·주기

**운영 시간: 자동 대량 작업은 한국시간 01:00 이상~05:00 미만에 실행합니다.** 기본 AI 일정은 알고리즘 01시 → 수집 02시 → 업무담당자 03시이며 역할별 자동 실행 활성화 여부는 기존 설정을 유지합니다. 기존 야간 범위 밖의 AI 일정은 이 기본 시각으로 해석하고, 설정 화면에서는 01~04시만 선택합니다. 실제 시작은 앞선 작업 완료와 큐 상태에 따라 늦어질 수 있습니다.

- 낮에는 신규 공고·보도 감시와 사용자 조회를 유지합니다. 전체/과거 수집, 자동 연결·기준본 생성, 지역 통계 캐시 갱신, 보존 데이터 정리는 야간에 실행합니다. 자동 작업은 05시 이후 새 대량 요청을 시작하지 않고 확인 지점에서 중단·대기합니다. 이미 진행 중인 요청·DB 트랜잭션은 안전하게 마칩니다. 명시적 수동 실행은 시간 제한의 예외입니다.
- 수집 상태는 화면이 보일 때만 확인합니다. 대기 중 AI 상태는 60초, 실행 중에는 5초 간격입니다. 지역 화면은 5분, 원천 상태·화면 판본은 60초 간격이며 숨겨진 화면에서는 자동 갱신을 멈춥니다. 공용 모델 한도 **표시**는 60초 캐시이고 실제 예약·정산은 실시간 공통 원장을 사용합니다.
- HTTP ETag/Last-Modified가 있으면 조건부 요청으로 변경 없는 원문의 재전송을 줄입니다. 캐시 파일 부재·무결성 실패 시 원문을 다시 받으며 7일마다 전체 재확인합니다. 새 텍스트 원문은 압축 효과가 있을 때 gzip으로 저장하고, SHA-256·원본 바이트 수는 압축 전 기준입니다. 원문 판독은 `backend.raw_archive.read_raw()`를 사용합니다. 기존 원문 파일은 임의 이동·삭제하지 않습니다.
- 기준본은 관측 ID·시각·원래 검증 해시를 보존하면서 동일 내용을 `home_metric_snapshot_content`에 공유합니다. migration `0018_snapshot_content` 후 신규 생성에 적용하고, 기존 기준본은 야간 유휴 시간에 10개씩 해시·복원 일치를 검사하며 전환합니다. 기존 전체 JSON 형식도 조회할 수 있습니다. 첫 전환 후 구버전 리더로 단순 롤백하면 안 되며 공유 내용을 복원하거나 새 리더를 유지해야 합니다.
- `/poc/home/api/operations/status`에서 야간 창·다음 시작 시각·유지관리 진행을 확인합니다. `data/runtime/operations-maintenance.json`과 `archive-inventory.sqlite3`에는 재개 지점·원문 참조 목록을 저장합니다. 이 목록만으로 삭제를 결정하지 않습니다. PostgreSQL 일반 autovacuum을 유지하며 낮 시간 `VACUUM FULL`·대량 삭제는 실행하지 않습니다.
- 애플리케이션 컨테이너 로그는 `local` 드라이버의 파일당 10MB·3개 회전으로 제한합니다. 기존 DB 컨테이너는 불필요한 서비스 중단을 피하기 위해 그대로 유지하고, 다음 계획된 재생성 때 compose의 동일 로그 제한을 적용합니다.


2026-10-31 운영 API는 내부 18101 포트로 무중단 전환했습니다. `POC10_HOST_PORT`와 루트 `POC10_UPSTREAM`을 함께 맞춥니다. API는 `--lifespan off`로 수집/복구/과거 데이터 재조정을 중복 실행하지 않고, 수집 작업의 복구와 예약은 전용 worker가 담당합니다. DB 스키마 migration은 배포 명령의 `alembic upgrade head`로 유지합니다.

원천 등록부는 [sources.py](backend/sources.py), 예약 주기는 [collection_jobs.py](backend/collection_jobs.py)가 기준입니다. 일반 원천은 수집 → 연결 → 스냅샷 후속 단계로 처리하며, 신규·변경 건수가 0이고 직전 성공 배치와 완전성·수집 범위 등 메타데이터도 같으면 연결·스냅샷을 생략합니다. 수집 이력과 마지막 점검 시각은 계속 갱신합니다.  `discovery_only` 공고·보도 탐색은 수집 후보만 저장하고 자동 실적 연결 단계로 넘기지 않습니다.

| 분류 | 설정 예 |
| --- | --- |
| 최신 탐색 | 국토부·국무조정실·SH·LH·iH·서울시·뉴시스 탐색 경로 등 1시간 |
| 모집공고 | LH·GH·iH 공고 2시간, LH 상세 4시간 |
| 기타 원천 | 원천별 `refresh_days`; SH 재고·서울 정비사업·GH 준공자료는 6시간 |
| 과거 보강 가속 | 01:00~05:00 KST, 소스당 하루 성공 배치 3개까지, 최소 1시간 간격. 통상 일일 대량 수집도 야간 실행, 명시적 수동 실행은 유지 |
| 수동 전용 | `manual_only=True`: 자동 예약 제외, 필요한 범위만 명시적으로 실행 |

시간은 성공 후 재실행 기준입니다. 대기열·호출 제한·실패 재시도 때문에 정확한 시각을 보장하지 않습니다. worker는 `LATEST`와 `BACKFILL`을 나누고 leader lock·lease·heartbeat로 중복 실행과 중단 복구를 관리합니다. 링크·페이지 구조가 바뀐 확정적 오류는 24시간 자동 재시도를 보류하고, 수동 재점검은 허용합니다. HTTP503 등 일시적 실패는 기존 재시도 간격을 유지하며, 성공 자료가 있다는 이유로 최근 실패를 숨기지 않습니다.

국토부·국무조정실 신규 탐색은 각 최신 3페이지에서 최근 30일 주택 관련 제목·게시일·원문 링크를 검사합니다. 모든 기관·언론사·과거 공고 전수를 검색하는 기능은 아닙니다. 공개 RSS 탐색도 공식 사업단계 증명과 구분합니다.

> 2026-10-31 저장공간 정리: HOME은 서버 내부 PostgreSQL/PostGIS를 사용합니다. 저장된 LH 이력에서 참조하는 원문은 유지하고, 24시간 이상 지난 미참조 `lh_notice_detail` HTML만 해시·복원 검증 후 정리합니다. 매일 02:40 KST 이후 최대 10분 지연으로 `home-storage-retention.timer`가 실행하며 회차별 복원본은 `data/storage-maintenance/home/`에 7일 보관합니다. 업무 DB·참조 원문·기존 정기 백업은 보존합니다. 최초 10번과 폴더·URL은 유지하고 포트폴리오 메뉴로 분류합니다.

### 8.2 일상 점검

1. API·DB·수집 worker·지역 worker의 실행/health를 확인합니다.
2. **출처와 수집현황**에서 마지막 시도·마지막 성공·설정 주기·실패 사유를 봅니다.
3. `/api/collection-jobs`에서 `QUEUED/RUNNING/RETRY/FAILED`와 처리 단계를 확인합니다.
4. 수집 범위와 원문·첨부·본문 추출 잔여를 확인합니다. 성공 배치만으로 전수 확보를 선언하지 않습니다.
5. 신규 자료 검토의 미완료 수, 원문 변경 재검토, 보류 해소 자료를 확인합니다.
6. 정책·사업 화면, 보고서 본문·붙임, CSV를 필요한 범위에서 점검합니다.
7. 작업일지에 대상·범위·원인·조치·검증·남은 과제를 남깁니다.

### 8.3 수동 수집·재수집

수집은 외부 API 호출과 DB 기록을 발생시킵니다. 원천 ID·조회 범위·호출 제한·기존 실행 여부를 확인한 뒤 실행합니다. 화면의 관리자 수집 요청 또는 대상 원천을 지정한 CLI를 사용합니다.

```bash
# 저장소 루트/운영 호스트: 지정한 원천 수집 및 도구가 수행하는 후속 처리
sudo docker exec poc10-home-api python -m scripts.collect --source molit_press_watch

# 개발·운영자가 동작을 확인한 뒤 필요한 원천으로 source ID를 변경
sudo docker exec poc10-home-api python -m scripts.collect --source opm_press_watch
```

인자 없는 전체 재수집이나 날짜별 `apply_*`, `restore_*`, `repair_*` 스크립트를 일상 점검 명령처럼 실행하지 않습니다. 일부 도구는 특정 당시 데이터·사업ID를 전제로 승인값을 변경합니다. 실행 전 코드의 대상·dry-run 여부·판본 검사·적용 효과를 확인합니다.

주소 좌표 수집은 후보 전체 payload를 메모리에 적재하지 않고 주소 필드만 스트리밍합니다. `POC10_GEOCODE_PER_KIND_REGION`으로 유형·시도별 조회 상한을 조정하며 최대25, 기본25입니다. `NOT_FOUND`에 임의 좌표를 넣지 않습니다. 대용량 수동 작업은 운영 API와 자원을 분리하고 동일 원천 lock을 준수합니다.

### 8.4 설정과 인증

| 설정 | 목적 |
| --- | --- |
| `POC10_DATABASE_URL` | 전용 DB 연결. 개발·복구에서는 반드시 격리 DB |
| `POC10_DB_PASSWORD` | 배포 도구가 사용하는 전용 DB 비밀번호 |
| `POC10_INTERNAL_SECRET` | 부모→HOME 관리자 요청의 HMAC 서명 비밀값 |
| `POC10_UPSTREAM` | 부모 서비스의 HOME upstream |
| `POC10_DATA_DIR` | 실행 데이터·원문 경로 |
| `POC10_AUTO_COLLECT` | 해당 프로세스의 자동 예약 활성 여부. worker의 이미 대기 중 작업 처리까지 정지하는 스위치는 아님 |
| `POC10_API_MEMORY_MB` | Docker CLI 배포의 API 메모리 한도 |
| 원천별 API 키 | [API_KEYS.md](docs/API_KEYS.md)와 `.env.example`의 변수명 참고 |

운영 API는 자동 수집을 끄고 별도 worker가 예약합니다. **수집을 완전히 멈추려면 worker 실행/대기 작업까지 관리**해야 합니다. API 프로세스의 환경변수 하나만 바꾸고 전체 수집이 중지됐다고 판단하지 않습니다.

관리자 요청은 부모 세션·허용 경로·동일 출처 검사를 거쳐 내부 `x-home-admin` 서명을 전달합니다. 내부 검증은 시간·메서드·경로를 포함하며 짧은 유효시간을 사용합니다. 브라우저에서 내부 비밀값을 사용하거나 인증을 우회하지 않습니다. 내부 API에 존재하는 관리 경로가 부모 프록시에서 모두 공개되는 것은 아닙니다.

`.env`, `data/runtime/*.env`, 비밀번호·API 키는 저장소·스크린샷·공유 문서에 넣지 않습니다. 신규 환경에서만 예제 설정을 복사하고 환경별 값으로 채웁니다. API는 loopback에 바인딩하며 부모 프록시를 통해 공개합니다.

<a id="deployment"></a>
### 8.5 배포와 되돌리기

현행 운영은 [deploy.py](scripts/deploy.py)의 **Docker CLI 방식**입니다. 원문·DB를 유지하고 API·worker 이미지를 교체합니다. 컨테이너 시작 시 Alembic migration이 실행됩니다.

```bash
# 저장소 루트. 검증·백업 범위 확인 후 운영 배포
sudo python3 PoC/10-home/scripts/deploy.py
curl --fail http://127.0.0.1:18101/health
sudo docker logs --tail 50 poc10-home-api
sudo docker ps --filter name=poc10-home
```

현재 CLI 네트워크는 `poc10-home`, DB 볼륨은 `poc10-home-pgdata`, API 포트는 `127.0.0.1:18101 → 8000`입니다. `data/`는 `/app/data`에 연결됩니다. Compose는 신규 환경 대안이며 CLI의 컨테이너·볼륨과 혼용하지 않습니다. Compose의 `home_pgdata`는 CLI 볼륨과 이름·실체가 다를 수 있습니다. DB 자원 한도도 CLI 초기 생성과 Compose 설정이 다르므로 실제 컨테이너 설정을 확인합니다.

배포 도구는 이전 API·수집 worker를 중지·이름 변경해 보존합니다. 지역 worker는 교체하므로 동일한 자동 보존을 가정하지 않습니다. 이전 컨테이너 존재는 DB 복구를 대체하지 않습니다. 되돌릴 때는 이미지와 스키마 호환성을 확인하고 새 worker를 중지해 중복 수집을 막은 뒤 계획한 버전으로 복귀합니다. DB down migration·볼륨 삭제를 단순 앱 롤백과 함께 자동 실행하지 않습니다.

부모 `main.py`·`poc10_proxy.py`를 변경한 경우에만 부모 서비스의 검사·재시작이 추가로 필요합니다. HOME 내부 문서만 바꾸는 작업에는 운영 재배포가 필요하지 않습니다.

## 9. 백업·공유·복구

### 9.1 DB와 파일은 별도 구성요소

[backup_database.py](scripts/backup_database.py)는 운영 DB의 동일 시점 스냅샷으로 custom-format `home.dump`를 만들고, 임시 DB에 복원해 행 수·확장·현재 판본 건수를 대조합니다. `manifest.json`, `SHA256SUMS.txt`, 복원 안내, 앱 README 사본 등을 함께 만듭니다.

```bash
# 저장소 루트. DB 덤프·검증용 임시 DB 생성·파일 기록을 수행하는 작업
sudo python3 PoC/10-home/scripts/backup_database.py
```

DB 덤프에는 원천 판본·검토 사유·감사 이력이 포함되지만 **앱 소스, DB 외부 원문·첨부 실물, 환경 비밀값은 포함되지 않습니다.** 자료 재현에는 필요한 `data/raw`와 코드 버전을 별도로 준비합니다. 패키지 생성은 기존 파일 삭제 정책과 별개입니다. 보관기간·RPO·RTO는 운영 주체가 정하고 현재 도구가 자동 충족한다고 가정하지 않습니다.

세 에이전트의 인수인계에는 **`data/runtime/ai-collection.sqlite3`도 별도 백업**해야 합니다. 역할 설정·실행 결과·규칙·원문 시험·판단 이력·미전송 정산은 이 SQLite에 있으며 PostgreSQL 덤프만으로 복구되지 않습니다. 실행 중 파일의 단순 복사 대신 SQLite의 일관된 백업 절차를 사용합니다. PoC7·10·11 중앙 예산 원장은 별도로 보존·대조하여 오래된 백업으로 사용량과 잔여량을 되돌리지 않습니다. [공통 예산 백업·전환 계약](docs/SHARED_AI_BUDGET.md)을 함께 전달합니다.

### 9.2 복구 절차

1. 패키지 manifest의 생성시각·스키마·코드·체크섬·포함/제외 범위를 읽습니다.
2. 체크섬을 검증합니다.
3. PostgreSQL16과 해당 PostGIS 확장이 있는 **별도 빈 DB**를 준비합니다.
4. `pg_restore --no-owner --no-privileges --exit-on-error`로 복원합니다.
5. 테이블별 행 수·확장·현재 kind별 건수를 manifest와 대조합니다.
6. 필요한 원문·AI SQLite를 일관된 시점으로 복구하고, 격리 앱의 자동 예약 및 수집/AI worker를 실행하지 않은 상태로 검증합니다.
7. 정책·사업·승인·목표/실적·신규 자료 검토·보고서·원문 파일을 확인합니다.
8. 복구 책임자가 검증 결과와 전환 범위를 확인한 뒤 운영 연결을 전환합니다.

패키지 폴더에서 사용하는 예시입니다. `home-import-db`와 빈 `home_import`가 준비된 환경에만 적용합니다.

```bash
sha256sum -c SHA256SUMS.txt
docker exec -i home-import-db pg_restore -U home -d home_import \
  --no-owner --no-privileges --exit-on-error < home.dump
```

에이전트 설정·실행은 `POST /admin/ai-agents/{role}/settings`와 `/runs`이며 관리 인증과 설정 판본 검사를 따릅니다. 알고리즘 시험·판단 및 단계 실적 승인은 별도 관리 API입니다. 정확한 요청 스키마는 [algorithm_review_api.py](backend/algorithm_review_api.py), [stage_reconciliation_api.py](backend/stage_reconciliation_api.py)를 확인하세요.

관리 저장 예: `POST /admin/publication-reviews/{document_id}`.

| 필드 | 계약 |
| --- | --- |
| `source_revision_no`, `review_revision_no` | 읽은 원문·검토 판본. 오래된 값이면409 충돌 |

유효성 오류422, 원문/검토 변경409, 인증실패401/403을 구분합니다. 승인 저장은 `publication_review`와 감사 이력을 만들고 필요한 자료참조 bridge를 생성합니다. 실적을 만들지 않는 `facts=[]`·`units=null` 계약을 보존합니다. CSV의 열 이름은 외부 분석과 연결될 수 있으므로 변경 시 문서·검사·기존 소비자를 함께 확인합니다.

11월 3일 외부 의견 278개 대상을 대조하여 원문 26건을 보충하고 업무 판단 19건(자료 연결 1, 등록 대기 1, 제외 8, 보류 9)을 처리했습니다. **실적 추가는 0호**이며 사업·목표·실적 원장 보존을 확인했습니다. [처리 근거](docs/evidence/HOLD_REVIEW_20261103/README.md).

이후 정책 추진현황 점검에서 캐시를 거치지 않은 원장 계산과 화면의 여섯 단계 값이 일치했습니다. 단계 후보 138건(사업화 44, 인허가 68, 착공 8, 준공 1, 공급 17)은 모두 보류였고 자동 반영 조건 충족은 0건이었습니다. 137건은 **제안에 연결된 검증용 본문**이 없고 123건은 사업 동일성 확인이 남아 있었습니다. 보류 건수는 신규 사업 수나 누락 호수가 아닙니다.

현재 원장상 10월 22일까지의 공급 누적 35,410호는 10월 30일까지 37,772호로 증가했습니다. 이 중 검토 연결 1,424호를 포함하므로 전체가 최종 확정량이라는 뜻은 아닙니다. 인허가 99,462호와 착공 81,131호는 유지됐습니다. 이는 **현재 원장의 사건일 기준 재구성**이며 과거 접속일별 화면 스냅샷 비교는 아닙니다. [정책 반영 점검 JSON](docs/evidence/POLICY_REVIEW_REFLECTION_20261103/audit.json).

검증 기록은 범위별로 구분합니다. 11월 3일 보류 검토·알고리즘·수집 관련 회귀검사 147개, 이후 단계 승인·정책 집계·캐시 점검 72개가 통과했습니다. 중복되는 테스트가 있으므로 합산하지 않습니다. **기능이 구현된 것과 모든 데이터 검토가 끝난 것은 다릅니다.** 현재 보완 과제는 원문·정확한 사업 식별·물량 범위를 확보하여 보류 후보를 실적 확정까지 연결하는 것입니다.

### 11.2 남은 데이터·기능 범위

- 아래 미해결 수치는 10월 29일 점검 기록이며 현재 잔여량은 해당 화면에서 다시 확인합니다.
- 토지이음 상세660건·본문 복구493건·첨부 텍스트63개·OCR 확인4건이 점검 당시 남았습니다. 서로 겹칠 수 있으므로 합산하지 않습니다.

- iH 재고 API504, GH 보도자료 직접 수집 접근 오류, 일부 과거 입주 이력·정비사업 상세 탐색이 남아 있습니다. 기존 GH 모집공고 경로와 구분합니다.
- 기존주택 잔여모집·다단지 모공고·임시 주거지원은 자산별 식별과 중복 검토가 필요합니다.
- 모델 API를 사용하는 세 에이전트는 구현돼 있습니다. 별도 외부 모델 검토서의 자동 재수입·승인, 기관 결재선·정책참고 전용 연결 구조는 현재 범위 밖입니다.
- 보고서 입력에 포함되지 않은 전체 후보군·미확보 목록은 ‘없음’이 아니라 미연결 범위입니다.
- 운영 상태는 새 게시물·수집·검토에 따라 변합니다. 수치 갱신 시 기준시각·동일 분모를 함께 갱신합니다.

### 12.2 공통 편집 기준

1. 문서에 원천 README 기준일·소스 버전·작성자·대상 독자·대상 환경·검증일을 표기합니다.
2. 현재 기능, 과거 적용 사례, 미구현/후속 업무를 분리합니다. 과거 숫자를 최신값으로 인용하지 않습니다.
3. 실제 버튼·상태명과 화면 경로를 사용합니다. 일반 사용자 안내에 내부 구현을 불필요하게 노출하지 않습니다.
4. AI를 활용한 패턴 개발, 모델을 활용한 담당자 업무, 동료 외부 검증을 구분합니다. 건별 모델 호출 비용이 없다는 설명을 전체 운영비용이 없다는 뜻으로 바꾸지 않습니다. 검토 승인을 사업등록/실적으로 바꾸어 서술하지 않습니다.
5. 데이터셋 검증에는 입력 버전·분모·검토 범위·미확인 항목을 남깁니다. 확인되지 않은 ‘전수 검증·공식 인증·100% 정확’ 표현을 사용하지 않습니다.
6. 명령마다 실행 위치와 읽기/쓰기 효과를 밝히고 비밀값은 넣지 않습니다. 개발·복구는 격리 환경을 전제로 합니다.
7. README의 상대 링크는 저장소 구조를 기준으로 합니다. 독립 배포 때 필요한 문서·이미지를 함께 묶거나 배포 가능한 URL로 바꿉니다. 비공개 백업 경로를 공개 다운로드 링크처럼 배포하지 않습니다.
8. 스크린샷·CSV·보고서 예시에 개인정보·인증값이 없는지 확인하고 업무 이력이 포함된 파일의 공유 대상을 정합니다.
9. 문서 변경과 기능 배포는 구분합니다. 매뉴얼 갱신만으로 코드·DB·과거 패키지를 갱신했다고 기록하지 않습니다.
