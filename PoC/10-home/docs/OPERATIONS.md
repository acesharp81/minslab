# HOME 운영

현재 배포는 Docker CLI 방식입니다. 전용 컨테이너 `poc10-home-api`, `poc10-home-db`, network `poc10-home`, DB volume `poc10-home-pgdata`, loopback API `18100`을 사용합니다.

## 재배포와 점검

저장소 루트에서 실행합니다.

```bash
sudo python3 PoC/10-home/scripts/deploy.py
curl --fail http://127.0.0.1:18100/health
sudo docker logs --tail 50 poc10-home-api
```

실행기는 `.env`를 서버 전용 `data/runtime/*.env`에 권한 `600`으로 전달하고 Alembic migration 후 API를 시작합니다. 이전 API 컨테이너는 중지 후 timestamp가 붙은 backup 이름으로 보존합니다. DB volume과 `data/raw`는 유지합니다.

부모 `main.py`/`poc10_proxy.py` 변경 시 회귀 검사 후 `sudo systemctl restart myservice`가 필요합니다. HOME 내부 코드는 HOME API만 재배포합니다. Compose 방식과 현재 CLI 방식은 컨테이너 관리자를 혼용하지 않습니다.

## 수집

최신 정책·사업 원천 7개와 과거 정책·공사 원천 2개를 시작 시와 24시간마다 자동 수집합니다. MinsLab 관리자 로그인 → HOME → 수집 원천 → `지금 수집`으로 요청할 수 있습니다. API 테스트 표본 3개 원천은 `manual_only=True`로 제외하며, HOME → API 테스트 데이터 → `확대 표본 수집`으로 실행합니다.

```bash
sudo docker exec poc10-home-api python -m scripts.collect
sudo docker exec poc10-home-api python -m scripts.collect --source lh_sale
sudo docker exec poc10-home-api python -m scripts.collect --samples
sudo docker exec poc10-home-api python -m scripts.collect --history
sudo docker exec poc10-home-api python -m scripts.collect --source vworld_district
sudo docker exec poc10-home-api python -m scripts.collect --source lh_block_location
```

`lh_block_location`은 LH 공개 지도의 블록 라벨점을 키 없이 자동 수집합니다. 정확한 블록 경계나 건물 형상이 아니며 서울·경기 현재 사업 블록 98개 중 66개에 완전 일치로 연결됐습니다. 자세한 기준과 미확보 범위는 [MAPS_UI_PLAN.md](MAPS_UI_PLAN.md#14-1차-구현검증-2026-10-03)에 기록합니다.

`vworld_district`는 기존 VWorld 키로 공식 공동주택용지 도형을 수집하는 수동 지도 원천입니다. 기본 자동수집과 `--samples`에서 제외합니다. 지구 대표 위치와 개별 블록 연결 상태를 구분하며 수집·화면 검증은 [MAP_INTERFACE.md](MAP_INTERFACE.md)에 기록합니다. 배경지도는 서버의 고정 VWorld WMTS 요청을 PNG로 검증·캐시하고 브라우저에는 HOME 타일 경로만 제공합니다.

블록 확대 시 실제 3D 주변 건물은 `GET /poc/home/api/map/buildings?block_id=...`에서 기존 `POC10_VWORLD_API_KEY`로 VWorld GIS건물통합정보를 조회합니다. 원문은 `data/raw/vworld_building_context`에 키를 제거한 SHA-256 이름으로 보관하고 결과는 최근 8개 블록까지 메모리에 6시간 캐시합니다. 조회 반경은 최대 1km이며 최대 5,000개 도형까지 페이지 수집합니다. 더 조밀한 곳에서는 750·500·300m로 범위를 줄입니다. 공식 높이를 우선 사용하고, 높이가 없으면 공식 층수×3m를 추정 높이로, 둘 다 없으면 지도 표현용 7.5m로 세웁니다. 높이 근거별 수량은 화면에 구분해 표시합니다. 건물과 정책 사업·블록의 관계는 미연계이므로 건물 수·높이를 공급 실적으로 집계하지 않습니다. 공급현황은 첫 화면부터 상시 3D 지도를 사용합니다. 상세 기준은 [MAPS_UI_PLAN.md](MAPS_UI_PLAN.md#15-접이식-우측-패널실제-주변-건물-3d-2026-10-04)에 기록합니다.

지도 `자료 연도`로 2018년부터 과거 발표·인허가·보고 상태를 조회합니다. 상단 `수집 조회일`은 해당 날짜까지 확보한 자료의 시점이므로 최초 수집일보다 과거로 바꾸지 않습니다. 과거 보고서도 VWorld 지구 수집 대상에 포함되며 현재 확보 경계를 참고 위치로 표시합니다. 정책/프로그램/지역 물량과 모집/입주/준공 누적 예정량 조회는 [SUPPLY_MAP.md](SUPPLY_MAP.md)를 따릅니다.

프로세스 잠금과 PostgreSQL advisory lock으로 중복 수집을 막습니다. 재시작 시 중단 배치는 `INTERRUPTED`로 기록합니다. 실패 시 마지막 정상 데이터를 조회할 수 있으며 원천별 실패 상태를 표시합니다.

누적 수집 기본값: `POC10_NOTICE_START_DATE` 미설정 시 정책 기원 연도 1월 1일(현재 2018-01-01), `POC10_PERMIT_DISTRICT_LIMIT=0`으로 법정동별 전체 페이지, `POC10_GEOCODE_PER_KIND_REGION=10`입니다. 인허가는 기존 6개 법정동·안전 상한 10,000건, 좌표는 한 배치 최대 40개입니다. 설정을 바꾼 뒤 HOME을 재배포합니다. 청약은 연도·지역별 전체 페이지를 검증하며 과거 원천은 기준일별 별도 레코드로 보존합니다. [소급 수집 결과](HISTORICAL_COLLECTION.md).

## 사업 연도별 목표

관리자 로그인 → 공급 현황 → 사업의 `목표 관리`에서 오늘 기준의 당해연도·향후 10년을 편집합니다. 연도별 계획/인허가/착공/공급/준공/입주 목표, 선택적 목표 호수, 필수 근거·메모, 선택적 HTTPS URL을 저장합니다. 미등록 선택은 해당 관리자 목표를 해제하며 원천 예정은 보존합니다. 과거 기준일은 읽기 전용입니다.

`GET /poc/home/api/roadmap?horizon=10`, `/roadmap/export.csv`, `/projects/{id}/targets`로 조회합니다. 관리자 `POST /api/admin/targets/{id}`는 부모 세션·동일 출처·내부 서명을 확인하고 `revision_no` 충돌 시 409를 반환합니다. 목표는 별도 `goal` revision과 `TARGETS_UPDATED` 감사이력으로 보관합니다. 목표 감사이력을 과거 정책 매핑에 적용하지 않습니다. 목표 저장은 실제 달성·공식 공급총량에 영향을 주지 않습니다.

## 공개·관리 경계

공개 경로는 GET/HEAD 조회만 허용합니다. 관리자 수집·매핑 변경은 부모 MinsLab 세션과 동일 출처 Origin 검증을 거친 뒤 서버가 서명한 짧은 유효기간의 내부 요청으로 전달합니다. 브라우저가 보낸 내부 서명·다른 PoC 쿠키는 HOME으로 전달하지 않습니다. API는 loopback에만 공개합니다.

`.env`, raw 디렉터리, DB와 운영 로그는 정적 경로로 제공하지 않습니다. 인증 API는 고정된 공식 HTTPS endpoint를 호출하며 credential query를 manifest에서 제거하고, 응답에 키가 포함돼도 제거한 bytes를 저장·해시합니다. 인증 요청 redirect는 같은 HTTPS 호스트만 허용합니다. API 표본은 정책 사업과 별도로 조회·다운로드합니다.

## 백업과 복구

```bash
mkdir -p PoC/10-home/backups
sudo docker exec poc10-home-db pg_dump -U home -d home -Fc > PoC/10-home/backups/home.dump
tar -czf PoC/10-home/backups/raw.tar.gz -C PoC/10-home/data raw
chmod 600 PoC/10-home/backups/home.dump PoC/10-home/backups/raw.tar.gz
```

DB와 raw를 함께 백업합니다. `.env`는 접근 제한된 별도 보관소에 보관합니다. 복구는 별도 DB·컨테이너에서 `pg_restore` 후 snapshot hash·revision·감사이력·health를 확인하고 전환합니다. 격리 복구 훈련은 후속 운영 검증 항목입니다.

## 기준일의 의미

화면 기본 기준일은 오늘(KST)이며 최초 수집일 이후를 선택합니다. 자료를 늦게 수집했다고 과거 시점에 알고 있던 정보로 소급 생성하지 않습니다. 과거 조회는 해당 날짜 종료 전 수집된 revision과 매핑을 재현합니다. 원천 기준일과 수집일을 구분하며 수집 원천 메뉴는 현재 운영 상태를 보여줍니다.

정책 흐름·과거 자료의 `자료연도`는 별도 필터로 2018년부터 조회합니다. 오늘 확보한 과거 문서는 현재 저장 지식 안에서 해당 원천 연도로 분류하며 실제 `recorded_at`을 앞당기지 않습니다.

선택 블록 주변 지하철역·초중고교·병원은 `GET /poc/home/api/map/infrastructure?block_id=...`에서 기존 `POC10_VWORLD_API_KEY`로 VWorld 장소 검색 API 2.0을 조회합니다. 반경 3.5km, 블록 라벨점 기준 직선거리이며 24시간 메모리 캐시합니다. 원천 응답은 키를 제거한 SHA-256 이름으로 `data/raw/vworld_infrastructure`에 보관합니다. 지도는 시설 분류와 좌표가 확인된 항목만 표시하며, 학교는 가까운 25곳, 병원 12곳, 지하철역 10곳까지 표시합니다. 시설이 안 보이면 먼저 이 API의 `status`, `counts`, `items`와 VWorld 키 상태를 확인하세요.

## 단계별 연계 오류·조치 기록 (2026-10-12)

데이터 연계 규칙 또는 수집 오류를 수정할 때 원인·실제 조치·영향 범위·남은 확인사항을 `collection_repair` 판본으로 함께 저장한다. 기존 사례를 수정하면 동일 key로 새 판본을 추가하고 과거 설명은 보존한다. 해결된 기술 오류와 미확정 사업 동일성·정책 귀속을 별도로 적는다. 과거 조치 소급 기록일과 원천 사건일을 혼동하지 않는다.

- `python -m scripts.record_collection_repairs`: 검증된 과거 10개 조치 기록. 동일 내용은 중복 판본을 만들지 않는다.
- 후속 조치: 검토한 JSON 배열 파일에 `key, repair_type, title, cause, action, remaining, stages, status, base_date, project_ids, source_ids, impact, report_url`을 작성하고 `python -m scripts.record_collection_repairs --file /path/to/records.json` 실행. 사업 지정은 `project_ids`, 공통 규칙은 `source_ids`로 범위를 제한한다. `report_url`은 기존 공개 점검 보고서 경로를 사용한다.
- 사업별 수집·연계의 다이어그램 상자 및 사업×단계 상세에서 관련 진단 기록과 연결별 최근 3개 실제 변경 기록을 확인한다. 전체 과거 Audit/Revision은 DB에 유지된다. 수집 실패→복구 전환도 별도 조치 판본을 자동 기록한다. 반복 실패는 Batch 이력에 계속 남고 동일 설명 판본은 늘리지 않는다.
- 조회는 재매칭을 수행하지 않는다. 표시 중인 화면은 경량 버전 API로 20초 간격 DB 변경을 확인한다. 숨긴 화면은 중지하고, 입력 중에는 갱신을 보류한다. 저장 또는 상세 닫기 후 다시 반영한다.
- 검증: `tests/test_collection_repairs.py`, `scripts/check-collection-repairs.cjs`. 브라우저 검증은 변경 버전 응답을 가로채며 담당자 수정 내용을 실제 저장하지 않는다.


오류·조치 이력은 오류 유형별로 조회한다. 전체 건수를 누르면 유형별 건수, 유형 건수를 누르면 그 유형의 원인·조치·영향 사업·남은 확인사항이 펼쳐진다. 유형은 `IDENTITY_LINK`(사업 식별·원천 연결), `SCOPE_QUANTITY`(전체/일부 물량 범위), `COLLECTION_GAP`(수집 누락), `STAGE_DATE`(단계/일정), `AVAILABILITY_STATE`(미확보 상태), `COLLECTION_FAILURE`(수집 실패/복구), `OTHER`이다. 기존 이력 유형만 보완할 때는 `python -m scripts.record_collection_repairs --classify-existing`로 이전 내용과 담당자 상태를 보존한 분류 판본을 추가한다. 다시 실행해도 분류된 기록은 수정하지 않는다.


품질 문제를 확인하면 같은 오류 기록에 `related_keys`(PNU·블록 등 연관 필드)와 `quality_checks`를 추가한다. 품질 점검은 `kind`(유효성/정합성/범위/처리), `layer`(원천값/원천의 한계/수집/연결/표시), `result`(완료/미해결/일부 보완/추가 확인/원천으로 적용 불가), `rule`, `evidence`, `repair`, `completion_criteria`, `checked_at`, `checked_scope`를 필수로 기록한다. `metrics`에는 숫자의 단위와 분모를 명시하고, `evidence_refs`에는 보관한 점검 스냅샷·해시를 남긴다. 원천에 0000-0000 블록 주소만 있는 상황을 원천 데이터가 잘못됐다고 단정하지 않고 제공 형식의 한계로 기록한다. 조회 범위와 원래 점검 범위가 다르면 점검 숫자를 재해석하지 않는다.

`python -m scripts.record_quality_details --pnu-audit /app/data/audits/PNU_DIAGNOSIS_20261012.json`은 검증된 기존 12개 이력에 품질 점검을 추가하는 일회성 보완이다. 담당자의 상태·조치 설명은 그대로 두고 품질 메타데이터 판본만 추가하며 동일 내용을 다시 실행해도 중복 판본이 생기지 않는다. 추가 조치를 할 때는 `patch_details`로 기존 기록의 해당 점검 내용만 변경하고, 최신 판정과 확인일을 갱신한다. 다이어그램 필드를 선택하면 그 필드에 해당하는 점검 이력이 표시된다. `GET /poc/home/api/project-collection/quality-guide.json`과 화면의 내려받기 링크에서 조회 범위에 맞는 품질·정비 기록을 받아 후속 가이드 작성에 사용한다. 과거 점검은 Revision에 보존된다.

### 필지 PNU 원천 정비 (2026-10-13)

`backend/parcel_identity.py`는 건축HUB의 시군구·법정동·대지구분·본번·부번을 검증합니다. 대지구분 0/1만 PNU 일반/산 1/2로 변환하고, 블록(2), 본번 0000, 공란 부번, 형식 오류는 생성 보류합니다. 코드 마스터 대조와 PNU 형식 통과는 사업 귀속·현행 지적 경계의 확정을 의미하지 않습니다.

`python -m scripts.reconcile_parcels`는 선택된 인허가 판본의 보관 원문에서 파서가 누락한 필드를 읽기 전용으로 진단합니다. `--apply`는 원문 파일명·SHA256·허가 판본을 `parcel_evidence`, 사업별 허가 PK 기반 다필지 후보를 `project_parcel` 판본으로 저장합니다. 기존 인허가 판본·담당자 선택을 덮어쓰지 않습니다. 조회 때 재매칭하지 않으며, 연결 해제된 허가의 후보는 다이어그램에서 제외합니다.

- 실제량은 정책기간 내 연결 사업의 착공 사건을 중복 제거하여 집계하고 검토 중 연결 포함을 명시한다. 정책 잔여에 단계 미확인을 포함하며, 입주 시작 사업 물량과 실제 입주 세대수를 구분한다.
- 검증: HOME 백엔드 전체 테스트 및 정책정보/프로그램 매핑 회귀, 부모 프록시 인증·동일 출처 검사. `scripts/check-policy-information.cjs`로 실제 HTTPS의 비로그인 차단, 관리자 화면, 근거/수정, 프로그램 선택, 모바일 폭을 확인했다. 브라우저 저장은 요청을 가로채 검증하여 운영 데이터에 시험 기록을 남기지 않았다.
- 기존 실행분석 테스트 2건이 오늘 저장한 기록을 2026-10-13 기준으로 조회하여 날짜 경과 후 실패하던 문제는 저장일과 조회일을 맞추도록 수정했다.


### 2026-10-14 정책정보 화면 밀도·직접 입력·원문 인용 개선

- 정책 화면과 동일한 파란 제목, 흰 카드, 얇은 입력 테두리를 사용한다. 상단 기본정보, 좌측 지역/연간 목표, 우측 프로그램/진행현황/조언, 하단 고정 저장 영역으로 재구성했다. 1440×900 및 1366×768에서 화면 본문 외부 스크롤 없이 전체 구성을 확인한다. 작은 화면에서는 본문만 스크롤하며 저장 영역을 유지한다.
- 수정 팝업을 없애고 입력칸과 체크박스를 직접 편집한다. 지역 변경 시 다른 지역의 입력 초안을 보존한다. 변경 표시와 항목별 원천값 복원, 기존 버전 충돌 검증 및 관리자 전용 접근은 유지한다.
- 근거 툴팁은 원문 문구/값 + 문서명·쪽수이며 최대 200자, 초과 시 ...로 줄인다. 키보드 포커스로도 조회 가능하고 클릭하면 전체 근거를 연다. 실제 운영 원문 PDF SHA-256 `6a72c5e14edcc3705043dfd58ac7aad2b0167fb343270d47ecd80522eeb0c5e6`에서 추진목표 문구를 확인했다(문서 4쪽 / PDF 7쪽). 목표표는 문서 43쪽 / PDF 46쪽이다.
- `policy_field_evidence.py`가 기존 확인 원문의 인용 메타데이터를 제공한다. 향후 수집은 `parse_original_plan`에서 문구·실제 페이지·원문 해시를 추출해 `field_evidence`로 보관한다. 화면을 열 때 PDF를 다시 파싱하거나 검색 API를 호출하지 않는다. 확인되지 않은 문서에는 쪽수를 생성하지 않는다. 목표표의 호수 환산 설명은 직접 인용과 구분한다.

### 2026-10-14 프로그램 관리 원문 보강

배포 후 `docker exec poc10-home-api python scripts/supplement-policy-programs.py`로 검토하고 `--apply`로 원문 보강한다. 원천 수정은 이력형 revision이며 담당자 program_profile 값은 덮어쓰지 않는다. 보강 기록은 사업별 수집·연계 오류 조치 이력(COLLECTION_GAP)에 남는다. 신규 프로그램14개·기존3개 근거, 신규 명시 사업3개, 지구별 분양계획20개와 기존 임대재건축5개 입주연도가 대상이다. 같은 명칭이어도 범위가 다른 기존 수집유형을 전체 교체하지 않는다.

프로그램 관리방식 기본값·사례·추가 자료 목록을 변경한 뒤에도 `python scripts/supplement-policy-programs.py --apply`로 원천 프로필만 갱신한다. `program_profile` 사용자 입력은 덮어쓰지 않는다. 프로그램 계획 대조는 `program_management.assessment`에서 집계하며 공급·입주·착공의 단계/기간/단위와 미확보를 구분한다. 합산 목표는 저장 시 최신 연결 사업으로 재검증하며 채택 근거를 목표 override의 `calculation`에 보존한다.

중복 프로그램 정비는 `python scripts/reconcile-program-identities.py`로 검토하고 `--apply`로 저장한다. 확인된2개 동일 프로그램 별칭만 대상으로 하며 다른 정책·프로그램 사용자 입력이 있는 경우 보류한다. 대표 프로그램 연결과 과거 이력·원천 사업 수를 전후 비교하고 중복 프로그램 재생성이 방지되는지 확인한다.

### 사업정보 편집 운영 (2026-10-14)

- `project_profile/manual_project`: 기본정보 수정값, 수집 근거 승인 해시 및 변경자·사유. 원천 project Revision은 유지한다.
