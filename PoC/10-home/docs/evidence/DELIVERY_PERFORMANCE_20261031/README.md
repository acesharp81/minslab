# 추진현황 로딩 점검 및 개선 · 2026-10-31

## 확인한 원인

추진현황은 DB에 저장된 원장을 조회한다. 화면 진입 시 외부 자료를 다시 수집하는 구조는 아니지만, 저장된 원장으로부터 그래프·지도·비교표를 조립하는 계산과 JSON 직렬화가 발생한다.

운영 DB 읽기 전용 프로파일에서 기존 첫 계산은 4.166초, SQL 35회 합계 0.408초였다. SQL 외 원장 조립·지도 단순화·비교표 생성이 지연의 대부분이었다. kind/recorded_at, 현재 판본·entity, source 관련 인덱스가 설치되어 있었다. 이번 측정에서 인덱스 추가가 주된 해결책이라는 근거는 없어 스키마를 변경하지 않았다.

정책 요약과 사업 연결 목록은 수집 배치 종료 시각에도 캐시가 무효화되었다. 실제 데이터가 그대로인 재수집도 두 응답을 다시 계산하게 했다. 확인 중 lh_completion_plan 배치 완료가 있었으며, 중간 반복 측정에서 정책 요약 1.53초·연결 목록 1.42초가 소요되었다.

## 적용 내용

- 화면 조회에 사용하지 않는 336개월의 중간 snapshots 계산 생략. 현재 단계 계산은 유지한다.
- 화면 초기 응답에서 중복된 필드별 감사·복구 이력, 보고서 전용 메타데이터, 월별 공정 상세 배열 제외. 이벤트·일정·수량·상태·근거 설명·원문 참조는 유지한다.
- 전체 원장 API와 보고서 조회는 상세 근거를 계속 제공한다.
- policy_monitor와 mappings 캐시에서 배치 완료 시각 의존성을 제거한다. 관련 판본·사업 연결·담당자 수정은 매 요청 DB 확인을 거쳐 즉시 반영한다. 수집현황 캐시는 기존 배치 상태 의존성을 유지한다.
- 운영 파일에서 빠져 있던 AI 후보 탐색/분석 이력의 불필요한 캐시 무효화 방지 코드도 검증 후 반영했다.
- 운영 API에 관련 backend 파일 4개만 적용했다. DB 원장·목표·실적과 타 서비스 설정은 변경하지 않았다.

## 측정 및 검증

| 항목 | 수정 전 | 수정 후 |
|---|---:|---:|
| 화면 API JSON 실제 바이트 | 5,726,713 | 3,645,880 |
| gzip 응답 바이트 | 650,167 | 416,509 |
| 첫 계산 cProfile 시간 | 4.166초 | 3.606초 |
| SQL 실행 합계 | 0.408초 | 0.428초 |
| SQL 횟수 | 35 | 35 |

응답 크기는 약 36.3%, 압축 전송량은 약 35.9% 감소했다. 프로파일 시간에는 계측 오버헤드가 포함된다.

운영 응답에서 제외하기로 한 필드 외 나머지 값 전체를 수정 전 응답과 대조하여 동일함을 확인했다. 보고서 API에는 report_metadata 및 field_provenance가 남아 있음을 확인했다.

정책 원장·화면 투영·캐시 관련 pytest 41개 통과. 배치만 바뀔 때 캐시 유지, 판본과 담당자 승인 변경 시 즉시 무효화를 별도 검사했다. 운영 Chromium 최종 반복 조회에서 그래프 표시 1.418초, JavaScript 오류 0건. 첫 기준 측정의 반복 조회도 1.390초였으므로, 일반적인 반복 조회 전체가 빨라졌다는 주장보다 응답 축소와 불필요한 재계산 방지가 이번 개선의 효과다.

서버 재시작 직후 캐시가 비어 있는 실제 화면 측정에서는 약 5.48초가 걸렸다. 최초 원장·지도 계산 자체는 여전히 필요하다. 이 시간을 반복 조회 시간과 혼동하지 않아야 한다. 서버 부하·네트워크에 따라 사용자 체감은 달라진다.
