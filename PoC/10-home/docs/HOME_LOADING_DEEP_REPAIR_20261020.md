# HOME 로딩 지연 심층 점검 및 개선

작성일: 2026-10-20. 이전 [로딩 점검](HOME_LOADING_REPAIR_20261020.md)에서 남아 있던 첫 조회 지연과 자동 수집 중 재지연을 추가 조사했다. 이번 작업은 조회 경로와 실행 구성을 개선하며 업무 수량을 맞추기 위한 데이터 보정은 하지 않는다.

최종 메뉴 전환 확인: 2026-10-21 KST. 날짜가 바뀐 뒤의 운영 화면은 10월 21일을 기준일로 사용하므로 10월 20일 원장 보존 대조와 구분한다.

## 확인된 원인

### 1. 화면 하나를 열어도 모든 범위의 비교표를 계산했다

정책 모델은 선택 화면과 관계없이 정책·프로그램·시도·시군구·개별 사업의 연도별·누적 비교표 전체를 만들었다. 기준 응답은 22,768,862바이트였고, 비교표 두 종류만 약 19MB를 차지했다. 정책 화면과 프로그램 화면이 같은 전체 계산을 반복했다.

실제 운영 데이터를 읽기 전용으로 프로파일링하면 약 4,016만 회 함수 호출, 프로파일러를 포함한 18.39초가 관측됐다. 반복 행 복사에 약 6.84초, 전체 대시보드에 약 6.10초, 범위별 비교표에 약 3.33초가 소요됐다. 중첩된 측정이므로 시간을 합산하지 않는다. 시도 지도 윤곽 합성에도 약 2초가 소요됐다.

### 2. 같은 화면에서 예전 지도 계산도 중복 요청했다

정책·프로그램 화면은 자체 사업 원장으로 지도를 그리면서 `/policy-geo/metrics`도 요청했다. 이 요청은 별도의 전체 대시보드를 다시 계산했다. 실제 화면에 쓰이는 지도·수량의 출처를 확인한 뒤 해당 두 화면에서 중복 요청을 제거했다.

### 3. 자동 수집과 웹 조회가 하나의 Python 프로세스를 공유했다

정례 수집의 `COLLECT → LINK → SNAPSHOT` 작업이 API 프로세스 안의 스레드에서 실행됐다. 특히 `LINK`의 대규모 연결 계산 중 CPU 사용률이 약 100%에 이르렀고, 웹 요청이 같은 Python 실행 자원과 메모리를 두고 경쟁했다.

중복 계산만 제거한 중간 배포에서도 정책 첫 표시 7.566초 후 프로그램 표시가 16.992초까지 다시 느려졌다. 당시 `lh_notice_detail`의 `LINK` 작업이 실행 중이었다. 사업별 수집연계도 21.893초, 지역 분석도 16.080초로 지연됐다. 반복 조회 캐시만으로 해결됐다고 볼 수 없는 근거다. [분리 전 요청별 기록](analysis/loading_deep_20261020/browser-cold-final.json).

같은 기록의 사업 화면 67.699초는 주요 정보 표시 뒤 주변 시설을 기다리다 종료한 전체 관측 시간이다. 사업 핵심 표시 시간이나 시설 서버 자체의 처리 시간으로 인용하지 않는다. 기록에는 실제 사업 상세 재조회와 위치 조회의 반복 지연이 남아 있다.

### 4. 외부 주변 정보 조회가 다른 위치의 응답도 막았다

시설·건축 문맥 조회에서 하나의 전역 잠금을 외부 통신 동안 유지했다. 한 위치가 지연되면 이미 준비된 다른 위치의 캐시 조회까지 기다릴 수 있었다. 서로 다른 위치는 별도 잠금으로 처리하도록 변경했다.

## 적용한 변경

1. **화면 범위별 비교표**: `/policy-delivery/view`에서 선택한 정책·프로그램과 그 지역 범위만 비교한다. 개별 사업 비교표는 실제 선택할 때 계산한다. 모든 사업의 사건·일정·호수 원장은 유지한다. 전체 보고·내보내기용 기존 API도 유지한다.
2. **반복 연산 절감**: 같은 요청에서 읽은 DB 행은 자체 생성한 메모리 직렬화 결과를 재사용하고, 요청마다 독립적인 객체로 복원한다. 동일 구성원의 대시보드 계산은 한 번만 수행한다. 외부 파일이나 원천의 pickle을 읽지 않는다.
3. **불필요한 재조회 제거**: 수집 상태·무관한 지역 통계 적재로 정책 화면의 계산 결과를 폐기하지 않는다. 업무 원장·담당자 입력·정책 및 프로그램 연결 변경은 계속 감지한다.
4. **지도 윤곽 재사용**: 원본 경계의 내용 지문으로 합성 윤곽을 저장한다. 원본이 바뀌면 새 지문으로 다시 계산한다. 시군구 원본 경계와 사업 좌표는 그대로 사용한다.
5. **수집 실행 분리**: `poc10-home-worker` 컨테이너가 기존 정례 수집·연결·스냅샷 큐를 처리한다. API의 내장 정례 수집 스레드는 끈다. 별도 작업자는 CPU 1코어·메모리 1,536MiB 한도로 실행하며 API 메모리와 분리한다. Docker CLI 배포와 Compose 구성을 함께 수정했다.
6. **수집 재개와 중복 방지 유지**: 기존 원천별 잠금·작업 임대·heartbeat와 재시도 규칙을 사용한다. 별도 작업자에는 단일 리더 잠금과 상태 파일을 둔다. 중단 당시의 진행 작업은 기존 10분 임대가 만료되면 같은 단계부터 재시도하며, 임의로 성공 처리하거나 원장 수량을 만들어 넣지 않는다.
7. **외부 조회 잠금 축소**: 서로 다른 시설·건축 위치의 외부 통신이 준비된 캐시 응답을 막지 않도록 했다. 외부 제공처 자체의 응답 시간은 여전히 영향을 준다.
8. **메뉴 전환 중 응답 누락 보완**: 최종 회귀 점검에서 정책에서 프로그램으로 이동할 때 목록 갱신이 진행 중인 요청의 상태까지 무효화해 정상 응답을 버리는 문제가 드러났다. 완료된 데이터의 지문과 요청 순번을 분리하고, 현재 화면·조회일·선택 범위가 일치하는 응답을 적용하도록 수정했다. 응답을 일부러 지연한 상태에서도 실제 차트와 보고서 범위가 올바른지 검증했다.

정책 화면 JSON은 6,739,135바이트로 기존 대비 약 **70.4% 감소**했다. 데이터 원장을 삭제한 결과가 아니라 사용하지 않는 비교 행렬과 화면 밖 진단값을 보내지 않은 결과다.

## 업무 데이터와 기능 보존 검증

- 관련 테스트 **153개·서브테스트 27개 통과**, JavaScript 4개 파일 구문 검사 통과. 큐의 단계 진행·실패 재시도·경합과 오래된 작업자 처리도 확인했다. [기록](analysis/loading_deep_20261020/tests.json).
- 메뉴 전환 보완 뒤 관련 JavaScript 검사 **25개 통과**. 공개 서버의 데이터 요청을 350ms 늦춰 목록 갱신이 먼저 끝나도록 한 뒤 정책↔프로그램 4회 전환에서 차트 표시와 보고서 범위를 확인했다. 로컬 JS 대체 없이 실제 배포본으로 통과했으며, 이 인위적 지연 시험을 성능 수치로 사용하지 않는다. [경쟁 상태 회귀 검증](analysis/loading_deep_20261020/browser-menu-race-regression.json).
- 실제 DB를 읽어 정책 화면과 **연결 프로그램 22개**의 모든 표시 대상 연도별·누적 비교표를 기존 전체 모델과 대조해 동일함을 확인했다. 사업 사건·계획·현재 수량·집계 문제·지도 수량 대사도 동일하다. [대조 결과](analysis/loading_deep_20261020/equivalence.json).
- 시군구 원본 경계와 사업 좌표·시도 지도 중심점은 동일하다. 합성 후 단순화한 경기 외곽선은 연산 순서 때문에 일부 정점이 달랐고 최대 차이는 0.000753도였다. 기존 단순화 허용치 0.002도 안이며 원본 경계 변경은 아니다. 좌표 파일 전체가 바이트 단위로 같다고 주장하지 않는다.
- 배포 후 운영 API를 다시 대조해 현재 원장·전체 사업 사건·계획·현재 수량과 표시 비교표가 동일함을 확인했다. 추정을 포함하는 정책 관리값은 착공 79,884호·공급 58,541호·연말 착공 계획 92,574호·연말 공급 계획 70,005호를 유지했다. 이 값을 모두 원천 확정 실적이라고 재해석하지 않는다. 자동 수집이 계속되는 운영 DB 자체가 영구히 변하지 않는다는 뜻도 아니다. [운영 API 대조](analysis/loading_deep_20261020/api-final.json).
- 공개 사이트에서 프로그램 3개를 전환하고 정책 화면·지도 범위·보고서 데이터 구성을 확인했다. JS 오류와 API 실패는 0건이고, 중복 `/policy-geo/metrics` 및 전체 `/policy-delivery` 요청도 없었다. [공개 사이트 기능 검증](analysis/loading_deep_20261020/browser-interactions.json).
- 공개 서버의 JavaScript 4개 파일이 작업 공간의 수정본과 동일하며 `no-cache`로 제공됨을 확인했다. 이미 열려 있는 탭은 한 번 새로고침해야 새 코드가 적용된다. [정적 파일 검증](analysis/loading_deep_20261020/public-assets.json).

## 최종 운영 측정

측정은 동일 호스트 Chromium에서 주요 콘텐츠 표시까지의 단일 표본이며, 외부 지도 타일·주변 시설 완료 및 사용자 인터넷 환경과 구별한다. 여러 사용자가 보는 운영 API의 캐시는 다른 방문으로 준비될 수 있으므로, 최초 계산은 같은 배포 이미지·운영 DB를 조회하는 별도 임시 API에서 확인했다. 이 API는 내장 수집과 시작 시 업무 재조정을 실행하지 않았으며, 화면 비교표·매핑·대시보드 캐시는 비어 있었다. 정례 수집은 운영 작업자가 계속 담당했다.

아래 최초 표본은 **공유 덤프의 격리 복원·인덱스 생성 부하가 함께 있는 상태**다. 운영 DB 한도를 임시로 높이기 전에 측정했으며, 일반 운영의 지연 상한 또는 지속 부하 P95를 보장하지 않는다. 정책 첫 요청의 `X-Home-Cache: MISS`와 실제 계산 4.035초를 확인했다. 프로그램 첫 조회는 앞선 정책 조회에서 만든 공통 입력을 재사용한다. 지역 통계는 앞선 화면에서 일부 준비됐으므로 모든 메뉴를 완전히 독립적인 콜드 조회라고 부르지 않는다.

| 화면 | 별도 API 첫 방문 · 복원 부하 동시 |
| --- | ---: |
| 정책 추진현황 | 7.389초 |
| 프로그램 추진현황 | 4.316초 |
| 사업 추진현황 | 5.252초 |
| 사업별 수집연계 | 7.267초 |

사업 주요 정보는 5.252초, 주변 시설 목록은 6.630초에 표시됐다. 5개 화면 모두 JS 오류·요청 실패·테스트 타임아웃이 없었다. [최초 방문별 요청 기록](analysis/loading_deep_20261020/browser-isolated-cold-under-backup.json). 임시 API는 측정 후 제거했다.

운영 API에서도 복원 부하 중 5개 화면이 정상 표시됐다. 이 표본의 정책 비교표는 이미 준비된 응답이었으므로 최초 계산 증거로 사용하지 않는다. [운영 API · 복원 부하 중](analysis/loading_deep_20261020/browser-backup-load.json).

실제 정례 `lh_notice` 작업이 별도 작업자에서 `COLLECT → LINK → SNAPSHOT`을 거쳐 23:32:12 KST에 완료됐다. API의 내장 자동 수집 설정은 `false`, 별도 작업자의 자동 수집 설정은 `true`다. 두 컨테이너 모두 healthy이며, 작업자의 단일 리더 잠금과 스케줄러·최신·과거 자료 처리 경로가 실행되는 것을 확인했다. [배포 구성](analysis/loading_deep_20261020/deployment.json).

이후 `building_general_permit`의 실제 수집이 진행되는 동안 정책 응답은 HTTP 200·캐시 적중·0.291초였다. 당시 덤프 복원을 병행하며 DB 메모리 한도를 임시 8GiB로 높인 상태였다. 이는 동시 수집 상태의 한 표본이며 작업자 CPU를 포화시킨 부하 시험 결과는 아니다. [수집 중 응답 확인](analysis/loading_deep_20261020/under-active-collection.json).

복원 검증 종료 및 DB 메모리 한도 2GiB 원복 후, 최종 수정본으로 공개 주소에 접속해 **같은 탭에서 메뉴를 이동**했다. 아래는 재배포 직후 방문과 이후 새 세션에서 재방문한 실제 표본이다. 정책 행은 첫 정책 화면을 연 후 다른 메뉴를 거쳐 정책으로 복귀한 시간이다.
