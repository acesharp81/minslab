# 개별 사업 추진현황 분석보고서 적용 (2026-10-23)

사용자 첨부 「개별 주택공급사업 추진현황 분석보고서 자동생성 기능 구현」을 사업 화면의 **추진현황 보고서 만들기**에 적용했다. 정책·프로그램 보고서의 기존 진입 경로는 유지했다.

## 보고서 구성과 이용

- 사업명·ID 검색, 보고 기준일, 최초 유효 관리계획 / 이전 보고시점 / 현재 채택 관리계획, 분석 범위, 요약·상세, 분석 관점, 근거 표시를 선택한다.
- 표지·핵심 요약 다음에 기존 **6단계 진행 카드**와 **120개월 목표·측정 시계열**을 유지한다. 목표 옅은 파랑, 측정 분홍, 추정은 빈 원 표시를 재사용했다.
- 본문은 사업 개요, 단계 현황, 일정 비교, 물량·변경, 행정절차, 건설·공급·준공·입주, 위험, 향후 조치, 종합평가의 9개 장이다.
- 본문은 인쇄/PDF, HTML, CSV, 산출근거 JSON으로 출력한다. 실제 샘플은 표지·그래프를 포함해 A4 6~8쪽 (표지·그래프 각 1쪽, 분석 본문 4~6쪽)이다.
- **붙임 4종은 생성·다운로드 버튼을 누를 때만 조립한다.** 원천·사건, 블록·유형 명세, 일정·물량 변경, 검증 결과를 별도 HTML/CSV/JSON으로 받는다. HTML은 인쇄/PDF 저장이 가능하다.
- 본문 생성 시 입력을 복제하고 SHA-256을 기록한다. 붙임 생성 시 재조회하지 않으며 본문과 같은 입력 해시를 갖는다.
- 생성이력은 **현재 브라우저 IndexedDB**에 입력, 모델, 생성시각, 보고서 ID, 산식 버전과 함께 저장한다. 서버 공유 이력은 아니다. 공유·보존은 JSON 다운로드를 사용한다. 기관 담당자 인증 이름이 없으면 생성자를 임의로 기재하지 않는다.

## 데이터·판정 원칙

`GET /api/project-brief/{project_id}?as_of_date=YYYY-MM-DD`는 정책 보고서와 같은 캐시된 원장을 사용한다. 대표 ID 또는 명시적으로 연결된 원천 ID만 매칭하며, 복수 대표 매칭은 추측하지 않고 안내한다. 정책 합계 원장에 대표 ID가 없는 사업은 기존 사업 편집 화면의 관리값으로 보고서를 구성하고, 정책 합계 연결 미확인임을 표시한다. 다른 대표사업과 임의로 합치거나 정책 총량에 추가하지 않는다.

- 정책 보고서의 `contribution`, `schedules`와 공통 표·CSV 렌더러를 재사용한다. 사업 보고서가 별도로 실적·매핑을 수정하지 않는다.
- 기존 기준일 판본과 당시 매핑을 사용한다. 오늘 이후 보고일은 거절한다. 과거 조회 실패 시 최신값으로 대체하지 않는다.
- 원천 사건 / 등록 채택 / 추정 / 후행 근거 / 확인 필요의 구성합을 관리 도달량과 대조한다. `CONFIRMED`나 actor 이름은 기관 결재 증빙이 아니다.
- 기준선이 없으면 비교 불가. 최초 저장 관리계획을 최초 공식계획으로 부르지 않는다. 추정·월·분기·관측상한·서로 다른 물량 범위는 정확한 일수의 지연으로 계산하지 않는다.
- 기한 도래와 미측정만으로 실제 지연을 확정하지 않는다. 미확보를 0으로 치환하지 않으며, 실입주·실제 공정률을 계획·경과기간에서 생성하지 않는다.
- 원천 계획량과 대표 관리량을 나란히 유지한다. C2의 1,030호 공사범위와 344호 임대 관리범위를 합산하지 않는다. 하위 범위의 독립 포함관계가 확보되지 않은 공급유형 선택은 비활성화한다.
- A9의 원문 검증 사실 `AMENDED_APPROVED_STOCK`은 568→574호 변경승인 근거로 별도 표시한다. 관측일까지 승인된 총량이며 그날의 신규 승인량·최초 승인일이 아님을 명시한다.
- 일반 저장 판본 차이는 공식 변경승인으로 자동 해석하지 않는다. 변경 사유와 원문 검증 사실은 별도 붙임에서도 확인할 수 있다.
- 원천 최신성 주의는 기존 원장의 `STALE_SOURCE` 기준(원천 기준일 30일 초과)을 표시하며, 공식 사업 지연 등급으로 바꾸지 않는다.

## 성능과 재현

연결 원천의 반복 수집 판본마다 수집 배치 전체 manifest를 붙이면 한 사업에 수십 MB가 중복됐다. 보고서용 판본 조회는 단일 DB 조회로 판본 ID·batch ID·원래 payload hash·값·등록시각을 반환한다. 원본 파일은 기존 보관소에 유지한다. 최초 정책 원장 준비 약 3초, 사업 입력 준비 약 1.6~1.9초(운영 DB 점검 시), 이후 기준일·사업별 캐시를 사용한다.

브라우저 입력 저장소를 사용할 수 없을 때에는 저장 실패를 명시하고 JSON 보관을 안내한다. 독립적인 블록·유형 물량이나 담당기관·조치기한이 없으면 임의로 배분하거나 지정하지 않는다.

## 함께 적용한 화면 수정

- 공급유형별 추진절차 문서의 **05 · 팀 수집관리표 98개 출처 / 출처 URL·API 발굴 목록** 섹션, 메뉴 링크, 검색·필터와 해당 내장 목록 데이터를 제거했다. 후속 절 번호를 조정했다.
- **데이터 신뢰도 확인** 문서의 배경, 사이드바, 제목, 강조, 표, 버튼을 홈페이지의 파랑·청록·밝은 회색 테마로 통일했다. 성공·주의 의미색은 유지했다.

## 검증 자료

`tests/js/project-brief-report.test.cjs`는 실제 3개 사업 입력과 결측·0, 공급→착공 금지, 월/추정/상한 날짜, 비교 기준, 붙임 지연 생성, 입력 불변·동일 해시, HTML/CSV 이스케이프를 확인한다. `tests/test_project_brief.py`는 대표 ID 범위, 과거 시점, 미래 기준일 거절, 캐시 분리, 판본 해시·인지시각 경계를 확인한다.

샘플과 화면 검증 결과는 `docs/evidence/PROJECT_BRIEF_20261023/`에 있다. 실제 입력 fixtures는 `tests/fixtures/project-brief/`에 보존했다. 샘플은 원천 공정 보유 사업, 변경승인 근거 사업, 전체·부분 물량 차이 사업이며, 근거가 부족한 사업을 임의로 ‘정상 진행’으로 지정하지 않았다.


과거 기준일의 최초 입력 준비가 공개 프록시의 30초 제한을 넘는 경우를 확인했다. 보고서 요청은 15초 내 완료되지 않으면 HTTP 202로 준비 상태를 반환한다. 후속 조회는 같은 Future를 공유하며 계산을 중복 실행하지 않는다. 최대 4분 동안 같은 기준일 결과를 이어 받아 최신값으로 바꾸지 않는다. 직접 확인한 과거 최초 입력 준비는 약 75초, 준비 이후 조회는 약 0.03초였다.

전체 JS 회귀검사(프로젝트 디렉터리에서 실행)는 138건 중 137건 통과했다. 기존 `background-refresh.test.cjs`의 `수집 정상` 배지 테스트 1건이 실패했으며, 해당 테스트와 `app.js`는 HEAD 대비 변경하지 않았다. 이번 보고서 관련 JS·Python 검증과 실제 다운로드 검증 결과를 별도로 보존한다.

## 잔존 작업 마무리 (2026-10-23)

기능 범위를 유지하면서 다음 오류를 보완했다. 원장 데이터·매핑·실적·목표 산식은 변경하지 않았다.

- 보고서 준비 중 창을 닫아 후속 조회가 사라져도 완료된 작업은 다음 요청에서 대기열에서 회수한다. 결과는 기존 입력 캐시에서 재사용하며, 실행 중인 작업의 8개 제한과 같은 요청의 작업 공유는 유지한다. 동시 조회의 이전 응답이 새 작업을 삭제하지 않도록 작업 객체를 비교한다.
- 저장 보고서 복원 시 이전 비교일의 필수 여부도 복원한다. 현재 목록에서 빠진 저장 사업은 해당 보고서의 ID·이름으로 선택지를 복원하며, 남아 있는 검색 필터를 초기화해 다른 사업으로 잘못 보이지 않도록 한다.
- 요약보고서에서 4행을 초과하는 표는 표시 행 수·전체 행 수와 전체 표 확인 경로를 안내한다. CSV·JSON에는 전체 행을 유지한다.

검증: 관련 Python 10건, JavaScript 80건 통과. 브라우저에서 비교 조건 전환 후 이력 복원, 목록에서 빠진 사업 복원, 검색 초기화, 요약 행 생략 안내, 두 그래프 유지, JSON 다운로드를 확인했다. 브라우저 결과는 `docs/evidence/PROJECT_BRIEF_20261023/completion-verification.json`에 기록했다. 운영 서비스에도 같은 변경을 적용했다.
