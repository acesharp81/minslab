## 판단

추가 개선 여지가 있다. 우선순위는 전체 집계 스냅샷의 반복 저장, 대량 원문의 변경 확인·압축 보관, 상태 확인용 API의 경량화다. 수집 실패 재시도와 변경 없는 수집 후 재집계는 최신 작업자에 완화 장치가 이미 반영되어 있다. 과거 24시간 기록을 현재 설정의 지속적인 과부하로 해석해서는 안 된다.

API·일반 작업자·AI 작업자 사이에는 일부 코드 버전 차이도 확인됐다. 운영 화면의 실제 요청은 /ai-collection이며 10초 간격이다. 작업 소스의 /ai-agents, 실행 중 3초·대기 중 15초 설정과 다르다. 향후 배포는 역할별 명령은 구분하되 같은 릴리스의 호환되는 API·웹·작업자 조합으로 관리하고, 배포 해시와 기능별 확인 결과를 기록해야 한다.

원문 상위 저장량은 LH 상세 공고 12.72GB, 토지이음 고시 7.53GB, 건축물대장 4.04GB, LH 공고 목록 4.02GB다. LH 상세 파일 10개 표본은 원본 2,007,257바이트에서 gzip 450,660바이트로 줄었다(약 77.5%). 표본 결과를 전체 원문 회수 가능 용량으로 환산하지 않았다.

최근 스냅샷 12개에서 context/result의 known_at만 제외한 내용 해시를 비교했더니 4종류였다(동일 내용 그룹 7·2·2·1개). 내용 반복 저장은 확인됐지만, 관측 시각 자체는 업무 이력이다. 기존 스냅샷 ID를 지우거나 통합하는 대신 **불변 내용 객체 + 관측 시각·행위자·사유·내용 참조**로 분리하는 설계가 적절하다. 알고리즘 버전·입력 판본·범위·필터는 내용 해시에 반드시 포함해야 한다.

원문에는 이미 완전 동일 바이트 저장 방지와 일부 문서의 original_file/original_sha256만 바뀐 판본 생성 방지가 있다. 하지만 다운로드 이전의 ETag/Last-Modified 재검증 캐시는 일반 Fetcher에 없다. 동적 HTML의 비업무 부분 변화는 다른 원문 파일을 만들 수 있다. 이것이 원문 37.72GB 중 정확히 얼마인지는 전량 의미 비교를 하지 않았으므로 미확정이다.

## 반복 수집과 현재 완화 상태

최근 24시간 집계에서 LH 공고 85회 성공, LH 상세 44회 성공, GH 공고 44회 성공이 기록됐다. 일부 구조·링크 오류 출처는 각각 76회 실패했다. 배치 실행 횟수이며 실제 HTTP 요청 횟수와 같지 않다. 한 배치가 여러 페이지를 요청하거나 내부 HTTP 재시도를 할 수 있다.

현재 일반 작업자의 시작 시각은 2026-10-31 11:42:40 KST다. 그 이후 별도 집계에서 구조 오류 출처들은 각각 1회 실패 후 SOURCE_REPAIR_REQUIRED 상태였고, 해당 사유는 24시간 대기하도록 설정되어 있었다. 그 이후 새 집계 스냅샷은 0개였다. 이 짧은 관측만으로 하루 안정성을 확정할 수는 없다.

현재 운영 코드에는 다음 완화가 존재한다.

- 공고 감시 1시간, LH/GH/iH 공고 2시간, LH 상세 4시간, 일부 출처 6시간, 대부분 1일, 일부 주간 수집.
- 원천·작업자 잠금, 작업 lease와 재개, 최신 공고/과거 보강 작업 구분.
- 구조 변경 오류의 24시간 대기와 기존 정상 자료 유지.
- 명시적으로 데이터·수집 맥락이 동일하면 연결·전체 스냅샷 생성 생략.
- 과거 보강은 01~06시, 횟수 제한 적용.
- 일반 Fetcher에 HTTP 타임아웃과 Retry-After 처리 적용.

현재 SOURCES 카탈로그는 84개이고 수동 전용/미구현을 제외한 자동 후보는 75개다. 이는 자료관리표의 개별 URL·API 경로 수와 다른 집계다. 스케줄러는 매분 후보를 순회하며 원천마다 활성 작업·최근 성공·최근 실패 등을 개별 조회한다. 외부 수집이 아니라 내부 DB 점검 부하이므로, 전체 상태를 한 번에 읽고 next_run_at으로 기한 도래 출처만 선택하는 방식이 적절하다.

| AI 컨테이너 healthcheck | 20초마다 Store 생성 및 status 전체 실행 | heartbeat 한 행만 확인, 스키마 초기화·과거 이벤트 조회 제거 |

브라우저 재현에서는 최초 조회와 약 10초 뒤 AI 상태 조회가 관측됐다. 다른 메뉴로 이동한 뒤 17초 관측 동안 추가 AI 요청은 없었다. 따라서 현재 운영본에 '다른 메뉴에서도 계속 폴링' 문제가 있다고 확정하지 않았다. 브라우저 탭 자체의 숨김 상태를 확인하는 조건은 보완 대상이다.

사용량 화면은 내부 공용 예산 게이트웨이를 조회한다. 이 경로 자체가 모델 추론을 실행하거나 매번 공급자 인터넷 사용량 API를 부르는 구조는 아니다. 공용 원장에는 표시용 캐시를 적용할 수 있지만 **실제 모델 호출의 한도 예약·정산은 기존 원자적 처리로 유지**해야 한다. 표시의 최신성 완화가 PoC7·10·11 공용 한도 초과로 이어져서는 안 된다.

최근 30분 API 로그 표본에는 /health 90회가 있었고, 조회 시간대의 사용자가 거의 없었다. 장기 사용자 호출량이나 과부하 시간대의 총량으로 해석할 수 없다.

## 권장 적용 순서와 검증 기준

1. **릴리스 정합성과 가벼운 상태 조회**: API·웹·작업자 버전 확인, 전용 heartbeat 조회, 중복 heartbeat 제거, 이력 지연 조회, 대기 중 60초·숨긴 탭 정지. 한 탭이 계속 대기 상태라면 10초→60초는 이론상 시간당 360→60회다. 실제 절감량은 사용 시간에 따라 다르다. 모델 예약/정산 테스트 및 작업 중지 반응 확인.
2. **새 중복 저장부터 억제**: 자동 스냅샷의 관측/내용 분리, 관련 입력이 바뀔 때만 새 내용 생성. 수동 확정 기준본과 관측 이력은 계속 보존. 보고서 재현·입력 판본 추적 및 같은 내용 재사용 검사.
3. **원문 조건부 수집·압축**: 서버 지원 시 ETag/Last-Modified로 304 응답 사용, 원문은 해시 주소의 압축 객체로 저장. 목록 변경·정정 공고 탐색과 주기적 전체 확인을 유지해 수정 공고를 놓치지 않기. 원문 hash는 압축 전 기준, 읽기 경로는 이전 비압축 파일과 호환.
4. **기존 저장 데이터 정리 목록 생성**: 파일→판본→스냅샷→보고서 참조를 연결해 '참조됨 / 유일 원문 / 재생성 가능 캐시 / 미참조 후보'를 구분. 작업 산출물·임시 다운로드·미참조 중복부터 보존 정책에 따라 정리. 백업 복원·참조 무결성 검증 없이 전체 과거판본 삭제 금지.
5. **스케줄·재시도·운영 로그**: 기한 도래 작업만 일괄 조회, 원천/호스트별 동시 요청 수와 속도 제한, 일시 오류에 지수 지연·무작위 분산, 영구적 4xx와 구조 오류 분리. 중복 재시도 층을 줄이고 원문 재처리로 중복 실적이 생기지 않게 한다. 로그는 local driver 또는 명시적 크기·개수 제한.

수집 주기를 단순히 전부 하루 한 번으로 늦추는 방법은 권하지 않는다. 공고·정정은 1~2시간 목록 확인을 유지하고, 상세 원문은 신규·변경 중심, 통계/계획 자료는 공식 갱신 주기에 맞추는 구성이 적절하다. 추가 메시지 브로커나 별도 캐시 서버보다 기존 DB·작업 큐·파일 저장 구조를 먼저 활용한다.

## DB·로그 상태와 점검 한계

PostgreSQL 16.9, autovacuum on이며 최근 실행 기록이 있다. home_revision의 죽은 행 추정치는 약 3.8만/살아 있는 행 약 689만(약 0.55%)이다. 이것만으로 전체 bloat를 확정할 수는 없지만, 현재 23.21GB를 vacuum으로 전부 줄일 수 있는 공간으로 보는 것은 잘못이다. 배치 등 갱신 많은 작은 테이블은 별도 임계값 조정 여부를 모니터링한다.

컨테이너 로그는 json-file이며 명시적 회전 설정이 없었다. 현재 로그는 API 약 0.10MB, 지역 작업자 약 0.11MB, DB 약 3.08MB로 큰 저장량 원인은 아니지만 장기 보존 상한은 필요하다.

최근 판본·감사 이력을 전체 분류하는 두 쿼리는 15초 제한을 넘겨 중단됐다. 전체 판본의 정확한 불필요 데이터 비율·회수 가능 용량은 산출하지 않았다. 원문 전체 의미 중복 검사나 대규모 파일 hash 재계산도 하지 않았다. 저부하 시간대에 참조 목록을 증분 작성하는 후속 작업이 적합하다.

## 공식 문서 검토

- [MDN: HTTP conditional requests](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Conditional_requests): ETag/Last-Modified 검증으로 변경 없는 본문 전송을 생략. 원천 서버 지원 확인과 로컬 본문 보존이 필요하다.
- [MDN: Page Visibility API](https://developer.mozilla.org/en-US/docs/Web/API/Page_Visibility_API): 문서 가시성에 따라 불필요한 폴링을 중지하고 복귀 시 갱신.
- [AWS Builders’ Library: Timeouts, retries, and backoff with jitter](https://aws.amazon.com/builders-library/timeouts-retries-and-backoff-with-jitter/): 타임아웃, 재시도 한도, 지수 지연과 무작위 분산으로 장애 중 요청 증폭 방지.
- [PostgreSQL 16: Routine Vacuuming](https://www.postgresql.org/docs/16/routine-vacuuming.html): 일반 vacuum은 재사용 공간을 확보하고, VACUUM FULL은 강한 잠금과 추가 I/O가 필요해 상시 해결책으로 부적절.
- [PostgreSQL 16: Cumulative Statistics](https://www.postgresql.org/docs/16/monitoring-stats.html): 살아 있는 행·죽은 행 및 접근·정리 통계를 측정하는 기준.
- [PostgreSQL 16: NOTIFY](https://www.postgresql.org/docs/16/sql-notify.html): 필요 시 커밋 후 변경 알림으로 반복 확인을 줄일 수 있다. 알림 누락·재연결을 대비해 영속 버전/작업 큐와 저빈도 확인을 함께 유지한다.
- [Docker: Configure logging drivers](https://docs.docker.com/engine/logging/configure/): 기본 json-file은 로그 회전이 없어 local 또는 명시적 회전 설정 권고.
