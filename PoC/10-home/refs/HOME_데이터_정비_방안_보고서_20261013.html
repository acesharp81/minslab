HOME 데이터 정비 방안
정책과 사업을 연결하는 공통 식별체계

주택공급 정보는 여러 기관에 존재합니다. 이제는 정보를 더 많이 모으는 것을 넘어, 서로 다른 자료가 같은 정책·같은 사업·같은 공급물량을 가리킨다는 사실을 일관되게 확인할 수 있어야 합니다.

관계기관 협의용 보고서현행 구조 분석 + 개선 제안작성 기준 2026.10.13
정비의 출발점
정책·사업을 식별하는 공통 키가 원천 데이터에 없을 경우, 시스템은 명칭·주소·블록·수량을 대조하고 담당자가 연결 관계를 검토해야 합니다.
정비의 도착점
관리 주체가 공통 ID를 발급·관리하고 제공기관은 기존 원천번호와 함께 공통 ID 또는 공식 대응표를 제공하는 체계입니다.
01 · EXECUTIVE SUMMARY

핵심 제안: “정보 수집”에서 “정보 연결”로

본 보고서의 목적은 HOME이라는 개별 시연 시스템을 홍보하는 것이 아니라, 기관마다 따로 관리하는 주택공급 정보가 정책 집행관리에서 하나의 사실로 이어질 수 있도록 공통 연계기준을 정립하자는 제안입니다.

WHY · 왜 필요한가

같은 사업을 다른 번호로 관리

정책문서, 인허가, 공사현황, 공급공고, 입주자료의 관리번호가 달라서 동일 사업인지 사람이 판단해야 합니다.

WHAT · 무엇을 바꾸는가

공통 ID와 연결정보 제공

정책·프로그램·사업을 안정적으로 식별하고, 원천기관의 기존 ID 및 공급범위·단계·근거를 함께 관리합니다.

HOW · 어떻게 시작하는가

시범사업부터 단계적 확대

기존 API를 유지하면서 공통 식별키 추가 또는 공식 ID 대응표 제공을 시범 도입하고 품질을 검증합니다.

제안의 핵심
모든 기관이 정책ID 하나만 추가한다고 자동 연결이 완성되지는 않습니다. ① 정책·프로그램 귀속, ② 통합 사업 식별, ③ 지구·블록·공급물량 범위, ④ 원천 사건·판본을 구분해 연결해야 합니다. 다만 일회성 수작업을 반복하지 않도록 기관에서 확인된 식별정보를 제공할 수 있게 해야 합니다.
현재 자료에 설명된 실제 업무 테이블12개첨부 문서의 현행 구조 설명 기준. 독립 테이블과 JSON 내부 자료종류를 구분합니다.
통합관리하려는 사업의 주요 흐름6단계정책 → 사업화 → 인허가 → 건설 → 공급 → 입주
개선의 중심 수단공통 ID + 대응표원천번호를 폐기하지 않고 정책·사업·세부 공급범위와 공식적으로 연결
근거: 첨부 PDF 1쪽(검토 결론), 3쪽(현행 12개 테이블), 4쪽(단계별 저장·연결 경로), 6~7쪽(개선 요청).
02 · SERVICE OVERVIEW

HOME은 무엇을 하려는 시스템인가

주택공급 정책은 “몇 호를 공급하겠다”는 발표에서 끝나지 않습니다. 실제로는 사업 지정, 인허가, 건설, 분양·임대공고, 준공과 입주까지 여러 기관의 업무가 이어집니다. HOME은 이 진행을 하나의 정책·사업 흐름에서 확인하기 위해 개발 중인 통합 모니터링 PoC입니다.

동일 공급범위 기준 계획 대비 실제 진행·일정

시도·시군구 지도와 연도별 시계열의 연계

쉽게 말하면 HOME은 개별 기관의 기존 시스템을 대체하려는 것이 아니라, 기관들이 만든 공식 정보를 같은 사업이라는 연결고리로 묶어 한눈에 보는 상황판입니다.
03 · THE CORE PROBLEM

왜 지금은 자동으로 연결되지 않는가

같은 실제 주택공급 사업도 업무 단계와 기관에 따라 서로 다른 식별번호를 사용하기 때문입니다. 개별 API가 충분한 데이터를 제공하더라도, 그 번호가 어느 정책·프로그램·실제 사업에 해당하는지 자동으로 알 수는 없습니다.

한 사업이 여러 기관의 자료에 등장하는 모습
위 그림은 구조 이해용 개념도입니다. 실제 모든 기관이 현재 공통 사업ID를 제공한다는 의미는 아니며, 개선 후 모습은 향후 협의가 필요한 목표 모델입니다.
문제 1

이름이 같아도 다른 사업

지구 재지정, 사업 단계 분할, 동일한 블록명 반복 등으로 명칭만 같다고 동일 사업으로 확정할 수 없습니다.

문제 2

번호가 같아도 범위가 다름

하나의 지구 전체 3,000호와 하위 블록 1,200호를 동시에 더하면 계획물량이 중복됩니다.

문제 3

상태가 달라도 같은 숫자로 보임

계획·모집공고·준공·입주예정은 다른 단계의 수치이며, 하나의 공급 실적으로 합산하면 오류가 발생합니다.

근거: 첨부 PDF 1쪽, 5쪽(후보 정규화·물량 범위·PNU·공식 문서·저장 관계).
04 · AS-IS OPERATION

현재 HOME은 어떻게 연결·관리하고 있는가

HOME은 근거 없는 공식 ID를 만들어 기관이 부여한 ID인 것처럼 사용하는 구조가 아닙니다. 기관별 원천 객체와 판본을 보존하고, 정규화한 사업 후보에 연결 근거와 검토 상태를 별도로 관리합니다. 현재 연결은 담당자의 확인이 전제되는 업무상 매핑입니다.

1. 수집

원천 보존

API·공개파일·공식 문서 수집. 수집 배치, 원본 해시, 판본 기록.

2. 후보 생성

사업 찾기

기관 원천번호, 지구·블록명, 주소, 시기 등을 비교.

3. 범위 판정

같은 물량인가

전체·일부·중복·분할, 공급유형과 공고 차수를 구분.

4. 검토·이력

담당자 승인

검토·확정·연결 해제와 판단 근거·변경 이력 관리.

현재 자료에 설명된 12개 실제 테이블

DB 구조를 모르는 독자를 위해 기능별로 묶었습니다. policy, permit, project 등의 자료종류는 주로 home_revision.kind로 분류되는 원천 정보이며, 모두 독립 물리 테이블을 뜻하지 않습니다.

반드시 구분할 두 종류의 사업 ID
첨부 자료의 현행 설명에서 PRO_…는 원천 사업 객체를 구분하는 home_revision.entity_id, HPR_…는 HOME에서 생성한 통합 사업 후보 home_project.id입니다. 두 값을 이름만 보고 같은 번호로 취급하면 잘못 연결될 수 있습니다. 이 구분은 향후 공식 사업ID 설계에서도 유지되어야 합니다.

현재 매칭에 활용하는 근거

01

원천 고유번호

기관·자료종류와 해당 시스템의 객체번호를 함께 사용합니다.

어떤 근거로 누가 연결했는지, 이후 어떤 변경이 있었는지 보존합니다.

05 · TO-BE ARCHITECTURE

개선 방향: ‘찾아 맞추기’에서 ‘함께 식별하기’로

현행의 원천 수집·원본 보존·담당자 검토 기능은 유지하되, 정책관리 주체와 원천기관이 같은 사업을 가리키는 공통 식별정보를 함께 관리하는 체계로 전환합니다. 핵심은 모든 기관의 데이터베이스를 하나로 합치는 것이 아니라, 기존 데이터를 서로 연결할 수 있는 최소한의 공통 언어를 마련하는 것입니다.

06 · IDENTIFIER DESIGN

정책ID만이 아니라 무엇을 식별해야 하는가

서로 다른 기관에 같은 번호를 붙이려면 **무엇을 하나의 객체로 볼 것인지부터 합의**해야 합니다. 정책은 여러 프로그램을 포함할 수 있고, 하나의 사업은 여러 정책에 포함될 수 있으며, 지구 전체와 하위 블록은 공급범위가 다릅니다.

10 · ROADMAP

일괄 개편보다 단계적인 공동 정비가 현실적입니다

기존 시스템을 전면 개편하면 업무 중단·예산·데이터 정합성 문제가 발생할 수 있습니다. 먼저 실제 원천키와 통합 후보를 확인하고, 일부 사업에서 공통 ID 체계를 시범 적용한 뒤 관계기관과 점진적으로 확대하는 방법이 합리적입니다.

1단계 · 공통 정의
식별 대상·권한 합의

정책/프로그램/사업/블록 구분, 발급·정정 주체, 필수 필드 결정

2단계 · 시범 등록
골든셋·대응표 구축

서로 다른 유형의 실제 사업 선정, 기존 번호와 공통 ID의 대응 정확도 검증

3단계 · 공급기관 연계
API/파일 추가 제공

기존 API 필드 유지 + 공통 ID 및 공식 대응표, 배치·판본 시험

4단계 · 운영 정착
확대·품질관리

기관별 적용범위 확대, 변경·해제 이력, 담당자 검토와 성과 관리

단계기관 간 핵심 협의구체적 산출물다음 단계로 넘어갈 기준
1. 표준·권한 합의무엇을 동일 사업으로 볼지, 누가 공식 ID를 발급할지표준 데이터 사전, ID 규칙, 관계·범위 코드, 책임 분담중복·합병·분할·취소 예외를 해석할 수 있는 정의 승인
2. 시범사업 검증기관 원천 사업번호와 공통 사업ID 대응 확인시범 사업목록, 매칭 근거, 오류·누락·보류 사례집대표 유형에 대해 수집→매칭→담당자 검토→재수집 일관성 통과
3. 제공체계 시험원천 API 수정 또는 공식 대응표 제공 방식 선택버전 호환 API 명세/대응표, 시험 결과, 권한·이용조건 검토기존 이용자 영향 없이 신규 키 및 대응관계 조회 가능
4. 상시 관리기관별 데이터 품질·갱신 책임과 이의처리등록부 운영지침, 품질 대시보드, 변경·해제 이력 관리체계오연결·누락·기준일·집계 충돌을 정기 확인하고 조치
단기 성과의 현실적 목표
모든 정책·사업을 한 번에 완전 연결하겠다고 선언하기보다, 선정된 시범사업에서 인허가·공사·공급·입주 자료가 공통 ID와 근거를 통해 얼마나 정확하게 재현되는지 검증하는 것을 우선합니다.
