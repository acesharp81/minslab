# 검수 이력 조회 성능 개선 — 2026-11-05

## 원인

운영 DB의 검사 27건에 약 1억 286만 글자의 상세 JSON과 255개 검사 버전이 저장되어 있었다. 이전 목록 API는 약 9KB의 제목·상태만 반환하면서도 `Store.jobs()`로 전체 본문과 과거 버전을 읽고 Python에서 모두 해석했다. `ORDER BY created`용 인덱스도 없어 전체 스캔과 임시 B-tree 정렬이 발생했다.

검사 버전 버튼 역시 전체 상세를 다운로드했고, 결과 열기·진행 조회와 이미지 존재 확인에서도 과거 이력을 반복 해석했다.

## 변경

- `job_history`에 목록과 버전 선택용 경량 요약을 저장한다. 최신순 `(created DESC, id DESC)` 인덱스와 상태 인덱스를 추가했다. 원본 `jobs`에도 최신순 인덱스를 추가했다.
- `Store.save()`는 원본과 요약을 같은 트랜잭션에 저장한다. 기존 데이터는 최초 한 번 요약을 생성한다.
- 기존 원시 SQL 기반 가져오기·보완 스크립트를 위해 삽입/수정 트리거는 변경 ID만 `job_history_dirty`에 기록한다. 조회 전에 해당 건만 트랜잭션으로 갱신한다. 삭제 시 요약도 정리한다. 본문 전체를 트리거에서 반복 파싱하지 않는다.
- 목록 API는 요약만 읽는다. `/api/jobs/{id}/versions`는 모델·결과 수·검토 수·관찰 재사용 가능 여부만 반환한다.
- 화면의 결과 열기·진행 조회는 `?view=latest`로 최신 검사 한 버전만 받아온다. 특정 과거 버전이 재분석에 필요할 때는 `run_id`로 해당 버전만 읽는다. 실패한 최신 검사에서 이전 관찰을 재사용하는 경로도 보존했다.
- 기본 상세 API와 JSON 보고서는 기존처럼 전체 이력을 제공한다. 원본 결과·기준자료 스냅샷·검토 기록을 줄이거나 삭제하지 않는다.
- 이미지 GET은 기본키로 존재 여부만 확인한다. 이미지 한 장을 보내기 위해 전체 이력을 해석하지 않는다.
- 서버 시작 시 진행 중인 검사와 대기열 수는 상태 인덱스로 조회한다.
- 목록의 중복 클릭은 하나의 진행 중 요청으로 합치며 로딩 상태를 표시한다. 버전 목록은 펼침/접힘 시 같은 데이터를 반복 요청하지 않는다.
- 다른 이력 카드의 과거 판독으로 재분석할 때, 그 카드의 검사 ID·버전 ID를 사용하도록 연결했다.
