## 1. 종합 결론

**업무바통으로의 프로젝트 전환은 타당하며, 이전 HWPX 전환 MCP 3종보다 제출용 MVP의 실현 가능성이 높다.**

임의 HWPX 양식의 쓰기 위치 발견과 서식 보존을 필수 범위에서 제외했고, 다음과 같이 업무의 시작과 끝이 명확해졌다.

> 자료 등록 → 근거 있는 인수인계 초안 → 전임자 수정·확정 → 후임자 활용

다만 현재 계획에는 다음 가정이 남아 있다.

1. 전수 색인과 범주별 검색만으로 전체 업무를 충분히 파악할 수 있다.
2. 검색 엔진에 전달한 원문 블록 ID와 사건 ID가 결과까지 자연스럽게 보존된다.
3. 근거 ID가 존재하면 생성 내용의 정확성도 확보된다.
4. 검색 MCP를 별도 컨테이너에 배치하면 API 서버와 바로 연결할 수 있다.

이 가정들은 그대로 구현하면 업무 누락, 출처 연결 오류, 사건 간 자료 혼합, 배포 지연으로 이어질 수 있다. **문서별 순회 추출, 검색 엔진과 독립된 근거 저장, 확정본 우선의 후임자 활용**을 핵심 설계로 추가할 것을 권고한다.

- 지원 포맷과 입력 규모를 명확히 제한한다.

## 4. 핵심 설계 변경 권고

### 4.1 초안 생성은 문서별 순회 추출을 기본으로 한다

현재 계획의 **전수 색인 + 범주별 다중 검색**은 업무 포괄성을 보장하지 못한다. 모든 문서가 색인되어도 유사한 문서가 검색 상위 결과를 차지하면, 드물게 언급된 중요한 업무가 초안에서 빠질 수 있다.

권고 처리 흐름:

```text
모든 문서의 정규 블록
  → 문서별 업무·일정·현안 후보 추출
  → 같은 업무끼리 통합
  → 관련 자료 검색으로 근거·충돌 보강
  → 인수인계 초안
  → 전임자 수정·확정

후임자의 질문
  → 확정본 + 연결된 원문 검색
  → 근거 있는 답변
```

문서마다 `추출 완료 / 관련 업무 없음 / 일부 미해석 / 실패`를 남긴다. 긴 문서를 블록으로 나눠 처리하는 경우 미처리 블록도 기록한다.

검색은 근거 보강과 후속 질의에 유용하지만, 초안 작성 대상 전체를 결정하는 유일한 경로로 삼지 않는다.

### 4.2 근거 식별자는 검색 엔진 밖에서 관리한다

실제 `minirag-mcp` 입력 API는 다음 형태다.

```python
ingest_data(data, source, format="text", title=None)
```

임의의 `block_id`, 원문 셀 주소, 원본 해시를 구조화 메타데이터로 전달하는 인자가 없다. 엔진이 입력을 다시 청킹하며, 동일한 `source`를 재사용하면 기존 색인을 교체한다.

따라서 계획서의 `SourceBlock → chunk_id → EvidenceLink` 관계는 별도 연결 계층이 필요하다.

권고:

1. 업무바통 DB가 불변 원문 revision과 정규 블록을 보존한다.
2. 검색용 `source`와 사건·문서 revision·블록 식별자 간 매핑을 저장한다.
3. 검색 결과를 DB의 실제 원문 블록으로 역조회한다.
4. 확정본 인용은 변경 가능한 검색 청크 번호만 참조하지 않는다.
5. 재색인 후에도 기존 확정본의 근거가 유지되는지 시험한다.

API 근거: `minirag-mcp 1.0.0` 배포의 `minirag_mcp/server.py`, `minirag_mcp/ingest/pipeline.py`.

### 4.3 검색 범위와 사건 접근 통제를 분리한다

배포 코드의 `scope`는 source 경로 범위를 제한한다. 범위를 생략하면 전체 인덱스가 조회 대상이다. 인접 청크 조회는 source를 직접 받는다.

`case_id`를 문자열에 넣는 것만으로 모든 도구의 격리가 보장되지는 않는다. 다음 중 하나를 선택해야 한다.

- 사건별 인덱스 저장 경로를 분리한다.
- 공유 인덱스를 쓰되 백엔드가 모든 검색·원문 조회·삭제 호출에서 사건 범위를 강제하고 검사한다.

시연 규모에서는 **사건별 인덱스 분리 + 쓰기 작업 직렬화**를 우선 권고한다. 역할 선택 화면은 시연용이며 실제 인증·권한 통제를 대체하지 않는다.

근거: `minirag-mcp 1.0.0`의 `minirag_mcp/scope.py`, `server.py`.

### 4.4 인용 존재와 내용 정확성을 각각 검증한다

유효한 근거 ID나 원문 발췌가 있다고 해서 생성 내용이 정확한 것은 아니다.

예를 들어 원문의 “검토 후 11월 말까지 제출 예정”을 “11월 30일 제출 확정”으로 바꾸면 출처가 있어도 의미가 왜곡된다.

검증을 세 층으로 나눈다.

1. 문서·블록·revision의 존재 확인.
2. 인용문이 해당 블록에 실제 포함되는지 확인.
3. 날짜·담당자·상태가 인용문의 의미를 넘어서는지 검토.

`예정/확정`, `요청/완료`, `담당/협의`를 구분한다. 원문에서 추출한 사실과 AI가 제안한 다음 행동을 별도로 표시한다. 근거 없는 사실 확정을 막되, 명확히 표시된 업무 제안까지 금지할 필요는 없다.

### 4.5 확정본과 원문 사이의 우선순위를 정한다

파일 수정 시각만으로 최신 업무 상태를 판단하지 않는다. 문서 작성일, 적용 시점, 문서 역할, 전임자 확인을 함께 고려한다.

전임자가 기한을 수정·확정한 뒤 후임자 질문에 과거 원문만 검색해 이전 기한을 답하는 문제를 막아야 한다.

> 후임자 답변은 확정 인수인계 revision의 해당 항목을 먼저 확인하고, 원문은 근거 또는 차이 설명에 사용한다.

- 전임자 직접 입력값은 `전임자 확인값`으로 표시하고 원문 추출값으로 위장하지 않는다.
- 확정 이후 자료가 추가되면 새 초안을 만들며 이전 확정본을 보존한다.
- 사실 출처와 사용자 확인 여부는 함께 존재할 수 있으므로 데이터 모델에서 두 속성을 구분하는 편이 좋다.

### 4.6 부분 추출을 처리 상태에 반영한다

텍스트가 일부 나왔다고 문서 전체가 읽힌 것은 아니다.

| 포맷 | 주요 확인 항목 |
|---|---|
| PDF | 스캔·텍스트 혼합 페이지, 텍스트가 없는 페이지, 표 읽기 순서 |
| XLSX | 날짜 표시 형식, 계산식과 저장된 결과, 셀 주소·표 머리글 |
| HWP/HWPX | 표 값과 머리글 관계, 병합셀, 누락된 개체 |
| DOCX | 본문 외 머리말·주석 등 중요 내용의 지원 범위 |

`parse_status=SUCCESS` 외에 부분 추출 여부와 경고를 보존하고, 초안 coverage에 반영한다. 초기 지원은 텍스트 PDF와 단순 표 중심으로 제한할 수 있다.

### 4.7 배포·전송·긴 작업 처리 방식을 명시한다

확인한 `minirag-mcp` 기본 진입점은 `stdio`다. 별도 컨테이너에 띄운다고 HTTP 연결이 자동 제공되는 것은 아니다.

초기에는 API 컨테이너가 검색 MCP를 subprocess로 실행하는 방식이 단순하다. 별도 컨테이너가 필요하면 전송 방식을 명시적으로 구성하고 시험한다.

파싱·임베딩·초안 생성을 하나의 긴 HTTP 요청으로 처리하지 않는다. 최소한 다음을 갖춘 작업 상태 관리가 필요하다.

- 작업 상태·파일별 진행률.
- 실패 단계만 재시도.
- 중복 업로드·생성 방지.
- 새로고침 후 결과 보존.
- 단일 인덱스의 쓰기 직렬화.

대형 큐 시스템은 필수 조건이 아니다. 임베딩 모델의 최초 다운로드·캐시 준비는 설치 절차에 포함한다. CPU 실행 가능성은 준비 없이 즉시 실행 가능하다는 의미가 아니다.

## 5. 공개 소스 채택 시 보완 사항

`minirag-mcp` 우선 실증은 합리적이다. 다만 후보 교체와 배포에는 다음 확인이 필요하다.

| 항목 | 확인·권고 |
|---|---|
| minirag 라이선스 | 실제 배포 메타데이터는 `MIT AND Apache-2.0`. 대표 저장소 라이선스만 보지 않고 배포 고지 확인 |
| 대체 엔진 비용 | `mcp-local-rag`는 Node.js 런타임·다른 임베딩·청킹 구현을 검증해야 함 |
| PDF 전이 의존성 | 대체 엔진의 `mupdf` 배포 메타데이터는 `AGPL-3.0-or-later`. 상위 프로젝트 MIT 표기만으로 검토 종료 금지 |
| SQLite FTS5 축소안 | 엔진 축소만으로 한국어 검색 품질이 해결되지는 않음. 표현 변형·기관명·번호·날짜 시험 필요 |
| 모델 변경 | 임베딩 모델·청킹 변경 후 색인 재생성과 검색 회귀 시험 필요 |

출처:

- [minirag 배포 메타데이터](https://pypi.org/pypi/minirag-mcp/1.0.0/json)
- [mcp-local-rag 배포 메타데이터](https://registry.npmjs.org/mcp-local-rag/0.23.2)
- [MuPDF 배포 메타데이터](https://registry.npmjs.org/mupdf/1.28.1)

이는 확인된 라이선스 식별자와 검토 필요성을 기록한 것으로, 전체 의존성의 배포 의무 실사가 완료되었다는 의미는 아니다.

## 6. 권고 MVP 범위

| 반드시 완성 | 핵심 완성 후 추가 |
|---|---|
| ZIP 또는 폴더 입력 중 하나의 안정적 경로 | 두 입력 방식 모두 |
| 지원 포맷의 실제 추출, 실패·부분 추출 표시 | OCR·복잡한 표 |
| 문서별 업무 후보 추출·통합 | 추가 자동 분류 |
| 항목별 근거·확인 필요·충돌 표시 | 연간 달력 |
| 전임자 수정·확정·revision | 후임자 수락 상태 |
| 후임자 확정본 열람·근거 조회 | 자연어 질의응답 |
| Markdown/HTML 출력 | HWPX 출력 |
| 새 환경 설치·재현 | UI 미화 |

HWP는 제한 실행 시험이 성공했으므로 지원 후보로 유지한다. 실제 시연 자료에서 실패하면 HWPX 재등록 경로로 제한하고 해당 실패를 명확히 표시한다.

15개 파일 제작·정답표 작성·검색 엔진 설치·한글 파서 시험을 첫날 모두 완료하는 일정은 낙관적이다. 먼저 작은 혼합 세트로 핵심 흐름을 검증하고 최종 15개로 확대하는 편이 현실적이다.

## 8. 품질 지표와 필수 시험

현재 계획의 검색 Top-5 Recall 외에 **중요 업무 누락률**과 **필드별 근거 정확성**을 추가한다.

| 지표·시험 | 검증 목적 |
|---|---|
| 포맷별 추출 성공·부분 추출·실패 | 색인 성공과 원문 해석 완전성 구분 |
| 한국어 검색 Top-5 Recall | 정답 근거 구간의 검색 가능성 확인 |
| 중요 업무 누락률 | 정답표의 핵심 업무 중 초안에 빠진 업무 확인 |
| 날짜·담당자·상태·다음 행동의 근거 정확성 | 근거 존재와 의미 일치를 구분 |
| 근거 없는 질문·원문 속 지시문 | 사실 임의 확정 및 문서 내용의 명령 취급 방지 |
| 구판본·신판본의 충돌 | 수정 시각만으로 임의 확정하지 않는지 확인 |
| 전임자 수정 후 후임자 질의 | 확정본 변경 내용이 실제 활용되는지 확인 |
| 재색인 후 이전 확정본 열람 | 근거와 revision의 불변성 확인 |
| 두 사건의 동일·유사 문서 검색 | 사건 간 자료 혼합 방지 |
| 작업 실패·재시도·새로고침 | 중복 생성·데이터 유실 방지 |
| 새 환경 설치부터 다운로드 | 평가자 재현 가능성 확인 |

## 10. 최종 권고

**업무바통 방향으로 전환하되, 문서별 전수 추출·독립된 근거 저장·확정본 우선 활용을 추가한 제한 MVP로 진행할 것을 권고한다.**

가장 먼저 입증할 장면은 검색 결과의 양이 아니라 다음 과정이다.

> 전임자가 실제 근거를 보고 한 항목을 수정·확정하고, 후임자가 그 수정된 내용으로 다음 업무를 파악한다.

이 흐름을 안정적으로 완성하면 지정과제의 목적과 구현 현실성을 함께 충족할 수 있다. MCP·추가 포맷·출력 서식은 이 흐름을 지원하는 수단으로 배치한다.
