## A. 실행 요약

첨부 계획서는 사용자가 의도한 **독립된 문서 전환 MCP 3종을 구축하고 AI Works Lite로 시연하는 PoC13**과 잘 맞는다. 공개 HWPX 라이브러리와 기존 저장소에서 기술적 실현 근거도 확인했다.

다만 기존 기능을 묶는 것만으로 완성할 수 있는 프로젝트는 아니다. 신규 양식의 요구정보·정확한 기입 위치 발견, 동적 사실의 의미 구조화, 오매핑 차단과 승인, 원본 양식 보존 생성은 추가 구현과 실증이 필요하다. **11월 11일까지 계획 전체를 완성할 수 있다고 확정할 근거는 아직 부족하다.**

추진 조건은 다음과 같다.

1. 예산요구서 원본 1종과 구조가 다른 대상 양식 2종을 확정한다.
2. 두 양식 모두에서 핵심 작성 위치를 찾고 시험값을 안전하게 기록할 수 있음을 먼저 입증한다.
3. 자동 분석과 사용자 보정을 구분하고, 불확실하거나 충돌하는 매핑을 코드로 차단한다.
4. MCP 3종이 기존 Hub와 Lite 없이도 호출 가능하도록 독립 계약을 갖춘다.
5. 설치·실행·출력 검증에 필요한 시간을 기능 개발과 별도로 확보한다.

### 권고 프로젝트 정의

> PoC13은 HWPX 원자료에서 근거 있는 정보를 추출하고, 새로운 HWPX 양식의 요구사항에 맞춰 재구성하여 새 문서를 생성하는 독립 MCP 프로젝트다. AI Works Lite는 이를 검토·승인·시연하는 클라이언트다.

여기서 문서 전환은 파일 확장자 변경이 아니라 **업무 양식 간 정보의 의미적 전환과 재사용**을 뜻한다.

### 기존 자산에 대한 주의점

- `_hwpx_template_schema()`는 `{{title}}`, `{{content}}` 등 사전 표식을 찾는 방식이다. 이를 처음 보는 양식의 의미 분석 구현으로 평가하면 안 된다.
- `report_hwpx.build_document()`의 본문 재구성 경로는 임의 대상 양식의 지정 셀 보존 쓰기와 목적이 다르다.
- `mcp/` 디렉터리나 manifest가 있다는 사실만으로 정식 MCP 서버가 되는 것은 아니다.
- 기존 RHWP 브리지에는 `aiworks.rhwp-bridge/1` 자체 메시지 형식이 있다. 이를 목표 MCP 서버 3종의 독립 프로토콜 구현 증거로 삼지 않는다.
- 기존 golden 시험은 사전 표식 기반 양식 준비·품질 검사 등을 포함한다. 미지 양식의 의미·위치 정확도를 독립 정답표로 검증하는 시험과 구분해야 한다.

### API 확인의 의미와 한계

- automation 배포 코드의 `hwpx_automation/handlers/form_fill.py`에서 세 API를 확인했다.
- `analyze_form_fill`은 원본 파일과 입력 데이터 또는 계획을 받는다. API 이름만으로 행정 양식의 업무적 의미를 자동 발견한다고 볼 수 없다.
- 배포 메타데이터에서 automation은 `python-hwpx>=6.5.0,<7`을 요구하며, MCP extra는 `mcp==1.28.1`을 명시한다. 의존성 범위 충족은 실제 호환성 시험 통과와 다르다.
- upstream README는 소스 변경과 공개 배포 상태를 구분한다. `main`의 예제·기능과 설치 버전을 혼합하지 않는다.
- **현재 권고 버전은 시험 후보이며 검증 완료 버전이 아니다.** 실제 fixture 통과 후 버전·배포 해시·의존성을 고정한다.
- 라이선스 식별자와 고지 파일 포함은 확인했지만, 모든 전이 의존성의 배포 의무와 제3자 고지 전체 실사는 완료하지 않았다.
- 전체 후보의 최근 commit·핵심 issue·설치 성공 여부를 망라하는 실사는 완료하지 않았다.

## E. 핵심 설계 보완 권고

### E.1 독립 프로젝트 경계

PoC13 자체 실행 설정·의존성·파일 저장 영역·프로젝트 저장소를 갖춘다. 기존 Hub DB나 대형 `backend.py`의 직접 import를 필수 조건으로 만들지 않는다. 공통 엔진 코드는 공유할 수 있으며 독립성을 이유로 세 번 복제할 필요는 없다.

### E.2 동적 항목과 고정 의미 규칙의 구분

항목명은 문서에서 동적으로 발견하되, 금액·연도·예산단계·계획/실적·총액/부분액 같은 의미 속성은 공통 규칙으로 정의한다. 이는 양식별 하드코딩이 아니라 오매핑 방지 계약이다.

현재 예시에 다음 계약을 보완한다.

- `MetadataSchema`: 필드 정의와 값 인스턴스를 분리하고 정의 버전을 관리한다.
- `ProjectFacts`: 사실별 안정적인 ID, 사업·세부사업 식별, 기간·범위·예산단계, 원본값·정규화값·근거, revision을 보존한다.
- 반복 항목: 단순 필드 목록 외에 행·사업·세부과제의 소속 관계를 표현한다.
- `TemplateSchema`: 원본 해시, 스키마 revision, 지원 구조, 필드 요구정보, 검증된 쓰기 anchor를 포함한다.
- `MappingPlan`: 사실·양식 버전, 대상 위치, 최종 표시값, 변환 규칙, 누락·충돌, 계획 해시를 포함한다.
- `DocumentArtifact`: 승인된 입력 스냅샷과 엔진·모델 설정, 출력 해시 및 검증 결과를 보존한다.

### E.3 MCP ②의 현실적인 첫 목표

첫 목표는 **지원 구조 내 자동 발견 + 사용자 확정**으로 한정한다. 구조 지도 → LLM 의미 해석 → 유효 anchor 검사 접근은 타당하다.

다만 유효한 셀을 선택했다는 사실만으로 의미까지 정확하다고 입증되지는 않는다. 위치 존재, 작성란 여부, 업무적 의미를 각각 검증한다. 의미와 위치의 자동 성공률 및 사용자 보정량을 따로 측정한다.

### E.4 빈칸 쓰기 범위

빈 셀에는 치환할 텍스트 노드가 없을 수 있고, 한 문장이 여러 텍스트 조각으로 나뉠 수 있다. 따라서 기존 노드의 값 치환만 허용하면 정상적인 빈 양식도 처리하지 못할 수 있다.

**기존 셀·문단 안의 최소 텍스트 노드 생성은 허용하되, 행·열·표 구조 변경은 제외**하는 경계를 권고한다. 지원하지 않는 구조는 명시적으로 반환한다.

### E.5 구조 검증과 시각 검증 분리

XML 재파싱과 구조 비교가 통과해도 긴 문장으로 셀 넘침이나 쪽 나눔 변화가 생길 수 있다. `VerificationReport`는 구조 검증·값 검증·시각 검증을 분리한다.

대표 산출물은 한글에서 실제 열림, 잘림, 페이지 배치를 확인한다. RHWP 열람만으로 한글 호환성을 확정하지 않는다. 시각 검증을 수행하지 않았다면 미검증으로 표시한다.

### E.6 승인과 의미 매핑

`approved=true`만으로 생성 권한을 표현하지 않는다. 승인은 `facts_revision`, 원본 양식 해시, 양식 스키마 버전, 매핑 계획 해시, 최종 작성값에 결합한다. 사실이나 매핑이 바뀌면 이전 승인은 무효가 되어야 한다.

요구액/확정액, 총액/단년도액, 계획/실적, 다른 사업의 값 혼동은 LLM 설명뿐 아니라 결정적 규칙으로 차단한다. 누락값과 충돌값은 추정해 채우지 않는다.

### E.7 파일 전달과 MCP 독립 실행

MCP ③에는 사실 스냅샷과 `TemplateSchema`뿐 아니라 해당 원본 HWPX에 접근할 수 있는 파일 참조가 필요하다. 입력·출력 파일 참조, 허용 경로, 해시, 오류 형식을 공통 계약으로 정의한다.

초기에는 Lite 백엔드가 독립 MCP 서버 3개를 `stdio`로 호출할 수 있다. 독립성은 HTTP 포트 3개 운영 여부가 아니라 정식 프로토콜과 독립 호출 가능성으로 판단한다.

근거: [MCP 전송 규격](https://modelcontextprotocol.io/specification/2025-06-18/basic/transports).

### E.8 우선순위와 재현성

두 번째 양식은 성공 기준이므로 후순위 선택 기능으로 두지 않는다. 두 양식의 구조·쓰기 시험은 P0, 최소 Lite 검토·승인 UI와 두 문서 E2E는 필수 범위다. 화면 미화·성능 최적화는 후순위로 둔다.

동일 입력의 재현성은 LLM을 다시 호출할 때 동일 결과를 보장하는 의미로 사용하지 않는다. 승인된 사실·스키마·매핑 계획·최종 작성값을 고정한 뒤 생성 결과를 검증하는 범위를 명확히 한다. 파일 바이트 동일성까지 요구한다면 ZIP 타임스탬프 등 추가 조건도 별도로 정의해야 한다.
